Design rationale — the lane-first information architecture

1 · What is a lane

A lane is a durable, named enforcement responsibility — gate · kernel-purity, freshness, buck2, gate-live-postgres-adapters. It outlives any one run. A run is one observation of a set of lanes against one candidate SHA.

Today no lane object exists anywhere in the system. The Actions UI re-creates 56 job rows per run and throws them away; cloud-ci-run-terminal-state/v1 is likewise a per-run document with a lanes[] array keyed by job_name. The lane is a derived entity: group artifacts by job_name across runs. That derivation is the whole IA. Everything else follows from having a lane to hang evidence on.

2 · What is a lane's evidence

Straight off the v1 contract, no invention:

  • state — one of pass | fail | no-verdict | blocked | verified-empty.
  • next_action — the single permitted action. This is the payload; the state is the reason.
  • because — the kernel's one-line derivation, naming the typed fields that decided it. Never a log excerpt.
  • failed_steps / unfinished_steps — repo-authored workflow step names. The discriminator between a gate rejected you and no gate ever looked.
  • queue_delay_seconds — starvation. A lane property that is invisible in any run-shaped view.
  • annotations — corroborating only, never the discriminator. Never leaves the console (§5).
  • input_digest + classifier_version — the verdict is bound to the exact bytes and the exact rules that produced it.
  • Observation history — (run_id, candidate_sha, observed_at, state, next_action) per run. This is the chronology, and it is inside the lane.

3 · What is the default view

“Needs a human, by lane.” Not a run list, not a reverse-chronological wall. The left rail is the primary navigation and it is a lane selector, bucketed by permitted next action, severity-first. Time is a strip inside the selected lane.

The measured argument, from the two real runs embedded in this page:

  • Run 30677213867 — 56 lanes: 50 pass, 5 fail, 1 no-verdict. The single lane that is machine-clearable (gate · affected-set → retry, the runner died mid-step) is buried among five that need a code change. A timestamp-ordered list makes those six look identical.
  • Run 30692655896 — 11 lanes, 7 red. Discounting the fan-in (§3) that is 6 real failing lanes, and 4 of those 6 failed on the identical step (Materialize cloud-ci generated faces, with and without its (out-of-graph boundary) qualifier). A fifth, registry-drift, failed on Materialize faces then assert byte-parity — same root cause, different step name, so the signature grouping does not catch it and the rail honestly shows ▸ grouped ×4 rather than claiming ×5. Four rows collapse to one action; the fifth is a known limit of grouping on a step-name signature, and the fix is a lane-to-root-cause edge the contract does not carry today.
  • Queue delay in run 30692655896 reaches 8226 s (2 h 17 m). That is a fleet-capacity story that a per-run view structurally cannot tell, because it only becomes a signal across runs of the same lane.

The fan-in lane is not a lane. oya-ci-required appears in lanes[] as fail / fix-candidate in both runs, but it is the roll-up of the others, not an independent observation. It is promoted to the header verdict and removed from the rail — otherwise it double-counts every real failure and adds a row that no human can act on.

4 · What “needs a human” means, per state

A red lane is not automatically a human's problem. retry is the only red outcome a machine may clear on its own, and today it is indistinguishable from fix-candidate — which is exactly the cost the typed states were introduced to remove.

statenext actionneeds a human?who, and what they decide
passproceedno—
failfix-candidateyescandidate author — a gate observed a violation in the change
no-verdictretry (attempt 1)nomachine-clearable; surfaced but not queued to a person
no-verdictfix-infra (attempt > 1)yesfleet owner — repeat infra fault is systemic, “retry harder” is not a remediation
blockedwaitno — unless the run roll-up is also blockedpipeline owner — a run where every lane is waiting is a wedge, and nothing upstream will ever clear it
verified-emptyneeds-humanalwaysrule owner — a rule with 0 measured sites enforces nothing; only a person can say whether that is a dead rule or a broken scan

The blocked row is the one rule the contract does not give you for free: it needs the run roll-up as context, which is why the lane view keeps the roll-up in the header rather than discarding it.

5 · Sanitization — what may leave the console

Two projections of the same lane, and the boundary is reusability: a card that can be pasted into a ticket, a chat, or a status page is a different object from what an authenticated operator sees.

fieldshareable cardwhy
job_name, state, next_actionkeepthe failure and the decision — the point of the card
becausekeepkernel-authored from typed fields; contract-guaranteed never to be a log excerpt
failed_steps, unfinished_stepskeepworkflow step names, already public in .github/workflows/; this is the invariant that was violated
input_digest, classifier_version, candidate_shakeepattribution — makes the card re-verifiable instead of merely quotable
ownerkeep — but v1 has no owner fieldsee §6
annotationsclass onlyfree-form operator text. In the real embedded data it already carries a filesystem path (/tmp/cache-hit-report.json), process exit codes, and a curl/HTTP error. Reduced to a typed class (runner-lost, process-exit, artifact-missing, network) plus a redaction count.
queue_delay_secondskeepa scalar; no operational context in it
job_id, run URLs, logsdropinternal handles; a log line is the exact thing the typed contract exists to stop passing around

The sanitizer is an allow-list, never a deny-list: an unknown future field is dropped by default. The deny-list in the self-check above is not the mechanism — it is the test of the mechanism, and it includes a synthetic ghp_ token control so a green result proves the check can fire at all rather than proving only that nothing happened to match.

6 · Defects this design surfaced in the v1 contract

  • No owner field. cloud-ci-run-terminal-state/v1 carries no owner and no repo path, so a “needs a human” view cannot route to a human — it can only display that some human is needed. The repo already has the mapping (OWNERS files: console/OWNERS → axis-cloud-platform, evidence/OWNERS → cloud-ci-platform), but nothing joins a job_name to a path. The card shows the gap rather than inventing a name.
  • Lane identity is a display string. job_name is "gate · kernel-purity (ADR-0547, *-kernel/*-core zero transient-tech deps)" — identity, an ADR reference, and a human description fused into one field. Any cross-run join is therefore a string match against a value that changes whenever someone edits the parenthetical. A stable lane_id would make the lane a real entity instead of a derived one.
  • verified-empty is unreachable in practice. It requires the --subjects sidecar, which no lane emits today; both real fixtures classify with an empty SubjectCounts. The state exists in the type and has never once been produced. This prototype renders it from the contract and labels it as never-observed rather than pretending it is live.

7 · What this prototype is not

  • Not wired to anything. No fetch, no poll, no API. Two frozen JSON documents, embedded.
  • No auth, no tenancy, no Cedar visibility tiers — the console's real surface catalog (console/ports/workspace-shell-kernel) has a six-tier visibility model this ignores entirely.
  • Not Leptos. HTML/vanilla JS, per the prototypes-then-Leptos convention.
  • Not responsive beyond a single breakpoint, and untested on the tablet / VR-AR targets the console must eventually serve.
  • No lane history beyond the two captured runs — every lane strip here is 1 or 2 observations deep, because that is all the real data there is.
