# skill-conformance-ratchet

A drafting-quality ratchet for the `~/.agents` skill corpus (`skills/` +
`adapters/codex/skills/`). One file, stdlib only, no dependencies.

**Destination:** this belongs in `~/.agents/`, not in this repo. It is staged
here because the authoring lane was confined to an isolated worktree. Move it at
landing. It is a linter, not vendored skills — unrelated to the retired
`tools/agent-skills/` tree.

## Why it exists

The official validator (`skills-ref`) checks frontmatter validity and naming
only. Nothing checks whether a skill will actually be *selected* by the model or
*executed* once selected. That is what this checks.

An earlier prose standard failed because it demanded descriptions open with the
literal string `Use when`. Measured against this corpus, **0 of 34 skills pass
that rule** — a standard nothing satisfies is not a standard. The governing rule
here is: *write the assertion, do not describe it.* Every assertion ships with a
violating fixture that it must reject, and `--selftest` proves it.

## Usage

```bash
python3 skill_conformance.py             # check against baseline; exit 1 on regression
python3 skill_conformance.py --selftest  # prove every assertion bites
python3 skill_conformance.py --freeze    # regenerate baseline.json
python3 skill_conformance.py ROOT ...    # override corpus roots
```

`baseline.json` is generated by `--freeze`. Never hand-edit it.

## The five assertions

Chosen by (violations prevented) / (effort to comply). Baseline is the frozen
failure count; the ratchet fails if any assertion exceeds it.

| assertion | baseline | what it prevents |
|---|---:|---|
| `description_states_trigger` | 28/34 | description says what the skill *does* but never *when* to use it, so it is never selected |
| `description_min_length` | 14/34 | a 33-char description cannot disambiguate from 33 sibling skills |
| `body_within_line_budget` | 3/34 | SKILL.md over 500 lines burns context that belongs in `references/` |
| `body_has_example` | 3/34 | pure prose with no fenced block gives the model nothing executable |
| `refs_resolve` | 1/34 | body points at a `references/`/`scripts/` file that does not exist — fails at use time, so nothing else catches it |

## Deliberately NOT built

- **No frontmatter-validity or name-matches-directory checks.** `skills-ref`
  owns those, and all 34 skills already pass them. Duplicating them adds noise.
- **No "description must open with `Use when`" rule.** 0/34 pass; it is a style
  rule, not a substance one. `description_states_trigger` is the substantive
  version — it accepts a trigger clause anywhere in the description.
- **No unknown-frontmatter-key check.** The corpus legitimately uses ecosystem
  extensions (`argument-hint`, `triggers`, `role`, `scope`); flagging them would
  force deleting working metadata.
- **No H1-required check.** Five skills use XML-ish bodies (`<Purpose>`); that is
  a valid style, not a defect.
- **No description-max-length check.** The 1024-char limit exists, but the corpus
  max is 511. Zero bite, so it does not ship.
- **No YAML dependency.** The frontmatter is flat `key: value` plus folded
  scalars; a hand-rolled 15-line reader covers it.
- **No auto-fix, no CI wiring, no per-skill severity, no config file.**

## Known limitation

The baseline stores *counts*, not names. Fixing one skill and adding an equally
broken one nets to zero and passes. Store the failing sets if that becomes a real
problem — it costs baseline churn on every rename, which is why it is not done
here.
