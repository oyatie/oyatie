**Nothing in the build graph expresses a dependency rule.** Every structural invariant is enforced by after-the-fact detection, when the build system can make violations unrepresentable.

## Principles

1. **Prevent, don't detect.** If the build graph can make an edge impossible, no gate should be needed to find it.
2. **Start from the observed graph, not the ideal.** The first landing is a provable no-op; tightening is a separate, reviewable act.
3. **Visibility enforces the FACE seam; the tier gate keeps the DAG direction.** They are complementary, not redundant — do not try to encode ADR-0280 ordering in visibility allowlists.
4. **Ride the reorg.** Every move rewrites labels already; visibility lands at zero marginal cost during a move and at full retrofit cost after.
5. **Evidence over narration** — the no-op proof is a byte-identical target graph, not an assertion.

## The two halves of the mechanism

buck2 gives both directions, and clean architecture needs both:

- **`visibility`** — *who may depend on me.* Enforces encapsulation (nothing outside reaches `core/`).
- **`within_view`** — *what I may depend on.* Enforces the inward rule (a `core` crate cannot reach an adapter).

`within_view` is the half that actually encodes clean architecture, and it is currently unused repo-wide.

## The grammar

Per capability, one `PACKAGE` file per face — **4 files × 24 capabilities ≈ 96 files, or ~24 if set at the capability root with per-face blocks.**

| Face | `visibility` (who may depend on it) | `within_view` (what it may depend on) |
|---|---|---|
| `<cap>/core/**` | `<cap>/ports`, `<cap>/adapters`, `<cap>/facade` | `<cap>/core`, `base`, `third-party`, **other caps' `ports` only** |
| `<cap>/ports/**` | `PUBLIC` — this is the cross-capability seam | `<cap>/core`, `base`, `third-party` |
| `<cap>/adapters/**` | `<cap>/facade` only — adapters vanish at cutover | `<cap>/core`, `<cap>/ports`, `base`, `third-party` |
| `<cap>/facade/**` | `app/**` | `<cap>/ports`, `<cap>/adapters`, `base`, `third-party` — **NOT `<cap>/core`** |

That last cell is ADR-0562 §4's non-negotiable rule ("a facade composes core ONLY through ports") expressed as a build constraint rather than a gate finding. `adapters` is included per §10.6's composition-root reality, which is currently an ungated exception.

**Meta directories:**

| Dir | `visibility` | `within_view` |
|---|---|---|
| `base/**` | `PUBLIC` | `third-party` only — `base` is the floor, it depends on nothing first-party |
| `kernel/**` | `os/**` | `third-party` (own excluded workspace) |
| `os/**` | capability roots | `kernel`, `base`, `third-party` |
| `governance/**`, `build/**` | off the runtime ladder — unconstrained |

**Cross-capability rule, stated once:** a capability may depend on another capability's `ports/`, never its `core/`. Visibility enforces this exactly. It does **not** enforce ADR-0280 DAG *direction* — encoding "only capabilities above me" would need per-capability allowlists that rot. `layer-dependency-acyclicity` keeps that job.

## Migration path — the no-op-first ratchet

The critical constraint: **buck2 visibility has no advisory mode.** It builds or it does not. So correctness must precede enablement.

**Step 1 — Generate visibility that exactly permits today's graph.** Derive the real edge set (`buck2 uquery` over `//...`), emit the minimal `visibility`/`within_view` that admits every existing edge. Landing this is a **provable no-op**: the target graph and full build are byte-identical before and after.

**Step 2 — Prove the no-op.** `buck2 targets //...` diff empty; full build green. This is the gate on Step 1, and it is mechanical.

**Step 3 — Tighten one rule at a time.** Each tightening is a small diff, and **its build failures ARE the violation list** — precise, exhaustive, and generated by the compiler rather than by a bespoke scanner. Suggested order, cheapest and highest-signal first:
1. `adapters` visible only to own `facade` (transient-tech containment, ADR-0510)
2. `facade` cannot see own `core` (ADR-0562 §4 — replaces `facade-core-layering`)
3. cross-capability `core` invisible (replaces the "12 packages / 21 edges reach another capability's core" class the gate explicitly declines to cover)
4. `base` within_view = third-party only (proves the floor is a floor)

Each step lands with its failures either fixed or explicitly carved out — the same shrink-only discipline as the existing baselines, but expressed where it cannot go vacuous.

## What this changes about the gate fleet

| Gate | After visibility |
|---|---|
| `facade-core-layering` | **backstop** — should never fire; 35 baselined keys become build failures to fix |
| `core-dependency-isolation` | partially subsumed; keeps the 21-entry transient-dep denylist (third-party, not first-party edges) |
| `layer-dependency-acyclicity` | **keeps** DAG direction + cycles — visibility cannot express ordering |
| `port-placement` | **keeps** — it checks where a trait is *defined*, not an edge |

Net: two gates demoted to backstops, two keep distinct jobs. The point is not deleting gates — it is that **a backstop that never fires is a healthy gate, and a primary detector with 35 baselined violations is not.**

## Why this serves the stated goals

- **Parallelism** — visibility is a per-package property in PACKAGE files. Two capabilities' visibility can be authored concurrently without touching a shared file, unlike every registry/policy edit that currently serializes moves.
- **Owned domain / clean architecture** — the seam becomes a build fact rather than a review convention. `within_view` is literally the dependency-inversion rule.
- **Engineering rigor** — violations are found by the compiler, exhaustively, with no baseline, no corpus to go vacuous, and no gate to keep wired.
- **Organization** — visibility forces each capability to state its public surface, which is the question the reorg is actually asking.

## Pre-mortem

**1 — Step 1 is not a no-op and breaks the build.** The generated allowlist misses an edge (a buck-only dep, a genrule, a `mapped_srcs` reference).
*Mitigation:* derive from `buck2 uquery` over the real graph, not from Cargo manifests — the two surfaces differ, and §10.6 records `intelligence/facade/worker` carrying an edge in BUCK with zero Cargo path-deps. Prove with a full `//...` build, not a subset.

**2 — Tightening stalls because the violation list is large.** Step 3.3 (cross-capability core) already has a known ~21-edge population.
*Mitigation:* each tightening is independently landable and independently revertable. A tightening that reveals too much becomes its own burn-down, not a blocker on the others.

**3 — Visibility and the reorg fight each other.** A capability moves, its labels change, its PACKAGE file goes stale.
*Mitigation:* author visibility **as part of each move**, not as a separate sweep. For the 22 already-moved capabilities, land it now; for the rest it rides the move. This is the whole reason to plan it before the remaining 467 crates move.

## Test strategy

**Governing axiom (founder): a test that never failed is never a good test.** Every rule below lands RED-first — the assertion is demonstrated failing against the unfixed tree before the fix, and the failure is recorded. A test authored green is not evidence.

**Measured baseline for the whole repo** (`origin/dev`): 1,123 `rust_test` targets · proptest in **2 of 928** manifests · loom 1 · **fuzz targets 0** · `[[bench]]` **1** · chaos/soak/k6 in CI **0**. Unit and integration coverage is real; every other tier is absent.

### Tiers that apply to visibility, and why

| Tier | Applied how | Value |
|---|---|---|
| **RED/GREEN** | A synthetic `facade -> own core` edge **must fail to build** before the rule is claimed enforced. Same for each Step-3 tightening. | The only proof that prevention replaced detection |
| **Property-based** | The face relation is a 4×4 matrix. For all `(from_face, to_face, same_capability)`, generated edge legality must equal the declared matrix. `proptest` already exists in-tree (2 manifests), so no new dependency. | Exhaustive over the rule space, not over examples |
| **Metamorphic** | **Moving a crate must not change its legality.** Generate a move, re-derive visibility, assert the legality verdict is invariant. | Directly tests the reorg interaction — the highest-risk coupling in this plan |
| **Regression** | Step 1's no-op proof (byte-identical `buck2 targets //...`); each tightening's post-fix failure list frozen as a test | Prevents silent re-widening |
| **Black-box** | Tests assert *"the build fails"*, never *"the PACKAGE file contains X"* | Tests the enforced behaviour, not the encoding — the encoding may change |
| **Performance** | buck2 graph-evaluation wall-clock before/after Step 1; visibility adds constraint checks to every edge | A structural gain that costs build latency is a trade, not a win — measure it |
| **Compatibility** | The full-tier matrix already spans 6 platforms; Step 1 must be green on all, not just local darwin | Local-green is not the authoritative signal here |

### Tiers that do NOT apply — and saying so is part of the rigor

**Chaos, soak, load, usability** are runtime properties. Visibility is a build-graph constraint with no running surface; applying them here would be theatre. **Security** is indirect — visibility prevents a coupling class, but it is not an access control, and claiming it as a security test would be an overclaim of exactly the kind `parity-claim-evidence` exists to reject.

Naming the inapplicable tiers explicitly is deliberate: an unjustified test tier is how a suite becomes expensive noise that nobody trusts.

### The repo-wide gap this exposes (separate workstream, recorded not scoped)

The tiers absent from the whole repo are the ones that make **agentic fanout safe**, which is the original Bun question:

- **Fuzzing: 0 targets.** Bun ran 24/7 coverage-guided fuzzing post-merge and cited it as load-bearing for the rewrite's safety. Parsers, the codemod, canonical-JSON, and the AST substrate are the obvious first targets.
- **Property-based: 2 of 928.** Every pure kernel (`*-kernel`, 156 crates under `core-dependency-isolation`) is a property-test candidate by construction — they are pure by policy.
- **Benchmarks: 1 `[[bench]]`,** against 26 markdown files asserting performance baselines. That asymmetry is a claim-without-evidence surface.
- **Chaos/soak: 0 in CI**, against ADR-0248's `chaos_drill_cadence_days` declared per DAG node — a cadence nothing executes.
- **Test-bearing crates are wildly uneven**: `ci` 47/51 and `iam` 60/68, versus `workflow` **1/48**, `os` 3/41, and `console`/`gateway`/`flags` at **0**.

That last line is the one that matters for migration sequencing: **a capability at 92% test-bearing can absorb aggressive automated change; one at 2% cannot, because any "green" there is the absence of tests rather than the presence of correctness.** Test density should be an input to move ordering, and it currently is not.

## Acceptance criteria

- [ ] Step 1 lands with a **byte-identical** `buck2 targets //...` output and a green full build — the no-op proven, not asserted.
- [ ] `PACKAGE` file count > 0 and `within_view` uses > 0 (both are currently 0).
- [ ] Each Step-3 tightening lands with its failure list either fixed or carved out with a stated reason; no tightening lands with a new baseline.
- [ ] `facade-core-layering`'s baseline shrinks by the count that tightening 3.2 fixes.
- [ ] A synthetic illegal edge (facade → own core) **fails to build** — the RED proof that prevention replaced detection.
