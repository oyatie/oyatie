# Research: ci-webhook-replay-guard — Canonical Rules, Sources, and Slice Constraints

**Scope**: Standards governing webhook idempotency / delivery-dedup, GitHub
delivery-header semantics, and the verify-then-guard-then-dispatch ordering
invariant (ADR-0367). Written to constrain T1–T4 implementation choices with
verifiable citations. Produced at the BEST-PRACTICE RESEARCH stage; superseded
by the slice spec (`slice-ci-webhook-replay-guard.md`) for implementation
decisions.

---

## 1. Webhook at-least-once delivery — foundational guarantee

**MUST assume at-least-once.** Every mainstream webhook sender (GitHub, GitHub,
Stripe, Shopify) retries on non-2xx or timeout. A receiver that does not
implement deduplication WILL process events multiple times under normal
operational conditions (network blips, pod restarts, brief Jenkins unavailability).

Sources:
- [Webhook Delivery Guarantees — At-Least-Once, Retries, HMAC & Dead Letters](https://codelit.io/blog/api-webhooks-delivery-guarantee): "Always design for at-least-once. It is the only practical guarantee for webhooks."
- [Idempotency and Deduplication — Svix Webhook University](https://www.svix.com/resources/webhook-university/reliability/idempotency-and-deduplication/): "Every well-designed webhook includes a unique event ID. This identifier stays the same across retries."

**Consequence for this slice**: the guard is not optional hardening — it is the
minimum correct behaviour for a Jenkins dispatch receiver.

## 2. GitHub delivery-header semantics (authoritative source: Gitea/GitHub source)

GitHub is a hard fork of Gitea. The webhook delivery mechanism is shared.

### 2a. Headers sent per delivery

Source: Gitea `services/webhook/deliver.go`
(`https://raw.githubusercontent.com/go-gitea/gitea/main/services/webhook/deliver.go`),
function `addDefaultHeaders`:

```go
req.Header.Add("X-Gitea-Delivery", t.UUID)
req.Header.Add("X-Gogs-Delivery",  t.UUID)
req.Header["X-GitHub-Delivery"] = []string{t.UUID}
// GitHub adds:
// X-GitHub-Delivery: t.UUID  (compat alias)
```

The compatibility set sent by GitHub is:
`X-GitHub-Delivery`, `X-Gitea-Delivery`, `X-GitHub-Delivery`, `X-Gogs-Delivery`
— all carry the same UUID from `HookTask.UUID`.

GitHub documentation also lists:
`X-GitHub-Event`, `X-GitHub-Signature` (HMAC-SHA256 of payload using the
configured secret).
Source: [GitHub Webhooks Documentation](https://github.org/docs/latest/user/webhooks/)

### 2b. UUID stability across automatic retries (CRITICAL for key derivation)

Source: Gitea `models/webhook/hooktask.go`
(`https://raw.githubusercontent.com/go-gitea/gitea/main/models/webhook/hooktask.go`):

```go
// CreateHookTask — called once at event time:
t.UUID = gouuid.New().String()   // generated ONCE, stored in DB with UNIQUE constraint

// ReplayHookTask — called for manual redelivery via UI/API:
return CreateHookTask(ctx, &HookTask{
    HookID:         task.HookID,
    PayloadContent: task.PayloadContent,
    // UUID is NOT copied → new UUID generated by CreateHookTask
})
```

**Conclusion**:

| Delivery scenario | UUID behaviour |
|---|---|
| Automatic retry (network failure, non-2xx) | **Same UUID** — same HookTask row retried |
| Manual redelivery (UI "Redeliver" button or API) | **New UUID** — new HookTask row created |

**Rule MUST-1**: `X-GitHub-Delivery` is stable across automatic retries and is
therefore a reliable idempotency key for deduplicating network-retry duplicates.

**Rule MUST-2**: Manual redeliveries receive a new UUID, so they bypass the
delivery-id dedup path and are dispatched as `FirstSeen`. This is correct
behaviour: a human explicitly requesting redelivery after a failed build window
expects the job to fire again.

### 2c. Header absence

The GitHub webhook documentation does not guarantee the header is always
present. The `unwrap_or("unknown")` sentinel in `lib.rs` is the correct
defensive handling. The sentinel MUST NOT be used as a literal dedup key
(distinct events without the header would collide). The fallback
`(head_sha, pr_number, CiAction)` tuple is the correct content-addressed key
for this case.

## 3. Idempotency key-derivation rules

**Rule MUST-3 (primary key)**: Use the provider's delivery ID (`X-GitHub-Delivery`)
as the primary dedup key when present and non-sentinel. It is stable across
automatic retries and is the cheapest, most precise dedup signal.

Source: [Hookdeck — Implement Webhook Idempotency](https://hookdeck.com/webhooks/guides/implement-webhook-idempotency):
"Use the webhook provider's unique ID … Repeated requests for the same webhook
will have the same webhook identifier."

Source: [codelit.io — Webhook Delivery Guarantees](https://codelit.io/blog/api-webhooks-delivery-guarantee):
"Generate the ID on the sender side — the same event must always have the same
ID across retries."

**Rule MUST-4 (fallback key)**: When delivery-id is absent, derive a
content-addressed key from immutable payload fields. For a CI trigger event the
minimal stable tuple is `(head_sha, pr_number, action)`. All three fields are
present on `CiTriggerEvent` at the wiring point (after Step 4 route).

**Rule SHOULD-1**: Use a stable discriminant (`u8`) rather than the enum itself
for hashing when the enum does not implement `Hash`, to avoid touching upstream
crates. This is the approach in `DeliveryKey::ContentHash.action_disc`.

**Pitfall — sentinel collision**: If the header-absent sentinel (`"unknown"`) is
used as a literal delivery ID, all header-less events collide on one key. The
implementation avoids this by treating "unknown" as equivalent to absent and
falling back to content hash.

## 4. Record-before-dispatch ordering (record-on-receipt)

**Rule MUST-5**: Record the delivery key BEFORE executing the side effect
(Jenkins trigger), not after.

Source: [Hookdeck — Implement Webhook Idempotency](https://hookdeck.com/webhooks/guides/implement-webhook-idempotency):
"Mark events as processed before executing side effects. If you send an email
first and mark as processed second, a crash between those two steps means the
retry will send the email again."

Source: [Svix — Idempotency and Deduplication](https://www.svix.com/resources/webhook-university/reliability/idempotency-and-deduplication/):
"INSERT event_id into processed_events (with unique constraint) → If constraint
violation: return 200 (duplicate detected) → If insert succeeds: proceed with
business logic."

**Consequence**: A concurrent replay of the same delivery arriving while the
first is still in-flight (Jenkins is being polled synchronously in Steps 7-8)
is deduped correctly with record-on-receipt. With record-on-success, the
concurrent replay would bypass the guard and fire Jenkins a second time.

**Accepted trade-off**: If the first delivery fails at Step 5 (Jenkins 502),
the key is already recorded. A legitimate retry within the TTL returns a 200
idempotent ack without re-triggering. This is best-effort single-instance dedup,
not a correctness guarantee. Operators can wait for TTL expiry (5 min) before
manually redelivering. A manual redelivery via the GitHub UI receives a new
UUID (see §2b) and therefore bypasses the guard as `FirstSeen` automatically.

## 5. TTL window

**Rule SHOULD-2**: Set the TTL long enough to cover the provider's automatic
retry window, but short enough to bound memory growth.

Source: [Hookdeck — Implement Webhook Idempotency](https://hookdeck.com/webhooks/guides/implement-webhook-idempotency):
"Set your idempotency TTL to exceed the retry window."

Source: [Svix — Idempotency and Deduplication](https://www.svix.com/resources/webhook-university/reliability/idempotency-and-deduplication/):
"A daily job that deletes records older than seven days is usually sufficient."

**GitHub automatic retry behaviour**: GitHub (Gitea upstream) uses an
exponential back-off retry schedule. Automatic retries are typically exhausted
within minutes for transient network failures; the GitHub UI shows a
"Recent Deliveries" list but does not document a maximum retry window. In
practice, automatic retries for a single delivery arrive within seconds to a
few minutes.

**Chosen TTL: 300 000 ms (5 minutes)**. Rationale:
- Covers all realistic automatic retry storms (seconds–minutes).
- Does not cover the 24 h GitHub manual-redelivery window (intentional:
  manual redeliveries get new UUIDs per §2b, so they dispatch as `FirstSeen`
  regardless of TTL).
- Keeps the in-memory `HashMap` small at typical CI delivery rates
  (tens of events/hour at most).

## 6. Verify-before-guard ordering invariant (ADR-0367)

**Rule MUST-6**: The guard MUST NOT be evaluated before signature verification
and authz succeed (Steps 2-3). Guard state must never be mutated by an
unauthenticated or unauthorized request.

Rationale (ADR-0367, §Decision.1 + §Decision.2):
> "The author-agent's self-reported evidence is never trusted … The merge gate
> verifies the *signature* of the trusted runner — a fabricated or self-reported
> evidence file has no valid signature and is rejected."

Applied to the receiver: allowing an unauthenticated request to record a key
into the guard would let an attacker pre-poison a delivery ID, causing the
legitimate first delivery to be treated as a replay and silently dropped (no
Jenkins kickoff, no pipeline). This is a denial-of-service vector specific to
pre-auth state mutation.

**Rule MUST-7**: Guard state mutation (record) MUST occur only after:
1. ed25519 / HMAC signature verification passes (Step 2).
2. Cedar authz gate passes (Step 3).
3. Event routing succeeds and produces a `Trigger` outcome (Step 4).

The wiring point in `lib.rs` (Step 4.5, between `route_github_event` and
`state.jenkins.trigger`) satisfies all three conditions.

**Rule SHOULD-3**: The explicit comment in `lib.rs` naming the ordering
(verify+authz+route → guard → dispatch) SHOULD be preserved. It is the
on-code evidence that the ADR-0367 ordering invariant is intentional, not
accidental.

## 7. In-memory vs durable store

The current implementation uses an in-memory `HashMap` (no persistence across
pod restarts). This is appropriate for the single-instance, best-effort dedup
goal of this slice.

**Rule SHOULD-4**: The in-memory store limitation SHOULD be documented in the
module-level doc comment (already present in `replay.rs`) and named as a
follow-up item alongside task #62.

**Pitfall — storage volatility**: An in-memory store loses all recorded keys on
pod restart. Any delivery that arrives in the window immediately after restart
will be treated as `FirstSeen`, even if it was already dispatched before the
restart. For the CI gateway use case this is acceptable: a pod restart during
an active Jenkins build is already a fault condition, and the Jenkins job is
idempotent with respect to the eventual status-post result.

Source: [Hookdeck — Implement Webhook Idempotency](https://hookdeck.com/webhooks/guides/implement-webhook-idempotency):
"In-memory caches lose data on restart, allowing duplicate processing."

## 8. SLO compatibility (ADR-0130)

The existing `ci-webhook-gateway.openslo.yaml` defines two SLOs:
1. `ci-webhook-gateway-dispatch-latency-p99` — p99 webhook-received → Jenkins-kicked latency (target: ≤ 5 000 ms at 99th percentile).
2. `ci-webhook-gateway-signature-verify-availability` — fraction of deliveries with non-fault verify (target: ≥ 99.9%).

**Idempotent replay acks (200 OK "duplicate delivery, already accepted") are
NOT errors** under either SLO:
- They are not counted as latency events in (1) because they short-circuit before
  Jenkins trigger (no dispatch occurs, no latency to measure).
- They are not faults in (2) because 200 is not a 5xx; the verify step completed
  successfully before the guard ran.

No SLO objective needs updating. The OpenSLO file remains valid as-is.

**Rule SHOULD-5**: If a future stage adds per-outcome Prometheus counters, replay
acks SHOULD be counted under a distinct `outcome="replay"` label, not
`outcome="error"` or `outcome="dispatch"`. This preserves SLO accuracy.
