## Intern read order

1. Start with **Foundation ADRs 0001-0100** for product thesis, tenancy, identity, audit, data boundary, flat architecture, and build/test basics.

2. Read **Expansion and Consolidation ADRs 0101-0241** when you need the active implementation and governance substrate history.

3. Read the **Keystone Bundle ADRs 0242-0258** before changing tenant scope, Cedar gates, substrate/product boundaries, compliance packs, deployment topology, or API versioning.

4. Read **Post-Keystone Hardening ADRs 0263-0296** for observability, consent, backup portability, owner-name indirection, and Foundry trust-root controls.

5. Read **Wave-3-G ADRs 0297-0321** for abuse defence, life-safety, personal/work boundaries, enterprise coverage, and universal B2B SaaS scope.

6. Check **Per-microservice ADR-MS** rows when changing a service that has a local decision contract.

## Maintenance protocol
- Add new portfolio-wide decisions under `docs/decisions/ADR-NNNN-*.md`; add service-local decisions under `microservices/<service>/decisions/ADR-MS-NNN-*.md` only when the service owns the decision.
- Keep ADR frontmatter populated with `id`, `status`, `date`, `owners`, `related`, and a `purpose` summary; the index degrades gracefully, but thin ADR metadata makes intern navigation weaker.
- Do not renumber ADRs to close gaps. Gaps are forensic evidence of retired, deferred, or skipped decision slots.
- When the source-shape caveat is fixed, run `./bin/oya doc adr-index --write --format json` and preserve this cluster-oriented human guide.
