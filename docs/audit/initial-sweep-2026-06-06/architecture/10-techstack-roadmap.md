# 10 — Tech-Stack Roadmap: NOW → PLANNED → FINAL-IDEAL

> **Lens.** READ-ONLY. Source-backed from the REAL trees (`/Users/jasonlee/Developer/source` = the oyatie monorepo on branch `phase0/producer`; `/Users/jasonlee/Developer/linux` = the kernel/OS/k8s self-hosting pilot). Each substrate is read off real crate/service dirs, `Cargo.toml` dep pins, and PRD/IP bridge files — NOT off ADR prose. The clean-arch crate-role suffixes (`-kernel` / `-domain` / `-usecase` / `-app` / `-api` / `-rest` / `-sdk` / `-worker`) name the layers; `-adapter-*` + `-api`/`-rest` ARE the ports/adapters seams (the mobility points where a vendored bridge today is swapped for the owned engine tomorrow). One crate per bounded-context = cohesion; crate-per-BC in a multi-BC service = detachment-for-scale.
>
> **Doctrine driving every row (the universal ratchet, D-META / D-CLOUD-NATIVE):** own-the-endpoint / vendor-the-bridge / **build-the-owned-alongside → run parallel/shadow → cutover only when the gate fires (proven) → THEN retire the bridge.** Never retire a bridge before its owned replacement is built and proven. So NOW = vendored bridge live; PLANNED = the confirmed next owned piece being built alongside; FINAL-IDEAL = bespoke owned endpoint, dogfooded (oya = tenant `oyatie-internal`) as part of a hyperscaler-class cloud.
>
> **Posture (D-CLOUD-NATIVE):** cloud-native services/controllers/pipelines, "do what Go does, cloud-native, in Rust" — NOT a CLI toolbox. The `oya` CLI is retired and stays retired.

## How to read the seam (clean-arch evidence)

The mobility seam in every row is a **`-adapter-*` crate sitting in front of an owned `-kernel` / `-domain` crate**, exposed through an `-api`/`-rest` port. Three live exemplars from the real tree prove the ratchet is *structural*, not aspirational:

- **CI:** `oya-ci-controller-kernel` (owned domain) ← `oya-ci-controller-github-adapter` + `oya-ci-webhook-gateway-jenkins-adapter` (vendored bridges). Swap the adapters at cutover; the kernel is forge/CI-engine-agnostic.
- **Identity:** `oya-identity-oidc-issuer-kernel` (owned) ← Zitadel adapter IPs (bridge). Cut over by retiring the Zitadel adapter.
- **AI:** the owned engine domain ← `oya-intelligence-adapter-{anthropic,openai,gemini}-api` + `-subscription` (vendored provider bridges, dual-consumption). Re-home down to `cloud-intelligence`, converge calls, retire mocks.

Where the owned kernel does **not** yet exist, the row is honest about it: **PARC** (policy engine) is ~2 hits / essentially unestablished — a real net-new build behind the permanent Cedar contract; the **owned distributed DB engine** has no source (design-spec only — L8 dropped from the migration, deferred to a future build campaign); **`cloud-scm`** has no dir yet (GitHub-interim only).

## Sequencing note (D8 / D-SEQ / D-LANES)

"Own everything, sequenced" ≠ "build everything at once." **oya-ci is the day-0 crown-jewel** (its output is the ability to build the rest — unblocks the dogfood loop), but builds **parallelize** (fractal parallel/sequential lanes). The infra-sovereignty ratchet is an **ordered list + per-substrate M0 evidence-gate (contract + incumbent benchmark + evidence before owning), NO calendar dates.** Every OWN-when-proven cutover is gated by ADR-0510's trigger and the ADR-0123 maturity-claim-gate — no parity claim without measured evidence.
