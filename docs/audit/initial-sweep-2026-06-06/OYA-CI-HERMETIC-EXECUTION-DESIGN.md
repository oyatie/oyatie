## 0. HEADLINE (the git-facts boundary decision + the design in one screen)

**The git-facts boundary decision (the crux):** Git is inherently ambient and CANNOT be made a pure function of declared inputs *inside* a hermetic action. The standard hyperscale resolution (Bazel/Buck2) is to push all ambient git access to ONE emitter step at the edge of the build graph whose OUTPUT is content-addressed and declared, and then make every downstream action a pure function of that frozen artifact. We adopt that pattern with a SPECIFIC boundary placement:

> **DECISION: The git-facts artifact is a COMMITTED, byte-parity-protected generated face (`cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app/git-facts.generated.json`), emitted by a NEW non-hermetic git-facts emitter step that runs OUTSIDE the buck2 action graph (a CI pre-step + a local regen hook), and re-validated by `registry-drift` byte-diff exactly like the other five faces. The producer and every gate `rust_test` consume it as a DECLARED buck2 input (a `srcs`/data dep). No buck2 action ever calls git.**

This is **Option C (committed git-facts face, regenerated by emitter + drift-checked)**, chosen over Option A (`.git` as a declared buck2 action input) and Option B (CI-only uploaded artifact, never committed). Justification in §1.4. It is the only option that (a) keeps the producer and all gates pure-hermetic and RBE-cacheable, (b) honors that git itself can't be hermetic by isolating it to one emitter, (c) makes the git-facts artifact tamper-evident under the EXISTING `registry-drift` mechanism (no new trust root), and (d) requires zero buck2-RBE access to the `.git` directory (which RBE workers do not and should not have).

**The design in one screen:**
1. **Hermetic producer** — delete the four `Command::new("git")` callsites; add a `git-facts.generated.json` declared input; the producer becomes a pure function `(git-facts face + oya-ci.toml + tracked file contents) -> 6 faces`. (§1)
2. **git-facts emitter** — a NEW tiny `rust_binary` `oya-cloud-ci-git-facts-emitter` that IS allowed to shell git (the ONE ambient boundary), run only by the CI pre-step + the local pre-commit/regen hook, never inside a cacheable action. Emits the tracked-paths list + path->last_touch_commit + commit-sha->author-ts + HEAD-ts as canonical JSON. (§1.5)
3. **Buck2-native gates** — replace every `Command::new(env!("CARGO"))` with consumption of the buck2-built producer's committed faces as declared `rust_test` inputs (the gate self-tests read the face files; they do NOT spawn the producer at all). Sandbox regeneration (registry-drift / firewall) invokes the buck2-built producer BINARY via a `$(exe ...)`-substituted env var, never cargo, never git. (§2)
4. **Cloud-native hyperscale CI** — buck2 RBE (NativeLink) + remote CAS read-through cache + the existing `infra/ci/buck2-affected-gate.sh` (uquery owner -> rdeps closure) + the `oya-ci-controller` K8s-Job control-plane (one-logic-multiple-runners). Staged migration cargo -> buck2 with byte-parity proof before the required-context switch. (§3)
5. **Refactor list + byte-parity staging + ADR + pre-mortem.** (§4-§7)

**Byte-parity invariant preserved end-to-end:** the hermetic producer MUST reproduce today's faces byte-for-byte. The mandate's cited counts (bnf=79, manifest=233, cargo-prefix=1, brand=4494, cross-artifact=168, automation=153, staleness=64) are functions of the git-derived `last_touch_commit`/`age_days` plus the file-content scans. Because git-facts is a frozen committed snapshot regenerated identically, the producer reproduces identical faces (proof obligation in §6, Stage P2).

## 1. HERMETIC PRODUCER (the crux)

### 1.1 The non-hermeticity, verified against real source
`cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app/src/main.rs` makes FOUR distinct ambient git calls:
- `git ls-files` -> `git_ls_files()` (main.rs:882-903) -> tracked-paths list (the registry row universe; also used by brand-residue, bnf, manifest-hygiene, cargo-prefix, enforcement scans).
- `git log --name-only --format=commit:%H` -> `git_last_touch()` (main.rs:907-930) -> path -> last_touch_commit map.
- `git log --format=%H %ct` -> `git_commit_timestamps()` (main.rs:605-627) -> commit-sha -> author-timestamp map (staleness aging).
- `git log -1 --format=%ct` -> `git_head_secs()` (main.rs:585-602) -> HEAD commit time (the deterministic "now").

The producer shells out via `std::process::Command` only — NO `gix`/`git2`/`libgit2` crate dependency (verified: zero matches). So the ambient surface is exactly these four subprocess invocations against an ambient `.git`. Everything else the producer reads is already a declared file: `oya-ci.toml` (`load_config`, main.rs:196-206), ADR corpus, masterplan/roadmap, `catalog.json`/`contracts.json`, `Cargo.toml` manifests, and the tracked file CONTENTS (read via `read_text` over `repo_root.join(path)`).

Note the subtlety: even the non-git reads are technically ambient (they read the working tree, not a buck2-declared input). Under the strict directive these MUST also become declared. §1.3 addresses this — the git-facts boundary is the hard part; the working-tree file reads are a second (mechanical) declared-input conversion.

### 1.2 The git-facts artifact schema (the declared, content-addressed input)
A single canonical-JSON face that snapshots ALL four git outputs. Proposed shape (canonical JSON, BTreeMap-sorted, exactly matching the producer's existing `to_canonical_json`):

```json
{
  "schema": "oya-ci/git-facts/v1",
  "head_commit": "18121e6ad231...",
  "head_time_secs": 1749384000,
  "tracked_paths": ["AGENTS.md", "cloud/cloud-ci/gates/...", "..."],
  "last_touch_commit": { "<path>": "<sha>", "...": "..." },
  "commit_author_ts_secs": { "<sha>": 1749300000, "...": 0 }
}
```

This is the EXACT set of facts the four git calls produce. The producer's existing pure helpers (`collect_repo_inputs`, `build_staleness_input`, `resolve_*`) consume these maps unchanged — only the SOURCE of the maps changes from `Command::new("git")` to `serde_json::from_str(&read_declared(git_facts_path))`.

### 1.3 The refactored producer (pure function)
- DELETE `git_ls_files`, `git_last_touch`, `git_commit_timestamps`, `git_head_secs` (main.rs:585-627, 882-930) and the `CliError::Git` variant.
- ADD `--git-facts <path>` CLI arg (REQUIRED in hermetic mode; defaults to `<repo-root>/cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app/git-facts.generated.json`).
- `collect_repo_inputs` takes the parsed git-facts struct: `tracked_paths` and `last_touch` come straight from it; `build_staleness_input` reads `head_time_secs` + `commit_author_ts_secs` from it instead of calling git.
- The working-tree file reads (ADR bodies, manifests, masterplan, the brand-residue corpus scan over `tracked_paths`) are declared by listing them in the buck2 target's `srcs`/data — see §1.6. The producer code is unchanged for these (it still `read_text`s `repo_root.join(path)`); hermeticity is enforced by buck2 sandboxing the declared input tree, not by changing the read calls. This is the standard Buck2 pattern: the action's inputs are declared in BUCK; the binary reads relative paths inside the sandbox.

Result: the producer binary is a pure function of `{git-facts.generated.json, oya-ci.toml, declared tracked file tree}`. No subprocess. No ambient git. Fully RBE-able (it would run on a remote worker that has only the declared inputs).

### 1.4 The boundary decision — options analysis (justification for Option C)

| Option | Where git runs | Producer/gates hermetic? | RBE-able? | Tamper-evident? | New trust root? | Verdict |
|---|---|---|---|---|---|---|
| **A — `.git` as declared buck2 action input** (a `genrule`/custom rule globs `.git/**` as `srcs`, runs git inside the action) | Inside a buck2 action | NO — `.git` is enormous (packs change every commit), non-deterministic across clones (pack ordering, reflogs, gc state), and RBE workers must NOT receive `.git`. The action input-hash changes on every unrelated commit -> cache always cold. | NO (poisons cache; `.git` not shippable to RE) | weak | yes (the rule) | REJECTED |
| **B — CI-only uploaded artifact** (CI pre-step emits git-facts, uploads via `actions/upload-artifact`, downstream jobs download; never committed) | CI pre-step | Producer yes IF the artifact is staged as a declared input at action time; but local `buck2 build`/`buck2 test` (dev machine, no CI artifact) has NO git-facts -> local build is non-reproducible / broken. Violates "everything just works" (ADR-0515 D3). | partial | NO (nothing on disk to diff) | yes | REJECTED |
| **C — committed git-facts face, emitted by an out-of-graph emitter, drift-checked** (chosen) | A non-hermetic emitter step (CI pre-step + local regen hook), OUTSIDE the action graph | YES — producer + all gates read a committed file as a declared input; identical on CI and local. | YES — the committed face is a normal content-addressed source input; its hash only changes when git history changes, which is exactly when the faces should change. | YES — reuses the EXISTING `registry-drift` byte-diff (the emitter re-runs in CI and the face must match committed). | NO new trust root — folds into registry-drift. | **CHOSEN** |

**Why Option C wins under the directive:** It is precisely the Google/Meta pattern — "git is at the edge; the build graph consumes a frozen, content-addressed snapshot." The emitter is the ONE place git is ambient, and its output is declared + drift-protected. Critically, it reuses the existing tamper-evidence mechanism (`registry-drift`): if anyone hand-edits git-facts or it goes stale vs the real history, the CI emitter regenerates it and the byte-diff RED-fails — identical to how the five faces are already protected. No new trust root, no `local_only`, no cargo fallback, no `.git` shipped to RBE.

**The emitter is NOT a buck2 action.** It is a `rust_binary` that buck2 BUILDS (so it is itself a hermetic, cacheable build artifact), but it is RUN by the CI pre-step and the local regen hook — exactly as `cargo run -p producer` is run today in the `producer-regen` CI job, except it is the only thing allowed to touch git. The buck2 build graph never depends on running it; it depends only on its committed OUTPUT.

### 1.5 The git-facts emitter (`oya-cloud-ci-git-facts-emitter`)
A new ~120-line crate `cloud/cloud-ci/gates/oya-cloud-ci-git-facts-emitter` exposing a `rust_binary`:
- Contains the four git subprocess calls VERBATIM moved out of the producer (so the logic that built `tracked_paths`/`last_touch`/`commit_ts`/`head_secs` is preserved bit-for-bit — this is what guarantees byte-parity of the downstream faces).
- Writes `git-facts.generated.json` via the same `to_canonical_json` canonicalizer.
- Is the single justified, narrowly-scoped exception to "no ambient git in an action" (ADR-0515 D3 permits a documented narrow exception). It runs OUTSIDE the action graph, so it does not violate action hermeticity.
- Run by: (1) the CI `git-facts-regen` pre-step (replaces the git-dependent part of `producer-regen`); (2) a local `git` pre-commit hook / `just regen-faces` developer command (so a local clone "just works" without CI). Both produce the identical committed face.

### 1.6 Declaring the working-tree reads (the second hermeticity surface)
The producer reads ~4 corpus families ambiently today. To make the producer action hermetic these become declared inputs in its BUCK target:
- `git-facts.generated.json` (the new face) — declared input.
- `oya-ci.toml` — declared input.
- The ADR corpus (`docs/decisions/ADR-*.md`), masterplan/roadmap/catalog/contracts JSON, and ALL tracked `Cargo.toml` + the brand-residue tracked corpus — declared as a `srcs`/data glob or a generated filegroup keyed off `tracked_paths`.

Trade-off acknowledged: the brand-residue census scans the ENTIRE tracked corpus (4494 residue keys across many files), so the producer's declared input set is effectively "the whole tracked tree." That is acceptable and correct — the producer's output legitimately depends on the whole tree, so the input-hash SHOULD change when any scanned file changes. This is "precise, not coarse" at the right granularity (the producer is a whole-tree analyzer by design; gates that consume only one face get a precise, narrow input — see §2).

## 2. BUCK2-NATIVE GATES (corpus born-blocking tests)

### 2.1 The two coupled defects, verified
- (a) `env!("CARGO")` is a COMPILE-TIME macro that only cargo populates. Confirmed at 9 callsites (one per gate self-test): `bnf_layer_suffix.rs:30`, `manifest_hygiene.rs:29`, `cargo_prefix.rs:31`, `total_accounting.rs:202`, `firewall.rs:48`, `registry_drift.rs:57`, `staleness_reaper.rs:185`, `cross_artifact_agreement.rs:176`, `automation_ratchet.rs:190`. Under `buck2 build`/`buck2 test`, `CARGO` is unset at compile time -> `env!` is a hard COMPILE error. So these `-gate`/`-corpus` `rust_test` targets cannot even build under buck2 today.
- (b) The tests then `cargo run -p oya-cloud-ci-accounting-registry-app --stdout --face X` AT RUNTIME, which re-shells git and re-invokes cargo — doubly non-hermetic. The tests also walk up the filesystem to find `repo_root()` via `specs/root-hub-pointers.json` (e.g. `bnf_layer_suffix.rs:16-27`), an ambient working-tree assumption.

The BUCK targets themselves are already clean: the `-gate` test (e.g. `oya-cloud-ci-bnf-layer-suffix-app-gate`, BUCK:32-43) has NO `local_only` and deps only on libs + the producer lib + serde_json. The toolchain wires `noop_test_toolchain` (`toolchains//:test`) AND `remote_test_execution_toolchain` (`toolchains//:remote_test_execution`, toolchains/BUCK:63-71) — so `buck2 test` can run rust_test locally now and remotely when RBE lands. The ONLY blockers are the test SOURCE (`env!`+`cargo run`+repo_root walk).

### 2.2 Redesign — gates consume the producer's committed faces as declared inputs
Two gate-test archetypes, both hermetic:

**Archetype 1 — pure face-reader gates (bnf, manifest-hygiene, cargo-prefix, total-accounting, cross-artifact, automation-ratchet, staleness):** The self-test asserts the gate goes RED on today's corpus. Today it does this by running the producer to get the face. Redesign: declare the COMMITTED face as a `rust_test` input and read it directly — DO NOT spawn the producer at all. The committed face IS the producer's hermetic output, and `registry-drift` already guarantees committed == regenerated, so reading the committed face is equivalent to running the producer but fully hermetic.
- BUCK: add the committed face to the test target's declared inputs. Two mechanisms:
  - (preferred) `env = {"OYA_CI_FACE_BNF": "$(location //cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app:bnf-layer-suffix-face)"}` where the face is exposed via an `export_file` target, so the test reads an absolute sandbox path from an env var (resolved at build time by buck2, NOT `env!` at compile time). Use `std::env::var` (RUNTIME) not `env!` (compile-time).
  - or list the face under the test's `srcs` glob and read it by relative path inside the sandbox.
- SOURCE: replace `run_producer_face(root, "bnf-layer-suffix")` with `read_face_from_env("OYA_CI_FACE_BNF")`; delete the `repo_root()` walk and the `Command::new(env!("CARGO"))` block. `evaluate`/`evaluate_keyed` are unchanged (already pure).

**Archetype 2 — regeneration/drift gates (registry-drift, firewall):** These MUST re-run the producer in a sandbox and byte-diff committed vs regenerated (that is their entire purpose — tamper-evidence). Redesign: invoke the buck2-BUILT producer BINARY, not cargo, and feed it the declared git-facts + tree inputs.
- BUCK: add `env = {"OYA_CI_PRODUCER": "$(exe //cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app:oya-cloud-ci-accounting-registry-app-bin)", "OYA_CI_GIT_FACTS": "$(location :git-facts-face)"}` plus the committed faces as declared inputs. `$(exe ...)` makes buck2 build the producer binary and pass its sandbox path; the test runs a hermetic, pre-built binary (no cargo, no compile-time env).
- SOURCE: replace `Command::new(env!("CARGO")).arg("run")...` with `Command::new(std::env::var("OYA_CI_PRODUCER")?).args(["--repo-root", sandbox_root, "--git-facts", git_facts_path, "--stdout", "--face", face])`. The producer (now hermetic) reads git-facts + the declared tree from the sandbox; no git, no cargo.
- The `repo_root()` walk is replaced by the buck2-provided sandbox root (an env var or `$(location)` of the declared input tree root).

### 2.3 Net effect
Every gate `rust_test` becomes a pure function of declared, content-addressed inputs: `{committed face(s)} -> RED/GREEN`, or `{producer exe + git-facts + declared tree + committed face} -> byte-diff`. All are `buck2 test`-runnable, RBE-able, and remote-cacheable (a gate test is a cache HIT until its declared face input changes). No `env!("CARGO")`, no `cargo run`, no live git, no `local_only`, no `repo_root` working-tree walk.

## 3. CLOUD-NATIVE HYPERSCALE CI (the buck2 execution model)

### 3.1 RBE + remote CAS (the warm-cache/delta-cold pattern, ADR-0515 D4)
- **Remote execution:** the `remote_test_execution_toolchain` is ALREADY wired (`toolchains/BUCK:68-71`) and the `[build] execution_platforms = prelude//platforms:default` is set (`.buckconfig:27-28`). The missing piece is a `[buck2_re_client]`/RE-API endpoint pointing at a backend. Per ADR-0515 D4 the candidates are NativeLink / BuildBuddy / EngFlow / BuildBarn. Recommendation: **NativeLink** (Rust-native, self-hostable in the cloud-native k8s substrate, aligns with the all-Rust doctrine and the owned-runner destination D5). Add a `.buckconfig` `[buck2_re_client]` section + an execution platform that routes actions to RE.
- **CAS read-through cache:** the RE backend's content-addressed store doubles as the shared action cache. An unchanged action's input-hash is a HIT on ANY runner (ephemeral GitHub runner, owned oya-ci pod, dev laptop). The 12MB `accounting-registry.generated.json` and 3.8MB `gate-baseline.generated.json` are large but content-addressed — fetched once, cached by hash, never recomputed when inputs are unchanged.
- **Buck2 binary + buck-out warm-start:** `actions/cache` keyed on the buck2 version + toolchain hash + `.buckconfig` hash so ephemeral runners do not cold-bootstrap (ADR-0515 D4).

### 3.2 Affected-set gate (assessment of `infra/ci/buck2-affected-gate.sh`)
The script is SOUND and already implements the hyperscale affected-targets pattern correctly:
- `git diff --name-only merge-base..HEAD` -> changed files; classifies Rust/buck-graph files (`*.rs`, `Cargo.toml/lock`, `.buckconfig`, `BUCK`, `toolchains/`, `third-party/`).
- `buck2 uquery owner('<file>')` per changed file -> owning targets; **FAILS CLOSED** on a uquery error (the documented false-pass-bug fix — a non-zero exit is a graph failure, not "no owner"; lines 60-75 of the script).
- BUCK-file changes expand to the whole package pattern (a BUCK edit can alter any target in the package) — correct.
- `buck2 uquery 'rdeps(//..., %Ss)' @argfile` -> reverse-dep closure (handles the 1689-owner third-party/BUCK overflow case via `@argfile` + `%Ss` placeholder — a real, already-fixed scaling bug).
- `buck2 build @affected` then `buck2 test @affected`.

Two notes/tensions:
- **It is a `.sh` script**, which ADR-0515 D3 forbids "bar a documented, justified, narrowly-scoped exception." This affected-gate is exactly such an exception (it is the buck2-driver glue, not gate logic), but it SHOULD be documented as the carve-out, OR (cleaner, aligned with the owned-runner destination) reimplemented as a Rust `rust_binary` `oya-ci-affected` that shells `buck2 uquery`/`build`/`test` — moving the glue into the all-Rust pipeline. Recommendation: keep the `.sh` as the GitHub-Actions-interim driver, plan the Rust port as a D5 owned-runner item. (REFACTOR item, §5.)
- It still uses ambient `git diff`/`merge-base` — but this is the affected-SELECTION layer (a CI orchestration concern), NOT an action input. Affected-selection is legitimately allowed to read git at the CI edge (same boundary class as the git-facts emitter); the actions it then runs are hermetic. This is consistent with the boundary doctrine.

### 3.3 Control-plane / one-logic-multiple-runners (D-CICD-AUTHORITY)
The `oya/ci-controller` crate family IS the control-plane abstraction:
- `oya-ci-controller-kernel` — pure domain: `GateRun`, `GateOutcome`, `CommitState` (forge-neutral), `map_job_to_status` (TOTAL pure observation->ReconcileDecision), `CommitStatusPoster` + `JobSpawner` trait seams. No I/O, no kube, no tokio.
- `oya-ci-controller-k8s-adapter` — spawns gates as K8s Jobs.
- `oya-ci-controller-github-adapter` / `-forgejo-adapter` — posts commit status (the forge-neutral seam).
- `oya-ci-controller-app` — the binary.

This is the "same canonical pipeline across time" (ADR-0515 D2): the gate LOGIC is the buck2 `rust_test` targets; the RUNNER is GitHub Actions now, the K8s-Job controller later. The controller spawns the SAME `buck2 test @affected` invocation in a K8s Job that GitHub Actions runs in a matrix leg. No logic fork.

### 3.4 cargo -> buck2 required-context migration (without breaking live green)
The live `.github/workflows/oya-ci-required.yml` runs `cargo test`/`cargo run` across `producer-regen`, the 7-gate matrix, `gate-registry-drift`, `gate-cloud-ci-firewall`, fanning into the single `oya-ci-required` required context. The migration MUST not break that context. Staged plan in §6. The core move: run buck2 ALONGSIDE cargo in non-required lanes, prove byte-parity of faces + verdict-parity of gates, then swap the `oya-ci-required` fan-in's `needs:` from the cargo legs to the buck2 legs in ONE founder-paired door (the required-context-content swap), keeping the context NAME `oya-ci-required` constant (so branch protection never sees a context rename — the same lesson as ADR-0515's name-stability rule).

### 3.5 Merge queue
GitHub-native `merge_group` is already a trigger in the workflow (`on: merge_group`). The buck2-affected gate amortizes whole-tree cost across the batch (ADR-0515 D4 merge-queue batching). Owned Tide-equivalent is a D5 destination item, out of scope here.

## 5. STAGING — byte-parity-preserving, never breaks live green

Reconciliation with the held **L1-office migration** (HEAD is "L1 office migration: faces-only settle") and the **§WS-E/F product plan**: this design SUPERSEDES/REFINES the rejected §WS-F "local_only" idea. The directive explicitly rejected `local_only`+cargo-fallback as non-hermetic; this doc replaces it with the git-facts-boundary + `$(exe)`/`$(location)` declared-input design (no `local_only` anywhere — verified `local_only` appears in zero BUCK files today). The L1-office migration is a faces-content settle (last_touch_commit convergence) and is ORTHOGONAL to the buck2-hermetic refactor: it changes face DATA, this changes the face PRODUCTION mechanism. Sequence the hermetic refactor to land AFTER L1-office faces settle (so byte-parity is measured against the settled faces, not a moving target).

## 7. PRE-MORTEM (>=3, with mitigations)

**PM1 — git-facts non-determinism breaks byte-parity.** RISK: `git log --name-only` ordering, `git ls-files` locale/quoting (`core.quotePath`), or author-vs-commit timestamp ambiguity makes the emitter produce a different git-facts.generated.json on CI vs local, so the regenerated faces differ byte-wise -> registry-drift RED-on-arrival. EVIDENCE this is real: the producer already sorts+dedups `git ls-files` (main.rs:900-901) and uses author-ts `%ct`, and the CI workflow ALREADY documents that a shallow checkout collapses ages to 0 (a known determinism trap). MITIGATION: pin git invocation flags in the emitter (`-c core.quotePath=false`, explicit `--format`); require `fetch-depth: 0` (already enforced in CI); the emitter canonicalizes via the existing `to_canonical_json`; and registry-drift is the BACKSTOP — it will catch any drift before merge rather than silently passing. DEEP-RESEARCH ITEM: confirm `git ls-files`/`git log` output is byte-stable across git versions on the GitHub ubuntu-latest runner vs the owned k8s pod image (pin a git version in both).

**PM2 — RBE / buck2-on-GitHub-Actions infeasible or too slow.** RISK: NativeLink/RE-API needs a reachable endpoint with auth; GitHub-hosted runners have no persistent RE backend; standing one up + securing it (cross-tenant cache poisoning is an explicit ADR-0515 RED fixture `tc-0.0.3 cross-tenant-shared-cache`) is heavy. The 12MB+3.8MB faces stress CAS transfer. MITIGATION: RBE is staged LAST (Stage P3) and is NOT required for hermeticity — `buck2 test` runs LOCALLY-on-the-runner hermetically via `noop_test_toolchain` (already wired) with NO RE backend; RBE is a THROUGHPUT optimization (D4), not a correctness gate. So the hermetic+buck2 mandate is met at Stage DOOR even if RBE slips. Cache scoping per-tenant (the cross-tenant fixture) is a NativeLink config concern handled at P3. DEEP-RESEARCH ITEM: NativeLink self-host on the cloud-native k8s substrate + per-tenant CAS namespace isolation + GitHub-runner->RE auth.

**PM3 — the cargo->buck2 required-context switch self-DoSes.** RISK: at Stage DOOR, if the buck2 legs are flakier/slower than cargo (cold buck-out, toolchain bootstrap, RE timeout), the required `oya-ci-required` context goes RED and blocks ALL merges (a self-inflicted denial-of-service on the trunk). EVIDENCE: ADR-0515 already records the `oya-pr-review` HTTP-501 multi-producer-deadlock lesson — a bad required-context change DoS'd merges before. MITIGATION: the byte/verdict-parity gate (Stage P2) MUST be green for a soak period BEFORE the swap; the swap keeps the cargo lanes as non-required shadow for one soak window (instant rollback = revert the `needs:` one-liner, no admin door since the context name is unchanged); buck2 binary + buck-out are `actions/cache`-warmed (D4) before the swap to avoid cold-start timeouts. The swap is a workflow-content change (revertible in one commit), NOT a branch-protection admin door — so rollback is fast and does not need the founder-paired GitHub-admin doors.

**PM4 (bonus) — declared-input set for the producer is effectively the whole tree, so the producer action is ALWAYS cold.** RISK: because brand-residue scans the whole tracked corpus, ANY file change re-hashes the producer's inputs -> the producer never cache-hits -> the 12MB face is recomputed on every PR. MITIGATION: this is CORRECT behavior (the producer output legitimately depends on the whole tree), and the producer is FAST (single-pass scans); the EXPENSIVE consumers (the 9 gate tests) get PRECISE inputs (one face each) so they cache-hit when their specific face is unchanged. The affected-gate only rebuilds the producer when a scanned file in the closure changed. Acceptable; do NOT try to shard the producer (premature). NOTE this is the tradeoff tension: whole-tree-analyzer hermeticity vs incrementality — resolved by keeping the analyzer coarse but its consumers precise.
