### ADR-0512 — Canonical monorepo pattern (vertical-slice nesting, one workspace, bounded-context crates, dependency-rule modules, Buck2 graph)

- **decision_atom:** The repo is ONE root Cargo workspace (one `Cargo.lock`, one-version, no nested `[workspace]` tables) with service code at `{oya,cloud}/<service>/crates/oya-<...>/` (oya = product/domain, cloud = platform/tenant) and shared libs at `libs/<lib>/`; the canonical crate boundary is the bounded context (not the layer, not the whole service), clean-architecture layers are enforced as `mod`s via the inward-only dependency rule, and Buck2's per-crate rustc-direct graph (not Cargo workspace fragmentation) is the build/parallelism/containment mechanism.
- **domain:** ci-cd-build (primary); api-contracts secondary only via the "co-locate contracts" clause — best read as single-domain ci-cd-build / repo-structure.
- **current_status:** Accepted (founder-locked 2026-05-29; amended 2026-06-02 for the `microservices/` → `{oya,cloud}/` root split).
- **disposition:** KEEP. Current, founder-locked, internally consistent, and it cleanly resolves the 0357-vs-0509-vs-0131 fork. The 2026-06-02 amendment is folded in-line (good ADR hygiene), so no separate AMEND is owed.
- **proposed_resolution:** NA (status == Accepted).
- **governing:** This ADR is itself governing — it **supersedes ADR-0357** (vertical-slice nesting, was Proposed) and **ADR-0509** (single-crate-per-service) and **amends ADR-0131** (per-µsvc flat layout). Verified on disk: ADR-0357 still reads `status: Proposed, supersedes:[]` and ADR-0509 reads `status: Accepted, superseded_by:[]` — both carry **stale front-matter** (neither records the 0512 supersession edge). Flag for the drift-prevention gate; trust 0512's claim.
- **truth_flag:** TRUE.
- **in_masterplan:** PARTIAL. The keystone map's CANONICAL POSTURE table (§3 CI/CD, §1.3 CI churn) names Buck2 + Argo + ArgoCD but does **not** carry the 0512 layout law (`{oya,cloud}/<service>/crates/`, crate=bounded-context, no flat `crates/`, no nested workspaces). This is a load-bearing structural decision that a generated masterplan must surface — currently under-represented.
- **tensions:** (1) Supersedes 0357 + 0509 whose front-matter is stale (drift, not contradiction). (2) The 2026-06-02 amendment **retires the `microservices/<ms>/` root** that ADR-0131 (and many sibling ADRs, incl. ADR-0514's own `related: ADR-0131`) still reference as canonical — a corpus-wide path-vocabulary churn (`microservices/` is now "legacy/removal-candidate after P0.1/P0.6"). Any ADR or spec still rooting paths at `microservices/` is now stale. (3) "`foundry` name remains eradicated" reaffirms ADR-0335/0347 retired-vocab — consistent, no tension.
- **hyperscaler_challenge:** ALIGNED. Google (Piper/Blaze→Bazel one-version monorepo), Meta (Buck2, the literal tool cited), and a one-version-policy single workspace are textbook hyperscaler monorepo discipline; crate=bounded-context as the Buck2 parallelism dial is exactly how Buck2/Bazel targets are meant to be sized. No amend/archive implication from the hyperscaler lens — this is the move they would make.
- **ai_slop:** None. The ADR is unusually self-aware (names the concrete trigger: an accidental 37-PR concurrent merge of the 0357 migration that clobbered the root manifest and spawned 28 nested workspaces) and ends with a hard process rule. Not slop.
- **refinement:** Propagate the `{oya,cloud}/`-root path-vocabulary change into a retired-vocab entry (`microservices/<ms>/` root → `{oya,cloud}/<service>/crates/`, governing ADR-0512 2026-06-02 amendment) so downstream auditors treat residual `microservices/`-rooted paths as stale, mirroring the foundry/tier retired-vocab treatment.
- **consensus_needed:** None — founder-locked. (Latent founder question only if masterplan is GENERATED: does the generator key crate ownership off the `{oya,cloud}/<service>/` path, and how does it treat the still-present legacy `microservices/` tree until P0.6 removal?)

### ADR-0513 — oya-ci: bespoke-Rust Prow (Forgejo-native CI/CD platform)

- **decision_atom:** Replace the Jenkins+Groovy+cpsScm+ephemeral-agent CI orchestration with **oya-ci**, a bespoke-Rust, Forgejo-native, kube-rs-native reimplementation of Prow's full component shape (hook/plank→controller / crier→reporter / tide→merge-queue / deck→Leptos UI / sinker / plugins) on the Talos substrate, retaining the proven `buck2-affected-gate.sh` logic and the `ci-webhook-gateway`, with trunk-sourced (dev-script-against-PR-ref-as-data) gate security, phased so the Jenkins gate path is deleted at the Phase-1 cutover.
- **domain:** ci-cd-build (primary); forge-vcs secondary (Forgejo-native gateway + commit-status + Tide merge-queue sit on the ADR-0363 forge substrate).
- **current_status:** Accepted (founder-locked 2026-05-30; amended 2026-06-02 making Tide/merge-queue owned-here-now, not a deferred adoption).
- **disposition:** KEEP. Founder-locked, coherent, evidence-backed (five named production failure modes), correctly scopes itself as the *phased* replacement of ADR-0380's Jenkins path. One AMEND-flavored caveat: the formal supersession of ADR-0380 is deferred to the Phase-1 cutover, so today both 0380 (Jenkins gate) and 0513 (oya-ci) are simultaneously "Accepted" — a deliberate bridge, not a contradiction, but the supersession edge must actually be written when Phase-1 lands.
- **proposed_resolution:** NA (status == Accepted).
- **governing:** Forward-governs ADR-0380 (Jenkins gate path) — supersession **pending Phase-1 cutover**, explicitly time-boxed in-body. Folds in ADR-0111 (merge-queue → `oya-ci-tide`) and ADR-0116 (reviewer-APPROVE → plugins); retains ADR-0374 (webhook gateway) and ADR-0392 (Buck2); sits on ADR-0363 (Forgejo). No archive owed yet.
- **truth_flag:** TRUE.
- **in_masterplan:** PARTIAL. Keystone §1.3 / §3-CI/CD net-truth records "bespoke-Rust **oya-ci** (Prow-shaped) is the target platform … Forgejo Commit Status as the gate sink," so the destination is represented — but the **Argo-Workflows-as-CI-orchestration claim (ADR-0511) and oya-ci-controller-as-job-executor (ADR-0513) are not reconciled** in the posture table; the masterplan must pick one CI-orchestration spine (see tensions).
- **tensions:** **MAJOR — CI-orchestration destination conflict.** ADR-0511 (`Proposed`) declares **Argo Workflows** the k8s-native CI-orchestration destination (Jenkins transitory); ADR-0513 (`Accepted`) declares **oya-ci-controller** (bespoke kube-rs, "plank → K8s Job per PR") the job controller/executor — which *is* the CI-orchestration role. The keystone §1.3 reconciliation ("Buck2 + Argo Workflows + ArgoCD, oya as governance overlay") reads as a post-hoc stitch; 0513/0514 never mention Argo Workflows and instead build a from-scratch controller doing what Argo Workflows does. An Accepted bespoke-Prow ADR plausibly **obsoletes the Proposed Argo-Workflows ADR** — this needs founder resolution, not silent coexistence. Secondary: 0513 owns Tide(0111)+reviewer(0116) inside one platform — consistent, no conflict.
- **hyperscaler_challenge:** QUESTIONABLE (the build, not the goal). Adopting **Prow's shape** is exactly what a hyperscaler does (Prow IS Kubernetes' own CI). But Google/AWS/Azure would near-always **run upstream Prow / Tekton / Argo Workflows** rather than reimplement the full hook/plank/crier/tide/deck/plugins set in bespoke Rust — the "adopt the shape, not the code" + full-component-set scope is a classic build-vs-buy over-reach that hyperscalers reserve for proven-bottleneck components, not the whole platform on day 0. Implication: not archive (the *reliability* problem is real and the Jenkins/Groovy failure modes justify *replacing the orchestration layer*), but AMEND-pressure to (a) justify full-set bespoke vs adopting Argo Workflows/Tekton for plank+sinker and owning only the Forgejo-native + Tide differentiators, and (b) reconcile with ADR-0511. This is the sharpest "own-everything breadth" instance (keystone §5 fault-line 5) on the CI axis.
- **ai_slop:** None. Failure modes are concrete and production-observed; the Prow→oya-ci parity table is precise. Not slop.
- **refinement:** When Phase-1 lands, write the explicit `superseded_by`/supersession edge onto ADR-0380 (the ADR already promises it but front-matter currently doesn't carry it — same stale-edge risk as 0512↔0357/0509).
- **consensus_needed:** **CONTESTED — founder question:** "Is the canonical k8s-native CI-orchestration spine (a) upstream **Argo Workflows** per Proposed ADR-0511 with oya only as governance/gate overlay, or (b) the **bespoke oya-ci-controller** (full Prow shape in Rust) per Accepted ADR-0513/0514 — and if (b), is ADR-0511 thereby archived?"

### ADR-0514 — Build/CI/CD Pipeline Target Architecture + Hyperscaler Remediation

- **decision_atom:** Narrow ADR-0513 to its Phase-1 critical path by specifying the prerequisite reliability fixes — a hermetic clang+lld+sysroot toolchain as default (dev≡CI at the link layer), trunk-sourced gate (deployed controller clones trusted `dev` + PR-ref as data), idempotent durable `reindeer buckify` with a post-buckify DEP patch step, rdeps depth-cap + presubmit/postsubmit two-tier + NativeLink CAS, structured failure summaries from buck2 event-log JSON, and a controller cutover deleting the Jenkins gate path — to reach a closed-loop conflict-free Tide merge that lets fan-out agents drive oyatie autonomously.
- **domain:** ci-cd-build (primary); security-supplychain secondary (the trunk-sourcing / PR-sourced-gate `pull_request_target`-class vulnerability fix, D2/#95, is a genuine supply-chain/gate-isolation decision).
- **current_status:** Proposed (2026-05-31).
- **disposition:** AMEND (then RATIFY). Sound, evidence-dense (every fault file:line-cited to `build-ci-pipeline-review.md`), and it is the executable spine of 0513 Phase-1 — but it has two unmet pre-acceptance conditions written into its own body: (a) it depends on a not-yet-authored linker ADR ("ADR-0488"/mold-via-clang exists only as a research note + `.cargo/config.toml` comment, body says "promote to a real ADR before this ADR is Accepted"), and (b) its `M-TOOLCHAIN` milestone vocabulary should be checked against the retired M0–M3/Milestone vocab (M-TOOLCHAIN is a function-named wave-style id, so likely OK, but confirm it is not a retired-milestone leak). Amend to resolve the ADR-0488 dependency, then ratify.
- **proposed_resolution:** **RATIFY** — the decision is the correct narrowing of an Accepted parent (0513) and fixes a real security hole + the dominant "green-on-dev/red-on-CI" failure loop; but ratification is **conditional** on first authoring the referenced linker/toolchain ADR ("ADR-0488") that its own body makes a precondition. Do not DROP — the work is live, in-progress (#96 repro), and load-bearing.
- **governing:** None archived by this ADR (`supersedes: []`). It is *governed by / depends on* ADR-0513 (parent), ADR-0392/0408 (Buck2), and the pending linker ADR. Inherits 0513's forward-supersession of ADR-0380.
- **truth_flag:** PARTIAL. TRUE as a remediation plan; PARTIAL because several rows are explicitly **claimed-resolved-elsewhere-evidence-pending** (#93/#91/#94/PR#25 — the ADR honestly refuses to call them done without commit SHA + gate receipt) and the linker ADR it depends on is unwritten. The ADR is correctly self-flagged, not wrong.
- **in_masterplan:** PARTIAL. The Buck2/CAS/affected-gate destination is in the keystone posture; the specific six-deliverable remediation contract (hermetic toolchain default, trunk-sourcing, durable buckify, rdeps depth-cap, structured failure summary) and the **closed-loop dogfood / fan-out-agents-drive-oyatie** end-goal are not represented and are exactly the kind of "true + relevant decision" a generated masterplan should backfill.
- **tensions:** (1) Inherits the **ADR-0511 Argo-Workflows-vs-oya-ci-controller** conflict (D4 cuts over to "deployed oya-ci-controller," never to Argo Workflows). (2) Depends on an **unauthored ADR-0488** (linker/mold-via-clang) — a dangling reference that blocks clean acceptance; the body itself says so. (3) `related: ADR-0131` (per-µsvc flat layout) while sibling ADR-0512's 2026-06-02 amendment already **retired the `microservices/` root** 0131 assumes — 0514's path/layout assumptions should be re-pointed at `{oya,cloud}/<service>/crates/`. (4) Multiple historical-backlog rows (#93/#91/#94/PR#25) carry status labels the ADR refuses to trust without evidence — a deliberate anti-slop guard, but a masterplan must not promote those to `done`.
- **hyperscaler_challenge:** ALIGNED on the principles, QUESTIONABLE on bespoke scope (inherits 0513). The six founder principles (hermetic "just works," CAS/RE affected-gate, observability-by-default, automate-DRY, doubt-driven evidence-gates, conflict-free Tide merge) are verbatim hyperscaler CI doctrine (Google's hermetic Blaze + trunk-based + presubmit/postsubmit + merge-queue). The trunk-sourcing fix is the correct `pull_request` vs `pull_request_target` security model. The questionable part is again **building the controller bespoke** rather than on Argo Workflows/Tekton (D4/D5). Implication: AMEND to reconcile the orchestration substrate (0511) and to author the linker ADR; the *remediation deliverables themselves* are sound and would survive any substrate choice.
- **ai_slop:** None — arguably the strongest anti-slop ADR in the chunk: it explicitly separates "this ADR's claims" from "historical backlog labels (evidence pending)," demands commit SHA + gate receipt + ADR-0134 resolution before any authority surface calls a row complete, and self-flags its own unauthored dependency. Exemplary.
- **refinement:** Before Accepted: (a) author the linker/toolchain ADR the body requires ("ADR-0488" mold-via-clang), (b) repoint layout/path references from ADR-0131 `microservices/` to ADR-0512 `{oya,cloud}/<service>/crates/`, (c) reconcile the CI-orchestration substrate with ADR-0511.
