### 1.4 The registry-drift FAIL — diagnosed: benign self-referential commit-SHA off-by-one (NOT real debt)

Re-ran the producer per-face and byte-diffed each committed face vs regenerated:

```
DRIFT   registry            committed=12035280  regen=12035280 bytes   diff-lines=6 (3 records)
MATCH   ttl-policy
MATCH   decision-crosswalk
MATCH   enforcement-inventory
MATCH   baseline            ← the GO-LIVE ratchet face is BYTE-EQUAL (clean)
```

The 6 drift lines are **only commit provenance**, nothing structural:
```
source_inputs_digest: fnv1a64:435fde20d4f56d22  →  fnv1a64:cea14a7bcf6e47ea
last_touch_commit (record for accounting-registry.generated.json): c43d38b2…  →  7adae31fb…
last_touch_commit (record for gate-baseline.generated.json):       c43d38b2…  →  7adae31fb…
```
`last_touch_commit` comes from `git log --name-only` (producer `src/lib.rs:256`, `src/main.rs:544`). HEAD is `7adae31fb chore(firewall): regenerate accounting faces after wave-3 …`. The two drifting records are **the two generated faces describing themselves**. They were generated when HEAD was still the parent `c43d38b2`, then the act of committing them changed their own last-touch to `7adae31fb`. The `source_inputs_digest` folds that in. **This is the classic fixed-point: an artifact cannot embed its own future commit SHA.** One more `regenerate → commit` cycle on the now-committed HEAD converges it (the next run sees its own content unchanged, so the SHA stops moving).

**Idempotency is intact** — two consecutive `--stdout --face registry` runs on the same tree produced the identical digest `fnv1a64:cea14a7bcf6e47ea`. The producer is deterministic; the drift is provenance churn, not nondeterminism.

## Part 3 — PREREQUISITE / SEQUENCING: does go-live need BIG-2 vocab eradication FIRST?

**Short answer: the THREE DOORS do not strictly require it, but DOOR 1's SSOT scrub and the integrity of the accounting faces do. FLAG: founder must rule on sequencing before Door 3 / before the faces are frozen as canonical.**

### The tension (evidence)
ADR-0515's own go-live sequence puts vocab eradication in **step 5** ("Then fix the canon through it"), i.e. AFTER the three doors (firewall-first per D-SEQUENCE). BUT the firewall's enforcement mechanism is **registry-drift = committed==regenerated** + the **baseline ratchet**, which together make the current face contents *canonical and tamper-evident*. The faces index `git ls-files` paths, so forbidden vocab in path names / contents is baked into the protected substrate:

Forbidden-vocab footprint in the tracked corpus (excl. `target`, excl. generated faces):
```
foundry:  3456 files   (of which oya-foundry/oyatie-foundry = 620 forbidden; Palantir = 243 carve-out — needs disambiguation)
jenkins:  1232 files
forge:     239 files
oya-vcs:   113 files
forgejo:    15 files
```
And **inside the committed generated faces themselves**:
```
foundry: 1511 occ   jenkins: 172 occ   forge: 44 occ   forgejo: 24 occ   oya-vcs: 19 occ
```

### Why this matters
- **The firewall does NOT police vocab.** `brand-residue` is a SEPARATE `libs/oya-check-brand-residue` crate, NOT one of the 6 firewall gates and NOT wired into the aggregator. So going live does not *enforce* eradication — but it also does not *prevent* the forbidden vocab from being frozen into the accounting registry as the canonical committed==regenerated truth.
- **If you go live first and eradicate later:** every vocab rename touches paths → changes `git ls-files` → changes the registry face → registry-drift goes RED until you regenerate + re-commit. That is fine (it is the gate working), but it means the eradication campaign becomes a forced face-regen treadmill, and the baseline ratchet may baseline forbidden-vocab debt keys in the interim.
- **The honest reading:** ADR-0515 is internally consistent (firewall-first; vocab is step 5). The forbidden vocab does NOT block the three branch-protection doors. BUT Door 1 (SSOT re-author) MUST scrub the Jenkins/forge/ADR-0124/ADR-0361/shell-script residue from `dev.json` + `branch-protection.yaml` regardless — that subset of eradication is a Door-1 prerequisite.

### Recommendation (for founder ruling, not a decision)
- **Do NOT block go-live on the full big-2 eradication.** Per D-SEQUENCE the firewall must be real first.
- **DO require, before Door 1:** scrub the SSOT-local forbidden vocab (Jenkins/forge/ADR-0124/ADR-0361/`branch-protection-apply.sh`) in the two branch-protection files — this is in-scope for Door 1 anyway.
- **DO decide consciously** whether to accept forbidden vocab being baselined into the accounting faces during the half-hardened window, or to run the eradication as Phase-1 step 5 with a planned face-regen + a `brand-residue` gate added to the fan-in afterward (ADR-0515 step 5 already lists "eradicate forbidden vocab tree-wide via the brand-residue gate").
- **FLAG:** if the founder's intent is "the firewall must never lock in forbidden vocab," then eradication is a PREREQUISITE and the sequence inverts for the vocab subset — this contradicts ADR-0515's firewall-first ordering and needs an explicit founder ruling.
