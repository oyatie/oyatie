## Batch-level systemic findings (apply to many ADRs in range)

- **S-1 (CRITICAL) — `foundry` µservice is the owner/home of the canonical data substrates, but canon killed `foundry`.** ADR-0192 (Milvus) `ADR-0192:47` "Milvus runs as a disaggregated cluster owned by the **foundry** µservice"; helm path `ADR-0192:128` "`microservices/foundry/iac/helm/milvus/`"; SeaweedFS object backend "`microservices/foundry/`" throughout. Canon `canon:D-INTEL`/`D-FOUNDRY-CLARIFY` rule "foundry is a dead context… platform→intelligence, fitness→governance, vcs→retired" and `canon:WF2` flags the 831-file foundry rename. The vector store is NOT an AI-platform primitive that belongs in intelligence — it is a **data-tier substrate** (`canon:D4` own-the-data-tier). Ownership home is wrong by canon AND by layering. AMEND across 0192 (and the SeaweedFS/observability cross-refs).
- **S-2 (HIGH) — "Redis" appears as live substrate in 0191 + 0208, directly contradicting 0184's own Valkey ruling.** 0184 forbids Redis 7.4+ (`ADR-0184:101-105` "Use Redis 7.4+ for Tier 3 (ignore the license change) — REJECTED … RSALv2 + SSPLv1 are non-OSS"). Yet `ADR-0191:46` "Redis-backed per-IP counters", `ADR-0191:68` "per-tenant Redis cache", `ADR-0208:74` "backed by **Redis Cluster** / Valkey pub-sub". This is exactly the canon `canon:D12` vocabulary-drift / `canon:D-DOCTRINE` "drift = faulty enforcement" symptom. AMEND 0191/0208 → Valkey.
- **S-3 (HIGH) — Kafka surfaces as a live broker option, contradicting `canon:D-EVENT` (Kafka→Pulsar, one streaming substrate).** `ADR-0192:58` "Log broker (Pulsar 4.2 **or Kafka**)"; `ADR-0193:80` + `ADR-0195` default path "ClickHouse's `Kafka` engine consumes directly". The Kafka *wire protocol* via Pulsar's KoP proxy is legitimate (`ADR-0195:71`), but the prose repeatedly presents Kafka-the-broker as a co-equal option. Canon: "PULSAR is the canonical eventing/streaming bridge… One streaming substrate." AMEND to name Pulsar (Kafka = wire-compat only).
- **S-4 (HIGH) — Pervasive `microservices/<ms>/` flat-catalog layout contradicts `canon:D-PURESPLIT` (pure two-tree split `oya/` + `cloud/`, ERADICATE `microservices/`).** Every ADR in this batch writes paths under `microservices/…` (e.g. `ADR-0184:144`, `ADR-0196:68`, `ADR-0202:75`, `ADR-0209:126`). Canon `canon:D-PURESPLIT`: "exactly two service trees — `oya/` (products) + `cloud/` (platform) — ERADICATE everything else (services/, platforms/, **microservices/** …)." Also `canon:D-CONFORM` brand/structure sweep. This is a batch-wide path-vocabulary AMEND (additive rename, `canon:D13-AMENDED`).
- **S-5 (MED) — "32 µservices" magic number repeated as fixed fleet size.** `ADR-0184:` n/a, but `ADR-0186:28` "all 32 µservices", `ADR-0192:21` "all 32 µservices", `ADR-0210:23` "32 µservices". The fleet is ~90 services per `canon:D3` ("~90-service portfolio") and unbounded by `canon:D9` maximal-vertical-scope. A hardcoded "32" is a staleness/anti-pattern (scale ceiling baked into prose + cost models e.g. `ADR-0210:64`). AMEND to remove the fixed count.
- **S-6 (MED) — `in-house roadmap` Phase-2 "build our own X" sections are an own-vs-buy pattern that is mostly RIGHT-by-canon but under-disciplined.** Canon `canon:D-META` is exactly "own-the-endpoint / vendor-the-bridge / ratchet-when-proven; **build-first-cutover-later**; never retire a bridge before the owned replacement is built+proven." Most of these ADRs already encode value-anchored triggers (good pattern, KEEP). The gap: several ADRs declare KEEP-forever ("no Phase 2 planned") for substrates that `canon:D4`/`canon:D-META` say should be owned-endpoints eventually (data tier). Flagged per-ADR below.
