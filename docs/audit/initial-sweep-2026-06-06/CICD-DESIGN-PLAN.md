## RALPLAN-DR SUMMARY

### Principles (the design invariants — every stage is checked against these)

1. **No false-green, ever (the cardinal Torvalds sin).** A required check that is green while a real check failed, was omitted, or has no producer is the #1 defect. The required context must be green **IFF every constituent lane is green** — it must NEVER run its own narrower command set. Live today the required job re-runs a 7-target governance subset and omits authority-policy/coverage/affected (`github-lane-unlocker-ci-cd.yml:79-87`), and the live ruleset itself diverges from its committed SSOT on EVERY axis (the SSOT's "shadow compatibility only … must not be treated as merge authority" note lives verbatim in `github-mirror/dev:infra/branch-protection/dev.json:12` `_phase0_target_note` + `dev.json:36` `legacy_shadow_context`, naming `oya-ci-required` as the sole intended required context, yet live requires `github-lane-unlocker-required` — verified live `gh api`, see Decision Driver #1).
2. **Data-structures-first; the verdict is data, not control-flow.** The firewall already models the verdict as data: `compare()` loops the union of `(gate,code)` keys with no early exit (`cloud-ci-firewall/src/lib.rs:172-215`); `fails()` keys only on `mode=="baseline-block-on-new" && !regressions.is_empty()` (`lib.rs:147`); `is_green()` = no failing code AND no un-signed-off ratchet growth (`lib.rs:160-162`). Surface-all is then a property of the data structure (`evaluate_keyed → BTreeSet`, no early return), not of careful sequencing. We build on this; we do not reinvent it.
3. **Surface-all, not fail-fast — parallel at the top, collect-all at the bottom.** Fan out lanes with `fail-fast:false`; aggregate at the join into ONE `FirewallReport` → ONE Check-Run with per-finding annotations + one summary + a persisted advisory burn-down. One sweep fixes everything. (External basis: nextest `--failure-output=immediate-final` + `dorny/test-reporter` glob-aggregate + problem-matchers, paired with a full summary because inline annotations cap at 10/step·50/job·50/run — `deep-research-cicd.json` findings.)
4. **Drift impossible by enforcement AND automation (defense-in-depth).** Even if the generator never runs, an enforcement gate catches the drift (`D-DOCTRINE`, canon line 195). The protection config itself must be defended: a presubmit byte-diff of live `gh` protection vs committed `dev.json` is the single gate that would have caught all four live drifts (context swap, signatures off, admins off, review-count=1) — `pipeline-analysis` anti-pattern #3. (The drift gate's reference target is the **re-authored** SSOT, not the superseded ADR-0513 SSOT — see Doctrine Reconciliation consequence 3; it cannot go blocking until that re-author lands or it is RED-on-arrival forever.)
5. **Build-first, cutover-later; ONE canonical pipeline, runner migration over TIME.** Per `D-META`/`D-CICD-AUTHORITY` + the ONE CANONICAL CI amendment: there is ONE canonical pipeline (one shared Rust gate-logic + one pipeline definition + one aggregator). GitHub Actions is the live runner now; the owned `oya-ci` is the SAME pipeline's future runner (a runner *migration*, not a second parallel CI). The **gate LOGIC is the same Rust crate** throughout. Never retire a bridge (Jenkins) before its owned replacement is built and proven. Eradicate forbidden vocab (`forgejo`/`foundry`/`jenkins`/`oya-vcs`) only AFTER oya-ci is proven (`D-CLOUD-NATIVE`, canon line 233).

### Decision Drivers (top 3 — what actually forces the design)

1. **The live required check is a structural false-green AND the live ruleset diverges from its own SSOT on every axis.** This is both directives #1 and #3 violated at the one gate that blocks merges, plus a directive-#4 security hole. **VERIFIED live `gh api repos/jason931225/oyatie/branches/dev/protection` (2026-06-07):** `required_status_checks.contexts = ["github-lane-unlocker-required"]` (committed SSOT names `oya-ci-required`), `strict=false`; `enforce_admins=false` (committed `github-mirror/dev:dev.json:14` = `true`); `required_signatures=false` (committed `github-mirror/dev:dev.json:17` = `true`); `required_pull_request_reviews.required_approving_review_count=1` (committed `github-mirror/dev:dev.json:15` deliberately null); `required_linear_history=true`, `allow_force_pushes=false`, `required_conversation_resolution=true`. So **LIVE diverges from BOTH committed SSOTs on EVERY axis** — context, admins, signatures, review-count — the interim lane-unlocker bridge vs the SSOT target (live `false/false/1` vs both committed SSOTs' `true/true/null`; live `github-lane-unlocker-required` vs both committed SSOTs' `oya-ci-required`). The `enforce_admins:false` / `required_signatures:false` weakening is a real security hole. Until Stage 1 lands, there is **NO true blocking CI gate on `dev`**. This is the firewall-first cardinal sin (`D-SEQUENCE`, canon line 204-210) and forces Stage 1 to be **kill-the-false-green** before anything else. **Governance note:** this divergence is the interim bridge vs the SSOT; raise to the founder (OQ-8) whether the live `enforce_admins:false`/`required_signatures:false` weakening **and** the unilateral required-context swap to `github-lane-unlocker-required` were authorized.
2. **Two disjoint git worlds, NO merge-base.** `github-mirror/dev` (9f1047e62, 10 commits, LIVE, carries only the lane-unlocker workflow) vs `phase0/producer` (2deaa3bcd, 985 commits, on disk, carries the firewall+gates+controller). The firewall predicate is sound but **wired into ZERO pipelines** and has **no `main.rs`/bin**. Go-live is a **fresh-root import, not a merge/cherry-pick** — this forces the topology decision (OQ-2) and makes the firewall-bin + source-landing the long-pole.
3. **GitHub Actions is the live runner of the ONE canonical pipeline (D-CICD-AUTHORITY + ONE CANONICAL CI).** Throughput, surface-all, and drift-defense must ALL be delivered through GitHub Actions running the shared Rust gate logic NOW, producing the one canonical blocking context `oya-ci-required`; the owned `oya-ci` is the SAME pipeline's future runner (cutover-later). This means every "real enforcement" deliverable must be a GitHub Actions seam, and the canonical pipeline source must be reachable by GitHub Actions (topology) — not deferred to the cluster. There is no parallel shadow run to stand up.

### Viable Options (≥2 with bounded pros/cons)

The single biggest open design decision is the **go-live topology** — where the ONE canonical pipeline SOURCE lives so the live GitHub Actions runner can execute it (under ONE CANONICAL CI, the canonical pipeline must be runnable by Actions; there is no shadow cluster lane to fall back to).

**Option B (RECOMMENDED) — Thin fresh-root-import PR lands the canonical pipeline source + re-authored SSOT onto `dev`.**
Land the **committed** gates + `accounting-registry-producer` + registry-drift (from `phase0/producer @ e32af212c`) PLUS the **uncommitted** ratchet artifacts + `cloud-ci-firewall` crate + gate-lib keying mods (from the working tree) + the **net-new `cloud-ci-firewall` `main.rs` bin** onto live `dev` root as one auditable fresh-root-import PR (filtered for forbidden vocab/stale files), wire it into the lane matrix, and **re-author the SSOT (`dev.json` + `branch-protection.yaml`) off ADR-0513 onto D-CICD-AUTHORITY** (framing change; the target context name `oya-ci-required` is KEPT) in the same landing.
- *Pros:* puts the ONE canonical pipeline **where GitHub Actions runs it** — delivering "real enforcement NOW via GitHub" per D-CICD-AUTHORITY/ONE CANONICAL CI, and the GitHub-Actions fan-in becomes the canonical `oya-ci-required` authority context. Source visible/auditable on `dev`'s graph; transparent diff. The SSOT re-author lands with the source it describes (no RED-on-arrival drift gate).
- *Cons:* manual fresh-root import (no merge-base → provenance-lossy); the import set spans **committed (`phase0/producer`) AND uncommitted working-tree** sources — both must be captured or the pipeline lands incomplete; larger blast radius; risks re-importing forbidden vocab unless filtered (the brand-residue gate must run on the import). Larger review surface. Carries the SSOT re-author + required-context-identity founder gate (OQ-8).

**Option C — Branch-swap (promote `phase0/producer` to BECOME `dev`).**
- *Pros:* single source of truth; gates native; no porting.
- *Cons:* hard one-way default-branch rewrite; orphans the live mirror history; **the live lane-unlocker workflow does NOT exist on `phase0/producer`** (only `backbone-microservices-ci.yml`) so the live gate would have to be re-created; highest blast radius. **NOT recommended.**

**Recommendation: B — the fresh-root import puts the one canonical pipeline where GitHub Actions runs it.** Under ONE CANONICAL CI there is a single pipeline producing the single blocking context `oya-ci-required`; only B puts that pipeline source where GitHub Actions (the live runner) can execute it. The owned `oya-ci` becomes the SAME pipeline's future runner at cutover (a runner-swap validated then), so there is no parallel shadow lane to stand up now. **This collapses the synthesis's "A-first / B-then-A-shadow" framing** (App-posted shadow lane is moot once there is no second context to post) and is flagged for the Architect. C is invalidated above (no live workflow on that root + default-branch rewrite blast radius).

*Why the App-posted shadow lane (former Option A) is dropped:* it existed only to post a separate `oya-ci-required` non-blocking shadow status and measure verdict-agreement against a parallel run. Under ONE CANONICAL CI there is exactly one pipeline, one context, and no parallel run — so a shadow lane has nothing to shadow and nothing to agree with. Its branch-agnostic-status insight (forge-neutral `CommitStatusPoster`, `oya-ci-controller-kernel/src/lib.rs:620-621`) is moot for this campaign; it may resurface only as plumbing for the future owned-runner swap, which is out of scope.

## DELIBERATE-MODE ADDITIONS

### Pre-mortem (3 failure scenarios + mitigation)

**Scenario 1 — "We shipped a new false-green."** The new zero-build fan-in required job is wired with `needs:[<lanes>]` but a lane is added later (or renamed) and not added to `needs`, OR a lane sets `continue-on-error:true`, OR the firewall bin exits 0 on an internal error (panic swallowed), OR **a gate crate exists in-tree (`cloud/cloud-ci/gates/*`) but is never registered in the firewall bin's evaluate set** (a silent false-green — the same cardinal sin one level down: the aggregator looks complete but silently skips a gate) — so the required context goes green while a real failure exists. This is the exact sin we are fixing, re-introduced.
- *Mitigation:* (a) The fan-in job does `exit 0` ONLY — it has no command set of its own (Principle 1); a **meta-test** asserts the required job's `needs:` list byte-equals the matrix lane set (a gate over the workflow YAML, run in presubmit). (b) The firewall bin distinguishes **`verdict=red` (findings)** from **`error=tooling-failed` (could not evaluate)** and exits non-zero on BOTH; **the TAMPER fixture lands as an ACTUAL test extending `cloud-ci-firewall/tests/firewall.rs` (not prose)** — a `firewall_goes_non_zero_on_tampered_or_empty_input` case alongside the existing `firewall_fixtures_execute_red_green_cases` (`tests/firewall.rs:100`), proving a swallowed-panic/empty-input case exits non-zero. (c) **Gate-registration-completeness meta-test (Pre-mortem-S1 sibling acceptance test):** a test asserts that **every in-tree `cloud/cloud-ci/gates/*` crate is registered in the firewall bin's evaluate set** — an in-tree-but-unregistered gate fails this meta-test. This closes the silent-skip false-green one level below the `needs:` meta-test. (d) Verifier lane (separate, no self-approval) re-derives the verdict independently and diffs.

**Scenario 2 — "An advisory→blocking flip wedged every PR."** Someone flips one of the 5 advisory codes (24,161 unowned; 20,643 unreachable; 83 stale; 2 zero-key TTL — `pipeline-analysis` disposition-flip finding) to `baseline-block-on-new` before its named infra exists (`owners-files-tree-wide`, `masterplan-reachability-wiring`, `ttl-policy-table-complete`). Every PR now blocks on frozen pre-existing debt → total merge deadlock.
- *Mitigation:* (a) The flip is **NOT a hand-edit** of `gate-baseline.generated.json`: it is a founder-signed disposition flip in `gate-disposition.json` → **producer-regen** of the baseline face → **registry-drift byte-parity** (the `mode` field at `lib.rs:147` is producer-emitted, see 4D), gated behind an **infra-prereq assertion**: a gate refuses the flip unless the named infra target is GREEN (e.g. `find -name OWNERS != 0` for `owners-files-tree-wide`; `resolve_owners` returns empty today, `accounting-registry-producer/src/main.rs:574`). (b) Each flip is its own `door:one-way` founder sign-off (OQ-3) with a dry-run that prints the would-block key count. (c) The advisory burn-down dashboard must read **shrinking** before a flip is even proposed.

**Scenario 3 — "We hardened branch protection and locked ourselves (or the founder) out / broke the live producer."** Applying `enforce_admins:true` + `required_signatures:true` + reconciling review-count on live `dev` while the required-context-of-record is mid-identity-change (the live `github-lane-unlocker-required` bridge being retired in favor of the canonical `oya-ci-required` produced by GitHub Actions), or before the SSOT re-author lands (so the drift gate is RED-on-arrival), or while commit signing isn't actually live (canon D-MERGE: "signatures-not-live-yet-but-flipping") → every merge blocks, admins can't bypass to fix it, unsigned automation commits rejected.
- *Mitigation:* (a) **HALT gate** — no live `gh` protection mutation happens in automation; it is a founder-paired, GitHub-admin, `door:one-way` step (`scripts/branch-protection-apply.sh:13-14,69` documents that `GITHUB_TOKEN` cannot self-request Administration-write). (b) **Order:** RE-AUTHOR the SSOT off ADR-0513 FIRST (OQ-8, framing change; context name `oya-ci-required` kept); stand up the GitHub-Actions-produced `oya-ci-required` fan-in and prove it GREEN on a real PR SECOND; switch the required-context IDENTITY to `oya-ci-required` (admin door) and confirm SSH commit signing (`id_ed25519`) is live on the merge-bot THIRD; only THEN harden admins/signatures/review-count. (c) The protection-drift gate runs **report-only** until BOTH the SSOT is re-authored AND the live state is hardened to match it — its soak target is "live == re-authored SSOT," never "live == ADR-0513 SSOT" (which has no zero-able target). (d) A documented rollback: the founder can revert the protection JSON via the same admin path.

### STAGE 2 — THROUGHPUT (organized around warm-cache / delta-only-cold; each item PRESERVES surface-all) `[parallel, after Stage 1]`

**Goal (the founder's deciding factor):** CI wall-clock must scale with the **SIZE OF THE CHANGE, not the repo** — the hyperscaler property. Keep wall-clock low without ever short-circuiting. Every item below is verified surface-all-preserving in `pipeline-analysis` (`preserves_surface_all:true`).

**Dependency:** Stage 1 (the aggregator + non-lying gate must exist first). **Blocks:** Stage 4 (merge queue amortizes the whole-tree firewall over batches).

**Cache-warmth & cold-surface (the ORGANIZING PRINCIPLE — the founder calls it "the deciding factor"):**
The single driver of every 2x item below: **keep caches WARM and ensure only the part that CHANGED is cold.** The mechanism:
- **Content-addressed actions + a remote/shared read-through cache** (Buck2 RE-API → BuildBuddy / EngFlow / BuildBarn / NativeLink) so an unchanged action's input-hash is a **cache HIT on ANY runner** (never re-executed) — `2E`.
- **Affected-targeting** (owner→rdeps closure runs ONLY the changed targets + their reverse-deps, never the whole tree on a small change) — `2F`.
- **Content-addressed producer artifact** (0 recompiles when unchanged) — `2C` (+ generate-once-share `2A`, O(1) reachability `2B`).
- **`actions/cache` for the buck2 binary / toolchain / buck2-out** so ephemeral runners don't bootstrap COLD every run — `2E`.
- **HERMETIC actions are a REQUIREMENT** — non-hermetic actions (wall-clock, network, absolute paths) **poison the cache** (their output hash is non-reproducible → false misses or, worse, false hits). Every cached action must be hermetic.
- **PRECISE (not coarse) cache keys — explicit anti-pattern to avoid** — a 1-file change must invalidate **only its dependents**, not the world; an over-broad key (e.g. hashing the whole tree into one key) collapses delta-only-cold back to whole-repo-cold. Avoid coarse keys.
- **Merge-queue batching amortizes the whole-tree cost** across a batch (~/N per PR) — `2F`/`4B`.
**Surface-all is PRESERVED at every cache layer:** a cache HIT still EXECUTES + REPORTS the cached result (the aggregator still surfaces it); nothing short-circuits or hides a finding. **Deep-research caveat (validate empirically):** hash-based affected-selection can occasionally over- or under-include (e.g. a comment-only edit flips a content hash) — the impact set must be validated empirically (compare selected-set vs a periodic whole-graph run), never trusted blind.

## ADR — oyatie CI/CD Firewall-First Pipeline Design

**Decision.** Adopt ONE CANONICAL CI: a two-level surface-all pipeline (parallel lanes at the top, one collect-all `FirewallReport` at the bottom) gated by a **single pure zero-build fan-in required context `oya-ci-required` that GitHub Actions PRODUCES as the canonical blocking authority-of-record** (NOT a re-point of the SSOT-branded "shadow compatibility only" `github-lane-unlocker-required`), plus a **branch-protection drift gate**, delivered **through GitHub Actions as the live runner** (D-CICD-AUTHORITY). The owned `oya-ci` is the **future runner of this SAME canonical pipeline** (a runner migration over time), NOT a second parallel CI and NOT a non-blocking shadow. Stage 1 kills the false-green (stand up the canonical `oya-ci-required` fan-in + build the firewall bin with a gate-registration-completeness meta-test + RE-AUTHOR the SSOT off ADR-0513 as a framing change keeping the `oya-ci-required` name + drift gate + kill within-lane fail-fast) BEFORE any throughput/automation work (firewall-first, D-SEQUENCE). Throughput (Stage 2) is organized around **warm caches + only-the-changed-part-is-cold** (the founder's deciding factor): CI wall-clock scales with the SIZE OF THE CHANGE, not the repo. Topology: **B (fresh-root import of committed + uncommitted sources, plus the SSOT re-author, onto `dev`) puts the one canonical pipeline where GitHub Actions runs it — no shadow lane.**

**Drivers.** (1) The live required check is a structural false-green and the live ruleset diverges from its committed SSOT on EVERY axis — context (live `github-lane-unlocker-required` vs SSOT `oya-ci-required`), `enforce_admins:false` (SSOT true), `required_signatures:false` (SSOT true), `review_count=1` (SSOT null) — VERIFIED live `gh api` 2026-06-07; directives #1/#3/#4 all violated at the one gate that blocks merges, and the SSOT itself is written under the SUPERSEDED ADR-0513 Prow worldview so it must be re-authored. (2) Two disjoint git worlds, no merge-base; the firewall has no bin and runs nowhere; the import set spans committed `phase0/producer` + uncommitted working-tree — go-live is a fresh-root import. (3) GitHub Actions is the live runner of the ONE canonical pipeline (D-CICD-AUTHORITY + ONE CANONICAL CI) → real enforcement must flow through GitHub Actions running the shared Rust gate logic now, producing the one canonical blocking context `oya-ci-required`; the owned `oya-ci` is the same pipeline's future runner (cutover-later), not a parallel CI.

**Alternatives considered.** (a) **Two CIs / a parallel non-blocking shadow run + verdict-agreement (former Option-A shadow lane + Stage 6)** — invalidated by ONE CANONICAL CI: there is exactly one pipeline and one context, so a parallel shadow has nothing to shadow; verdict-agreement was confidence-building, not enforcement, and is dropped. The GitHub→owned-runner cutover is a future runner-swap of the SAME pipeline, validated at swap time. (b) **C (branch-swap)** — invalidated: default-branch rewrite blast radius + the live workflow doesn't exist on `phase0/producer`. (c) **`oya-ci-required` as a non-blocking shadow context** (older D-CICD-AUTHORITY clause) — superseded by ONE CANONICAL CI: `oya-ci-required` IS the one canonical blocking context, produced by GitHub Actions now. (d) **Per-axis multiple required contexts** — invalidated by the `oya-pr-review` HTTP-501 multi-producer-deadlock lesson; one fan-in context with per-finding annotations instead. (e) **Re-pointing the shadow-branded `github-lane-unlocker-required` to be authority-of-record** — invalidated because the committed SSOT explicitly forbids treating that name as merge authority (verbatim in `github-mirror/dev:infra/branch-protection/dev.json:12` `_phase0_target_note` + `:36` `legacy_shadow_context`); the honest move is the GitHub-Actions-produced canonical `oya-ci-required` context (OQ-8). (f) **Hand-editing `gate-baseline.generated.json` to flip advisory→blocking** — invalidated because it drifts the producer face and trips registry-drift; the flip is producer-regen + signed disposition + byte-parity (4D). (g) **Coarse whole-tree cache keys** — invalidated: a coarse key collapses delta-only-cold back to whole-repo-cold; precise per-target keys + hermetic actions are required (Stage 2).

**Why chosen.** Only B makes the one canonical pipeline live-runnable by GitHub Actions (the live runner), and lands the SSOT re-author with the source it describes so the drift gate has a zero-able target — with no second CI to build or shadow to maintain. The zero-build fan-in + aggregator is the minimal change that makes the canonical `oya-ci-required` context stop lying while satisfying surface-all as a data-structure property (not careful sequencing); the gate-registration-completeness meta-test closes the silent-skip false-green one level down. The drift gate makes the protection config self-defending (directive #4). Throughput is organized around warm-cache / delta-only-cold (the founder's deciding factor) so wall-clock tracks change-size not repo-size, with every cache layer still executing+reporting (surface-all preserved). Firewall-first ordering follows the founder ruling that you cannot fix canon on fake enforcement.

**Consequences.** Positive: one true blocking gate produced by the canonical `oya-ci-required` context (one CI, not two); one-sweep fixes; drift caught by enforcement even if automation fails; no silent-skipped gate (registration meta-test); throughput via warm-cache + delta-only-cold (affected-targeting + remote read-through cache + content-addressed producer + actions/cache + hermetic actions + precise keys + merge-queue), so wall-clock tracks change-size not repo-size, all surface-all-preserving; supply-chain trust at the merge boundary; the shadow-run + verdict-agreement apparatus is eliminated (less to build/maintain). Negative/cost: a fresh-root import is manual and provenance-lossy and spans committed + uncommitted sources (mitigated by filtering + brand-residue gate + an explicit import-set checklist); the live go-live requires **THREE founder-paired GitHub-admin one-way doors** — (i) the required-context IDENTITY change to the canonical `oya-ci-required`, (ii) the SSOT re-author off ADR-0513 (framing change, name kept), (iii) admins/signatures/review-count hardening — so admins/signatures is NOT the "only" admin gate; advisory→blocking flips must be infra-sequenced AND producer-regenerated or they deadlock/drift; hash-based affected-selection can over/under-include and must be validated empirically against a periodic whole-graph run.
