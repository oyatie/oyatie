# ADR-0580: corpus substrate Phase -1 — the conservative-v1 `syn`-over-source AST extractor spike

## Status

**Proposed - 2026-06-22 (authored for founder adversarial review; door: two-way — additive, generates
no gate faces itself, removable by deleting the `governance/corpus/` tree + reverting the four
policy-as-data edits, no SSOT unwinding).**

## Context

The live-AST governance substrate ("corpus") is the planned fail-closed answer to decay/drift/
staleness: a content-addressed AST graph where docs/directives are build artifacts and liveness is a
fail-closed invariant rather than a hand-maintained mention. Before committing to the full design
(node model + query engine + a blocking gate), the founder asked for a **Phase -1 de-risk slice**:
build ONLY the extractor in isolation and measure whether parsing committed Rust SOURCE with `syn`
is a sufficient v1 liveness substrate, or whether the semantic layer (a rust-analyzer adapter / the
bespoke-rowan CST) must be pulled forward.

The single go/no-go number is the **OPAQUE-RATE**: the fraction of the corpus a source-level `syn`
extractor cannot resolve to a clean fact — code generated by macros, behind `#[cfg(...)]`, or
produced by build scripts. A high opaque rate would mean source-level parsing is blind to too much
of the live surface; a low rate means `syn`-over-source is a sufficient v1 substrate.

## Decision

### D1 — Conservative-v1 posture: `syn`-over-source behind a stable `AstSource` seam

The v1 extractor parses committed Rust source with `syn` 2.x. The fact producer is hidden behind a
stable `AstSource` trait so a W-tier successor (a bespoke rowan-style CST / a semantic ra adapter)
can replace the producer LATER without disturbing the fact model or any consumer. `salsa`/`rowan`
stay ABSENT for v1 (verified absent from `Cargo.lock`); `syn` + `blake3` are already vendored.

### D2 — Content-addressed `Function` fact with a split signature/body anchor

Each fact carries TWO independent `blake3` digests over disjoint canonical pre-images:

- `signature_hash` over `crate_id\0fqpath\0item_kind\0visibility\0signature` — the **stable liveness
  identity**, invariant under body edits AND pure reformatting. A rename / removal / visibility
  change MUST churn it.
- `body_hash` over the item's normalized token stream — the finer implementation-drift signal that
  may legitimately churn at body granularity.

Splitting the two is the whole point: signature stability lets governance track an item across
refactors while body sensitivity still detects implementation drift.

### D3 — Hermetic, deterministic extraction over `git ls-files` (no ambient walk)

The extractor resolves a capability's crates by REUSING `libs/oya-workspace-members-kernel`
(`resolve_member_dirs`, not a re-derivation of member-glob semantics), then walks each crate's
GIT-TRACKED `.rs` sources via `git ls-files` (the committed set only — vendored/target/ignored files
never leak in). No clock/rand/net; output is sorted/canonical, so the same input yields a
byte-identical fact set (ADR-0083 hermetic-determinism). There is NO hand-listed function set — the
facts ARE the `syn` output.

### D4 — `governance/corpus/` is the substrate home (governance-engine code, not a capability)

The corpus crates are physically homed under the `governance/` meta directory at
`governance/corpus/core` (cargo `corpus-core`) and `governance/corpus/extract` (cargo
`corpus-extract`, buck `//governance/corpus/extract:app`), de-branded per the ADR-0532/0533 path-tail
grammar. This is consistent with the capability-registry `governance/` meta_dir `owns_crates: false`
carve-out: it owns no CAPABILITY crate, but `governance/` hosts governance-ENGINE code (the registry
comment already concedes this for the `libs/oya-check-*` / `libs/oya-governance-*` dep-lint
authority). `owns_crates` is documentary, not gate-enforced; corpus is not a sold capability and
stays off the runtime ladder.

Four policy-as-data edits make the placement gate-clean (automation applies these human decisions;
it does not invent them — ADR-0568 D2):
1. root `Cargo.toml` `[workspace].members` gains `governance/corpus/*` (a 3-segment glob — the
   members-kernel matches `*` per-component with an exact segment count, so a 2-segment `governance/*`
   would NOT match a 3-segment crate dir).
2. `specs/capability-registry.json` governance `absorbs_current_crate_globs` gains
   `governance/corpus/*` → `meta:governance/` (the membership-lint glob is a stem `starts_with`
   match).
3. the capability-membership gate policy `scan_roots` gains `governance` so the corpus crates are
   actually scanned and validated against the mapping (governance is already in
   `allowed_top_level_dirs` + `meta_directories`).
4. `specs/reachability-registry.json` gains a `governance/corpus/OWNERS` ownership-seed prefix so the
   whole subtree is born-reachable.

### D5 — `syn` + `quote` promoted to direct workspace deps; reindeer emits the public aliases

`syn`/`quote` existed in `Cargo.lock` TRANSITIVELY only (private `third-party//:syn-2` /
`:quote-1`, no public alias). They are promoted to `[workspace.dependencies]` so the buck dep label
exists. The locked versions (`syn 2.0.117`, `quote 1.0.45`) and the generated `syn-2` feature set
(`full`/`extra-traits`/`parsing`/`visit`/`clone-impls`) are unchanged by the flip. The two PUBLIC
aliases were applied SURGICALLY (not a blanket `reindeer buckify` commit) because a full regen on
this checkout's reindeer version would ALSO wipe pre-existing post-buckify manual fixups
(`aws-lc-sys` DEP_* injection; `psm` per-OS `preprocessor_flags` select — the latter's own comment
warns it breaks the aarch64-linux link) and add an unrelated `base64` alias. The committed
`third-party/BUCK` diff is exactly the two alias blocks.

## Spike findings (the go/no-go evidence)

Extracted capability: **`flags`** — the smallest clean, already-de-branded capability (exactly 2
workspace crates: `flags/core/evaluation-domain` + `flags/core/server`; `comms` resolves to 19
crates, far larger). The mix is ideal: a pure-domain crate plus a service crate with gRPC/REST/
storage modules.

- **Fact count:** 41 clean facts (37 from evaluation-domain, 4 from server — the server's
  grpc/rest/ofrep/storage/targeting/tenants modules are scaffolded TODO stubs with zero items, which
  the extractor faithfully reflects: it IS the `syn` output). By kind: 20 type, 14 function, 4 impl,
  3 pub_item.
- **Reformatting fuzz:** whitespace + comment-only reformatting of every `flags/*.rs` source →
  re-extract → **signature-hash churn = 0** (per-item mismatches = 0, items lost = 0). The
  signature-level anchor is stable, as required.
- **OPAQUE-RATE:** 3 opaque / 44 total = **6.81%**, and ALL three are `#[cfg(test)] mod tests`
  blocks (`bucket::tests`, `evaluation::tests`, `tests`). There were ZERO `macro_generated` and ZERO
  `build_script_generated` opaque units in this capability. The PRODUCTION-code opaque rate is
  effectively 0%.

Two real defects the spike surfaced and fixed (de-risk value realized):
1. `syn`'s raw `to_token_stream` is NOT trailing-comma invariant (`(a: T,)` vs `(a: T)`), so a
   source-optional trailing comma churned the signature anchor. Fixed by reconstructing the
   signature from `syn::Signature`'s structured fields (`Punctuated::iter` drops the trailing
   punctuation).
2. An `impl`-block anchor keyed on a SOURCE LINE NUMBER churned under reformatting (inserting blank
   lines shifts lines). Fixed by a document-order ordinal (`#impl[n]`) — invariant under whitespace
   reformatting. A regression test (`impl_anchor_invariant_under_reformatting`) locks this in.

**Assessment:** for a clean, de-branded, pure-domain-plus-stub capability, `syn`-over-source is a
SUFFICIENT v1 liveness substrate — the opaque rate is dominated by test modules (legitimately
cfg-gated and out of the production-liveness scope), not by a semantic blind spot. The macro/cfg/
build-script opacity that would argue for pulling the ra/rowan semantic layer forward did not
materialize HERE. The honest caveat: `flags` has no `tonic::include_proto!`-style item-position
macros or build-script-generated code; the macro_generated rate is the metric to watch on a
proto-heavy capability (e.g. a gRPC server with real `include_proto!`), which a follow-up spike
should measure before the substrate is generalized. The conservative-v1 posture (stable `AstSource`
seam) means that finding, if it lands, swaps the producer without touching the fact model.

## Consequences

- A reusable, hermetic extractor + content-addressed fact model the full corpus design can build on,
  with the producer behind a stable seam.
- No gate, node model, or query engine yet (deliberately out of Phase -1 scope).
- `governance/` now physically hosts substrate crates (a new but registry-consistent pattern); the
  four policy-as-data edits keep the membership/reachability/workspace gates clean.

Precedent (proven patterns, Rust reimplementation): rust-analyzer's `syntax` (rowan) + `hir`
layering, `cargo-semver-checks`' rustdoc-JSON liveness, Bazel's content-addressed action graph,
Google's Kythe/Grok corpus — each a content-addressed code-fact substrate, here reimplemented
Rust-native, source-level first, semantic-layer deferred behind a port.
