# ADR-0614: De-commit the reorg move-manifest bijection

## Status

**Accepted — 2026-08-01.** The founder selected the de-committed, controller-derived move-manifest
posture during the north-star authority interview. The manifest, gitignore, deterministic
regeneration, fail-closed path resolution, registry-drift checks, and ADR-0563 amendment are already
present. The bijection is a pure derivation rather than a contributor merge surface; re-tracking it
requires a later Accepted reversing ADR.

## Context

ADR-0595 de-committed the six pure-derivation accounting faces under
`ci/facade/artifact-inventory-registry/`; ADR-0597 completed that strangler for the last shared
accounting face (`scm-facts.generated.json`); ADR-0613 de-committed the two remaining
controller-materialized projection faces (`masterplan.generated.json`, `product-graph.html`).
`specs/reorg/move-manifest.generated.json` — the rename-aware path-keyed CI baseline relabel's
move-bijection (ADR-0563) — was the LAST committed pure-derivation reorg face. ADR-0613 explicitly
deferred it, reaffirming ADR-0563's "stays committed" stance and naming the three preconditions for
reversal (an explicit ADR-0563 amendment; the path-resolver fail-open; move-manifest was never the
corruption source). This ADR is that amendment.

Leaving move-manifest committed is not merely friction — it is a **catch-22 that blocks every
capability-move reorg PR**:

- The required `generated-output-diff-policy` gate forbids ANY modification of a committed declared
  generated artifact (the allowed-generated-edit-paths set is empty BY DESIGN —
  `diff_policy_allowed_generated_edit_paths` returns `{}` because "contributors must not own
  generated bytes"). A move PR that regenerates the bijection therefore REDs the diff-policy.
- The `registry-drift` gate simultaneously requires `committed == regenerated` for the committed
  face. A move PR that does NOT regenerate it REDs registry-drift.

A real move must change the bijection (that is the whole point of the relabel), so it cannot satisfy
both at once. Every capability move is wedged between the two gates.

The hyperscaler doctrine resolves it cleanly: **generated / derived artifacts are never committed
merge surfaces at scale.** move-manifest is a pure, deterministic bijection — a function of the
committed move-plan(s) × the candidate tracked tree — exactly the shape the ADR-0595 → ADR-0613
strangler de-commits. CI materializes it on demand; contributors never own its bytes; the gate that
forbids editing a committed generated face simply no longer has a committed face to guard (it
exempts `not-tracked-in-git`).

## Decision

STOP committing `specs/reorg/move-manifest.generated.json`. Declare it
`materialization_mode: not-tracked-in-git` in `registry/generated-artifact-control-plane.json`,
remove it from git (`git rm --cached`), and cover it by `.gitignore` (the existing broad
`**/*.generated.json` rule; the ADR-0563 negation `!specs/reorg/move-manifest.generated.json` and
its "must be TRACKED" comment are removed). It is derived on demand as STEP 1 of the existing
materializer entrypoint
(`//ci/facade/generated-artifact-freshness:oya-cloud-ci-materialize-generated-faces-bin` →
`materialize_move_manifest`, which runs the codemod `manifest` subcommand) and written
out-of-graph before the scm-facts emitter's rename-aware relabel consumes it.

Gate / consumer consequences (all verified against the code, no flag day):

1. **Control-plane / policy gate** (`ci/facade/generated-artifact-policy`): no predicate change.
   The ADR-0595 `not-tracked-in-git` machinery already applies — the path is EXEMPT from
   `generated_artifact_declared_path_not_tracked` and, once `git rm --cached`ed, satisfies the
   one-way re-tracking guard `generated_artifact_not_tracked_path_is_tracked`. The
   `generated-output-diff-policy` bridge exempts move-manifest because a de-committed path no longer
   appears as an add/modify diff row (a `git rm` deletion yields NO candidate paths, so it is not a
   merge-surface violation), and future PRs never stage the gitignored materialized copy.
2. **registry-drift** (`ci/facade/inventory-registry-drift`): the
   `committed_move_manifest_equals_regenerated` byte-parity test is converted to
   `move_manifest_regenerates_deterministically` — the same regenerate-twice DETERMINISM canary the
   de-committed accounting faces use (`scm_facts_regenerates_deterministically`). There is no
   committed copy to compare; instead two fresh codemod emissions must be byte-identical. Coverage is
   NOT weakened: a non-deterministic generator (which could forge a different bijection on the
   materialize leg than on a relabel-read leg) still hard-fails.
3. **freshness gate** (`ci/facade/generated-artifact-freshness`): no recognizer change. move-manifest
   is only MATERIALIZED by this gate (`materialize_move_manifest`, step 1) — it is NOT in the
   freshness-CHECK scan set (`read_committed_generated_faces` scans
   `ci/facade/artifact-inventory-registry/` + `product-graph.html`; `read_decommitted_face_names`
   matches only `GENERATED_FACE_PATHS` / `CONTROLLER_MATERIALIZED_ARTIFACT_PATHS`). move-manifest's
   freshness is governed solely by registry-drift.
4. **path-resolver** (`ci/adapters/path-resolver`): `MoveManifest::load` / `ManifestBijection::load`
   / `ManifestPathResolver::load` still return `Self` infallibly, mapping absent → `empty()`
   (identity). This fail-OPEN is safe post-de-commit because the materializer writes the manifest as
   step 1 of every leg BEFORE any relabel-read (audited across
   `.github/workflows/oya-ci-required.yml`: every scm-facts emitter invocation runs via
   `materialize-generated-faces-bin`; there is no standalone-emitter leg). The doc comment records
   the materialize-first precondition and the fail-closed hardening follow-up.

## Consequences

- move-manifest is never in a PR diff again; the diff-policy vs registry-drift catch-22 is dissolved
  and capability-move reorg PRs can land. Reviewers see the move through **git rename detection**
  (`--find-renames`) plus the **committed move-PLAN** (`specs/reorg/<capability>-move-plan.json`,
  still tracked and reviewed) — the reviewed surface is the plan and the renames, not a committed
  bijection blob.
- Determinism (regenerate-twice) becomes the load-bearing integrity invariant for move-manifest, as
  it already is for the ADR-0595/ADR-0613 faces. Byte parity against a committed copy is retired.
- Latent hazard recorded, not dropped: the path-resolver `load` fails OPEN to identity on an absent
  manifest, which cannot distinguish `absent = materialization-error` (should hard-fail / false-RED,
  never merge bad) from `empty = no-move` (the correct identity). It is safe TODAY only because the
  materializer is ordered first on every leg. The fail-open → fail-CLOSED hardening (make `load`
  fallible; absent ⇒ error) is a tracked follow-up (a `ponytail:` marker on the `load` body + this
  note), deferred here to avoid rippling the infallible `load` signature through the emitter in this
  PR. Its failure mode today is a safe false-RED (blocks, never merges bad).
- Consumer safety (verified): no BUCK `srcs` reference the face, so `buck2 build` is unaffected. The
  only runtime reader is the scm-facts emitter (`ci/facade/scm-facts-snapshot`,
  `ManifestPathResolver::load`), which runs inside the materializer AFTER `materialize_move_manifest`.
  The `register_crate` scaffold (`ci/facade/crate-registration`) writes the manifest to the now-
  gitignored path but never git-adds it, so it cannot re-track the face.

## Alternatives considered

- **Keep move-manifest committed and special-case the two gates.** Rejected: it hard-codes an
  exception into the diff-policy (which is empty-allowlist BY DESIGN) and preserves the anti-pattern
  the whole ADR-0595 → ADR-0613 strangler retires — a committed pure-derivation merge surface.
- **De-commit AND refactor `load` to fail-closed in one PR.** Deferred: the fail-closed refactor
  ripples the infallible signature through `ManifestBijection` / `ManifestPathResolver` / the emitter
  and is a materially larger, higher-risk change. The materialize-first ordering makes the fail-open
  safe today; the hardening is a recorded follow-up rather than a blocker.

## Artifact accounting (ADR-0555)

This PR de-commits exactly ONE tracked generated face
(`specs/reorg/move-manifest.generated.json`; `git rm --cached`). The face leaves the tracked-output
set but remains DECLARED in `registry/generated-artifact-control-plane.json` (now
`not-tracked-in-git`), so declared-artifact accounting is unchanged in shape. The PR additionally
edits: the manifest artifact row (`cloud-ci-reorg-move-manifest`: materialization_mode +
final_tree_validation + public_product_contract); `.gitignore` (remove the ADR-0563 negation + its
comment; rewrite the ADR-0613 "move-manifest is EXCLUDED" note to document that move-manifest joins
the de-commit class); the registry-drift test (byte-parity → regenerate-twice determinism); the
freshness-gate unit fixtures (rename a misleading `move-manifest` committed-class example to a
neutral placeholder); `ci/adapters/path-resolver` doc comments (materialize-first precondition +
fail-closed follow-up); `specs/reachability-registry.json` (refresh the `specs/reorg/` anchor prose
— the prefix still covers the tracked move-plans); ADR-0563 (`amended_by: [ADR-0614]` + an "Amended
stance" note); and adds this ADR. It adds no new crate. `decisions.json` / `ADR-INDEX.md` are
land-time materialized, not hand-edited in this PR.
