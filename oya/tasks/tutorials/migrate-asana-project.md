# Tutorial — Migrate an Asana project to oyatie tasks in 30 minutes

You will: export an Asana project, import it into oyatie, verify the result, and remap custom-field types. Total time ≤ 30 min for a project with ≤ 1 000 tasks.

## Pre-requisites

- Workspace in paid tenant_class, or demo_trial with an import usage cap that admits the project size; the Asana importer is not feature-class gated.
- Asana Personal Access Token with `read` scope on the source project.
- `oya-dev-cli` ≥ 1.42.0.

## Step 1 — Inventory the source (≤ 5 min)

```sh
oya tasks import inventory \
    --vendor asana \
    --token <asana-pat> \
    --project <asana-project-id> \
    --out inventory/asana-project-<id>.yaml
```

The inventory lists: tasks, sub-tasks (up to 5 levels deep), custom fields (with their types), sections, assignees (by Asana user ID; needs mapping in Step 2), due-dates, attachments (URL-referenced; we don't auto-pull blobs — see Step 5), and tag/labels (Asana calls them "Tags"; oyatie calls them "Labels").

Review the inventory file before importing — it gives you a chance to:

- Drop sections you don't want (e.g., archived "Backlog from 2022").
- Note any custom-field type that doesn't map cleanly (Asana's "People" field maps to oyatie's "Person" custom-field type; Asana's "Number" maps to "Number"; Asana's "Date" maps to "Date"; Asana's "Multi-Select" maps to "Multi-Select"; Asana's "Text" maps to "Text"; Asana's "Formula" maps when the importer compatibility setting admits it).

## Step 2 — Map Asana users to oyatie users (≤ 5 min)

```sh
oya tasks import map-users \
    --inventory inventory/asana-project-<id>.yaml \
    --strategy by-email \
    --out mapping/asana-users-<id>.yaml
```

The mapping is generated by matching Asana's `email` to oyatie's `user.email`. Users without an oyatie account are mapped to `__unassigned__` and you can manually edit the YAML to point them at a real user (or leave unassigned and the importer will create the tasks unassigned).

Common edit:

```yaml
asana_user_id: 1234567890
asana_email: alice@example.com
asana_name: Alice Wong
oyatie_user_id: u-acme-alice-wong-001  # edit me; default was __unassigned__
```

## Step 3 — Map Asana custom fields to oyatie custom-fields (≤ 5 min)

```sh
oya tasks import map-fields \
    --inventory inventory/asana-project-<id>.yaml \
    --target-project <oyatie-project-id> \
    --out mapping/asana-fields-<id>.yaml
```

The mapping resolves each Asana custom field to either:

- An existing oyatie custom-field in the target project (by name match).
- A new oyatie custom-field to be created during import.
- Drop (you don't want this field in oyatie).

Edit the YAML to set the action per field. The importer will create new custom-fields with names matching the Asana names (lowercased + dashes); rename in oyatie afterward if desired.

## Step 4 — Dry-run (≤ 5 min)

```sh
oya tasks import dry-run \
    --inventory inventory/asana-project-<id>.yaml \
    --user-mapping mapping/asana-users-<id>.yaml \
    --field-mapping mapping/asana-fields-<id>.yaml \
    --target-workspace my-workspace \
    --target-project <oyatie-project-id>
```

The dry-run produces a report:

- N tasks would be created.
- M custom-fields would be added to the project.
- K user assignments preserved; L assignments unassigned.
- Q subtasks would be created.
- W tags converted to labels.
- The report ends with "no errors detected" or a list of issues to address before live-run.

## Step 5 — Live import (≤ 5 min for 1 000 tasks)

```sh
oya tasks import run \
    --inventory inventory/asana-project-<id>.yaml \
    --user-mapping mapping/asana-users-<id>.yaml \
    --field-mapping mapping/asana-fields-<id>.yaml \
    --target-workspace my-workspace \
    --target-project <oyatie-project-id>
```

Progress is reported every 10 s. Expected throughput: ~ 200 tasks/min (rate-limited by Asana's API quota of 1 500 reqs/min; the importer pages reads).

The audit-chain emits one `bulk_task_import_started` and one `bulk_task_import_completed` event with the project ID and count.

## Step 6 — Attachments (≤ 5 min)

Attachments are not auto-pulled in Step 5. Run:

```sh
oya tasks import attachments \
    --inventory inventory/asana-project-<id>.yaml \
    --asana-token <asana-pat> \
    --target-project <oyatie-project-id> \
    --concurrency 4
```

This downloads each attachment from Asana's CDN, uploads to oyatie's `drive` µservice (the canonical attachment store), and updates the task's attachment-reference. Throughput ~ 10 MB/s with `--concurrency 4`.

## Step 7 — Verify (≤ 5 min)

```sh
oya tasks import verify \
    --inventory inventory/asana-project-<id>.yaml \
    --target-project <oyatie-project-id>
```

The verify command compares:

- Asana task count = oyatie task count.
- Asana subtask count = oyatie subtask count.
- Asana custom-field values present on every task = oyatie custom-field values match.
- Asana due-dates = oyatie due-dates (timezone-aware comparison).
- Asana assignees mapped per `user-mapping` = oyatie assignees.

Report: `PASS` or per-task delta. Common deltas:

- "Asana task <id> had attachment <url>; oyatie task has no attachment". Run Step 6 again.
- "Asana task <id> assignee was unmapped". Edit the user-mapping; re-run Step 5 with `--update-only`.

## Step 8 — Sunset the Asana project

Once verify passes, set the Asana project to "complete" status in Asana — do NOT delete it for at least 30 days; if a re-import is needed, the source data must be intact. The 30-day window matches oyatie's own audit-chain retention for the import events.

After 30 days of successful operation on oyatie:

```sh
oya tasks import sunset-evidence \
    --vendor asana \
    --asana-project <asana-project-id> \
    --oyatie-project <oyatie-project-id> \
    --out evidence/migrations/asana-<asana-project-id>-sunset.json
```

The evidence file is committed and serves as the auditor-visible record that the migration completed.

## Common issues

- **Asana's "Custom Field" type "Formula" doesn't map under the current importer compatibility setting**: Enable the paid importer billing component or drop the formula field (importer warning will surface).
- **Asana's "Recurring task" semantics differ slightly**: Asana stores recurrence as "every N days from last completion"; oyatie uses RFC 5545 RRULE which is "every N days from start date". For exact behaviour parity, manually re-author recurring rules after import.
- **Asana's "Dependencies" model maps to oyatie's `blocks` only**: Asana's "dependency on" → oyatie's blocked-by. Asana doesn't model "relates-to" or "duplicates-of"; those remain in your project comments.
- **Asana Goals don't import**: oyatie's equivalent is "Milestones"; map manually if needed.
