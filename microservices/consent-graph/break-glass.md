# consent-graph break-glass procedures

- Owner: axis-consent-graph + security-axis + privacy-officer
- Date: 2026-05-18
- Authority: ADR-0214 §2.3 (fail-closed by default), HIPAA emergency-treatment, runbook integration.

## 1. Definition

Break-glass = an emergency-purpose data access that *bypasses* the normal consent-graph enforcement
flow under explicit, audit-heavy emergency conditions. Used sparingly; every break-glass invocation
is a P1-equivalent audit event.

This is NOT a general fallback — it's reserved for life-safety, regulatory-required, or system-wide
emergency conditions.

## 2. Authorized break-glass purposes

Per pack-overlay configuration:

### 2.1 us-healthcare pack
- Purpose: `emergency-treatment` (HIPAA-aligned; treatment of patient in medical emergency).
- Trigger: clinician initiates with patient-id + emergency-attestation.
- Scope: agreement's scope ∪ additional patient-treatment-relevant fields (defined per agreement
  template).

### 2.2 Banking pack
- Purpose: `fraud-investigation` (regulator + bank fraud team).
- Trigger: bank compliance officer initiates with case-id + regulator-reference.
- Scope: agreement's scope ∪ transaction history relevant to investigation.

### 2.3 All packs
- Purpose: `regulator-mandated-disclosure` (court order, subpoena, regulatory request).
- Trigger: legal-officer initiates with legal-instrument-reference.
- Scope: as specified by legal instrument (manually scoped).

## 3. Break-glass invocation

```rust
POST /v1/enforcement/break-glass-evaluate {
    agreement_id: AgreementId,
    purpose_override: BreakGlassPurpose,
    attestation: BreakGlassAttestation,
    legal_instrument_ref: Option<String>,
    requesting_principal: PrincipalId,
    case_id: Option<String>,
    expiry: Timestamp,  // ≤24h max
}
```

Steps:
1. Identity verification: `requesting_principal` must hold `break-glass:authorized` role in their
   tenant; verified via identity µservice.
2. Two-person rule: a second authorized principal must counter-sign within 30min (else request
   expires).
3. Attestation: `attestation` is a signed statement (HSM-signed) explaining the necessity.
4. Cedar policy compiled with relaxed scope (overlay on top of original agreement policy) for the
   specified expiry.
5. All actions under break-glass tagged with `break_glass_session_id` in audit-chain.

## 4. Cedar break-glass overlay

```cedar
permit (
  principal in Tenant::"<grantee_tenant>",
  action in [Action::"project.read", Action::"attested.query"],
  resource is Resource
)
when {
  context.purpose_of_use == "emergency-treatment" &&
  context.break_glass_session_id != null &&
  context.break_glass_session_id has "valid_until" &&
  context.break_glass_session_id.valid_until > context.request_time &&
  resource.entity_type == "PatientEligibility"
}
advice {
  alert: "break-glass-review-required",
  alert_target: "audit-officer@grantor"
};
```

The `advice` clause is Cedar 3.2 feature: emits a side-channel signal that triggers the audit-officer
review workflow without blocking the Permit decision.

## 5. Audit emission

Every break-glass invocation emits a sequence of audit-chain events (bilateral):
1. `break-glass-session-opened` — at invocation, captures full attestation + legal instrument.
2. `break-glass-read` — per actual data read under the session.
3. `break-glass-session-closed` — at expiry or explicit close.

All sealed bilaterally. Audit-officer must review session-closed event within 24h (alert workflow
fires at 12h).

## 6. Limits

- Max 24h session duration (extension requires re-attestation).
- Max 1000 reads per session (above triggers second-tier review).
- Max 5 break-glass sessions per agreement per year (above triggers compliance committee review).
- No break-glass on revoked agreements (revocation is final).

## 7. Audit-officer review workflow

Per `runbooks/consent-forgery-detected.md` (alternate use):
1. Audit-officer receives notification on session open.
2. Reviews attestation + legal-instrument-ref.
3. Validates necessity within 24h.
4. If invalid: emit `break-glass-disapproved` event; escalate to legal + privacy officer; notify data
   subject if PII involved (within 72h per GDPR Art. 33 if breach).
5. If valid: emit `break-glass-approved` event; close case.

## 8. Self-revocation by data subject

For B2C agreements:
- Data subject may invalidate any break-glass session on their data via self-revoke API.
- Triggers immediate session closure + audit emission + privacy-officer alert.

## 9. Compliance reporting

Quarterly:
- All break-glass sessions enumerated by purpose + pack + grantor/grantee tenant.
- Approved/disapproved ratio.
- Mean session duration + read count.
- Outliers flagged for committee review.

Generated by `consent_graph_break_glass_quarterly_report_worker`; sealed in audit-chain; retained 10y.

## 10. UI

Break-glass invocation UI (in healthcare or banking compliance console):
- Required fields: purpose, attestation text (≥200 chars), legal-instrument-ref if applicable,
  expiry.
- Two-person rule UI: counter-signer notification + 30min countdown.
- Active session monitor: live read count + remaining time.
- One-click close.

## 11. Cross-checks

- Break-glass session activity correlates with corresponding incident/case in incident-response
  system (cross-ref via case-id).
- Anomaly detection: clusters of break-glass invocations on same agreement trigger investigation.

## 12. Risks

- **R**: Break-glass abused as routine workflow.
  **M**: Limits (§6) + audit-officer review + quarterly outlier reporting + compliance committee
  involvement.
- **R**: Attestation perjury.
  **M**: Attestation HSM-signed by principal's identity key; non-repudiable; legal/disciplinary
  consequence + may be evidence in litigation.
- **R**: Cedar advice clause causes false-positive alerts.
  **M**: Alert routing tuned; audit-officer can mark as routine; baseline established post-launch.

## 13. PHASE-02 follow-ups

- Geographic restriction on break-glass (purpose-of-use must occur in grantor region).
- ML anomaly detection on break-glass patterns.
