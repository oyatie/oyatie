# ADR-AN-003: Analytics tenant isolation uses row policy, database tenancy, and Cedar gates

## Context

- The named architectural pressure is `analytics-scale-without-cross-tenant-leakage`.
- Analytics serves tenant dashboards, internal operations dashboards, billing reports, and compliance exports.
- ADR-0244 makes tenant_id a universal scoping primitive.
- ADR-0243 makes Cedar the universal authorization gate.
- ADR-0193 places analytics on ClickHouse and cold-tier object storage.
- Prior incident class `missing-tenant-predicate-dashboard` returned rows from another tenant.
- Prior incident class `fleet-table-tenant-id-null` inserted operational rows without tenant scope.
- Prior incident class `ad-hoc-sql-cross-tenant` bypassed API-level filters.
- Prior incident class `materialized-view-lost-tenant-id` aggregated across tenants by accident.
- Analytics rows may contain personal data, employment data, billing data, audit events, and sensitive categories.
- Relevant controls include GDPR Art. 5(1)(f), GDPR Art. 32, HIPAA §164.312(a)(1), SOC 2 CC6.1, ISO/IEC 27001 A.8.3, and KR PIPA Art. 29.
- The query engine cannot rely only on application filters.
- The database must enforce tenant boundaries.
- The API must enforce Cedar boundaries.
- The query planner must preserve tenant_id through materialized views.
- Fleet-internal dashboards need separate resources and separate principals.
- Break-glass reads need paired approval and audit-chain evidence.
- Tenant exports need complete but tenant-scoped data.
- Shared operational metrics need explicit de-identification or fleet-internal classification.
- Isolation must be testable in generated DDL and query fixtures.
- Isolation must work with ClickHouse row policies.
- Isolation must not degrade normal dashboards beyond SLO.
- The implementation must be buildable from this ADR.

## Decision

- We choose `defense-in-depth tenant isolation`.
- The named pattern is `database row policy plus Cedar gate plus tenant-bound query context`.
- Every tenant table includes `tenant_id`.
- Every tenant table includes `pack_id`.
- Every tenant table includes `data_class`.
- Every tenant dashboard query carries `tenant_id` in request context.
- Every tenant dashboard query passes Cedar before SQL execution.
- Every tenant dashboard query sets ClickHouse setting `oyatie_tenant_id`.
- ClickHouse row policies compare row `tenant_id` to `getSetting('oyatie_tenant_id')`.
- ClickHouse row policies deny when setting is missing.
- Fleet-internal tables use database `fleet_internal`.
- Fleet-internal tables require separate Cedar action.
- Fleet-internal tables must not contain raw tenant personal data unless classified.
- Materialized views must preserve `tenant_id`.
- Materialized views must preserve `pack_id`.
- Materialized views must preserve `data_class`.
- Aggregates may hash tenant ids only for fleet-internal views.
- Tenant id cannot be nullable.
- Pack id cannot be nullable.
- Query endpoints must not accept raw SQL from tenants.
- Query templates are registered and versioned.
- Break-glass access requires paired principals.
- Break-glass access emits audit-chain event before data return.
- Exports are generated by workers, not direct SQL console.
- SQL console access is disabled in production for tenant data.
- Cedar action `analytics.query.tenant_read` gates tenant dashboard reads.
- Cedar action `analytics.query.fleet_read` gates fleet dashboards.
- Cedar action `analytics.query.export` gates exports.
- Cedar action `analytics.query.break_glass` gates emergency reads.
- Cedar action `analytics.query.template_register` gates query-template registration.
- Row policy failure is a Sev-1 event.
- Missing tenant_id in generated SQL blocks CI.

## Alternatives Considered

### Application-only tenant filters

- Pro: easiest to implement.
- Pro: no ClickHouse row-policy complexity.
- Pro: fewer database settings.
- Con: one missing predicate leaks data.
- Con: ad-hoc SQL bypasses filters.
- Con: materialized views can drop tenant_id silently.
- Con: fails defense-in-depth requirement.
- Tradeoff: developer speed but unacceptable leakage risk.
- Rejected.

### Separate ClickHouse cluster per tenant

- Pro: strongest physical isolation.
- Pro: simple row policies.
- Pro: noisy tenant isolation.
- Con: cost explodes for small tenants.
- Con: operational fleet becomes unmanageable.
- Con: materialized view deployment scales poorly.
- Con: not needed for all tiers.
- Tradeoff: strong isolation but poor unit economics.
- Rejected.

### Separate database per tenant in shared ClickHouse cluster

- Pro: clearer namespace isolation.
- Pro: tenant exports are simpler.
- Pro: accidental joins are harder.
- Con: high tenant count creates DDL churn.
- Con: cross-tenant fleet aggregates become complicated.
- Con: does not eliminate need for Cedar.
- Tradeoff: moderate isolation but operational friction.
- Partial accept: high-risk enterprise tenants may get dedicated databases by pack overlay.

### PostgreSQL RLS instead of ClickHouse row policies

- Pro: mature RLS semantics.
- Pro: familiar enforcement model.
- Pro: strong transactional controls.
- Con: query performance cannot meet analytics SLOs.
- Con: materialized view pipeline changes.
- Con: cost is higher for high-volume rollups.
- Tradeoff: stronger OLTP controls but wrong warehouse engine.
- Rejected.

### Static per-tenant generated SQL views

- Pro: query text is simple.
- Pro: tenant filters are built into view definitions.
- Pro: no runtime setting required.
- Con: view count scales with tenant count.
- Con: schema changes are expensive.
- Con: stale views can persist after tenant moves packs.
- Tradeoff: simple query path but poor operability.
- Rejected.

## Consequences

- Positive: tenant isolation is enforced below application code.
- Positive: Cedar and ClickHouse both have to agree.
- Positive: missing tenant context fails closed.
- Positive: materialized-view tenant preservation becomes testable.
- Positive: break-glass has explicit evidence.
- Negative: every query path must set ClickHouse context.
- Negative: row policies add operational complexity.
- Negative: fleet-internal analytics need explicit classification.
- Negative: testing must cover generated SQL, DDL, and Cedar.
- Neutral: dedicated tenant databases remain a pack overlay for high-risk tenants.
- Neutral: future warehouse replacement must preserve same isolation contract.
- Follow-up work: implement query-template registry.
- Follow-up work: add ClickHouse row-policy fixture suite.
- Follow-up work: add break-glass analytics runbook.
- Follow-up work: add tenant-id preservation linter for MVs.

## Implementation Notes

- Data shape `AnalyticsQueryContextV1` contains `principal_id`.
- Data shape `AnalyticsQueryContextV1` contains `tenant_id`.
- Data shape `AnalyticsQueryContextV1` contains `pack_id`.
- Data shape `AnalyticsQueryContextV1` contains `audience_type`.
- Data shape `AnalyticsQueryContextV1` contains `data_class`.
- Data shape `AnalyticsQueryContextV1` contains `query_template_id`.
- Data shape `AnalyticsQueryContextV1` contains `purpose_id`.
- Data shape `AnalyticsQueryContextV1` contains `break_glass_case_id`.
- Data shape `AnalyticsQueryTemplateV1` contains `template_id`.
- Data shape `AnalyticsQueryTemplateV1` contains `template_sql`.
- Data shape `AnalyticsQueryTemplateV1` contains `required_columns`.
- Data shape `AnalyticsQueryTemplateV1` contains `allowed_workload_classes`.
- Data shape `AnalyticsQueryTemplateV1` contains `max_bytes_read`.
- Data shape `AnalyticsQueryTemplateV1` contains `cedar_action`.
- Data shape `AnalyticsQueryAuditV1` contains `query_id`.
- Data shape `AnalyticsQueryAuditV1` contains `row_count`.
- Data shape `AnalyticsQueryAuditV1` contains `bytes_read`.
- Data shape `AnalyticsQueryAuditV1` contains `tenant_id_hash`.
- ClickHouse setting `oyatie_tenant_id` is required.
- ClickHouse setting `oyatie_pack_id` is required.
- ClickHouse row policy is `USING tenant_id = getSetting('oyatie_tenant_id')`.
- ClickHouse row policy includes `pack_id = getSetting('oyatie_pack_id')`.
- ClickHouse row policy is attached to role `tenant_dashboard`.
- Fleet role `fleet_internal_reader` has separate table grants.
- API endpoint `POST /v1/query/{template_id}` runs a tenant-scoped query.
- API endpoint `POST /v1/export/{template_id}` starts a governed export.
- API endpoint `POST /v1/internal/query-templates` registers templates.
- API endpoint `POST /v1/internal/break-glass/query` runs emergency query.
- API endpoint `GET /v1/internal/query-audit/{query_id}` returns audit evidence.
- Query engine uses prepared templates only.
- Query engine rejects semicolon-separated SQL.
- Query engine rejects templates without tenant predicate marker.
- Query engine rejects templates that omit `tenant_id` from MV outputs.
- Cedar principal for tenant read is `Oyatie::Principal::User`.
- Cedar principal for fleet read is `Oyatie::Principal::Service("analytics-fleet-dashboard")`.
- Cedar principal for export is `Oyatie::Principal::Service("analytics-export-worker")`.
- Cedar principal for break-glass is paired `Oyatie::Principal::Pair`.
- Cedar resource for tenant read is `Analytics::TenantDataset`.
- Cedar resource for fleet read is `Analytics::FleetDataset`.
- Example permit: principal `User("usr_01HY")`, action `analytics.query.tenant_read`, resource `Analytics::TenantDataset::"tenant_01.audit_events"`, context `{tenant_id:"tenant_01", pack_id:"gdpr-eu", template_id:"tpl_dashboard_errors_v1"}`.
- Example forbid: same action with context `{tenant_id:"tenant_02", row_tenant_id:"tenant_01"}`.
- Example permit: principal `Pair("usr_oncall","usr_privacy")`, action `analytics.query.break_glass`, resource `Analytics::TenantDataset::"tenant_01.audit_events"`, context `{case_id:"bg_01HY", expires_minutes:30}`.
- Example forbid: fleet reader action with context `{data_class:"PERSONAL_DATA_RAW"}`.
- SLO `analytics-tenant-query.openslo.yaml` sets tenant dashboard p95 <= 800 ms.
- SLO `analytics-export-start.openslo.yaml` sets export start p99 <= 5 seconds.
- SLO `analytics-break-glass-evidence.openslo.yaml` sets audit event p99 <= 1 second before query.
- Failure mode `tenant_setting_missing` fails query closed.
- Failure mode `row_policy_disabled` opens Sev-1 and blocks deploy.
- Failure mode `mv_dropped_tenant_id` blocks deploy.
- Failure mode `fleet_query_raw_personal_data` blocks query.
- Failure mode `break_glass_unpaired` returns 403.

## Verification

- Test `tenant_query_requires_tenant_id_setting` verifies fail-closed.
- Test `row_policy_filters_other_tenant` verifies ClickHouse policy.
- Test `pack_policy_filters_other_pack` verifies pack setting.
- Test `tenant_template_rejects_missing_tenant_marker` verifies SQL linter.
- Test `mv_preserves_tenant_id` verifies MV output.
- Test `mv_preserves_pack_id` verifies MV output.
- Test `fleet_reader_cannot_read_raw_personal_data` verifies Cedar.
- Test `break_glass_requires_pair` verifies paired principal.
- Test `break_glass_emits_audit_before_query` verifies ordering.
- Test `tenant_export_uses_worker_not_console` verifies export path.
- Metric `oya_analytics_cross_tenant_denied_total` tracks denied attempts.
- Metric `oya_analytics_row_policy_missing_total` must remain zero.
- Metric `oya_analytics_query_without_tenant_context_total` must remain zero.
- Metric `oya_analytics_tenant_query_ms` must meet p95 <= 800 ms.
- Dashboard `analytics-tenant-isolation.json` shows denies, policy state, and query context failures.
- Dashboard `analytics-break-glass.json` shows paired approvals and expirations.
- Dashboard `analytics-query-templates.json` shows template versions and owners.
- CI check `analytics-row-policy-ddl` validates policies on every tenant table.
- CI check `analytics-tenant-id-preserved-in-mv` validates materialized views.
- CI check `analytics-cedar-query-actions` validates permits and forbids.
- CI check `analytics-no-production-sql-console` validates IaC.
- Security test injects missing tenant predicate and expects denial.
- Security test runs cross-tenant template fixture and expects zero rows.
- Annual audit exports row-policy evidence bundle.
