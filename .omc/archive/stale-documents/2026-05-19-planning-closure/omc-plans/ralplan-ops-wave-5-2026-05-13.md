### Scenario 1 — Cedar fragment misconfiguration leaks cross-tenant data via tenant-mgmt

**Outage shape:** Wave 5 introduces 11 new Cedar fragments. A subtle policy error in `ops-tenant-private.cedar` (e.g., forgetting to bind `principal.tenant_id == resource.tenant_id`) allows a tenant-admin from tenant A to view tenant B's user list via `/workspace/user-mgmt?tenant=B` query param injection.

  1. **(a) Signature verify** — reject if signature invalid (tampering at TLS or token signing key).

FOR UPDATE`. Within the locked transaction: **(c.i.a) [post-execution retry]** if `row.consumed_at IS NOT NULL` AND `row.outcome IS NOT NULL` AND `row.idempotency_key == request.idempotency_key`, **return cached `outcome`** (legitimate retry; common case). **(c.i.b) [in-flight, lease valid — architect r5 fix]** if `row.consumed_at IS NOT NULL` AND `row.outcome IS NULL` AND `row.in_progress_at IS NOT NULL` AND `row.in_progress_expires_at > NOW()` AND `row.idempotency_key == request.idempotency_key`, the winner is mid-execution within valid lease → return `Err(RollbackInProgress { retry_after: 5s })` (HTTP 409 Conflict with `Retry-After: 5` header). Client retries idempotently; the retry eventually hits (c.i.a) once the winner OR reconciler persists outcome at step (e)/(f). **NEVER return null/nonexistent cached outcome.** **(c.i.c) [in-flight, lease expired — critic r2 fix 1 crash-recovery]** if `row.consumed_at IS NOT NULL` AND `row.outcome IS NULL` AND `row.in_progress_at IS NOT NULL` AND `row.in_progress_expires_at <= NOW()` AND `row.idempotency_key == request.idempotency_key`, the original winner likely crashed mid-execute → **MUST NOT blindly re-execute**; instead trigger synchronous reconciliation by `operation_id`: invoke `WorkflowBridgePort::query_operation_state(row.operation_id)` to determine terminal state. If reconciler succeeds → atomically write outcome at (f) + return cached outcome. If reconciler reports operation still running (lease will be re-extended) → return 409 with `Retry-After: 10s`. If reconciler reports Unknown/Lost (workflow engine has no record) → escalate to durable reconciler worker (out-of-band; (f) below) and return 409 with `Retry-After: 30s` — caller eventually retries into (c.i.a) when reconciler completes. **Never duplicate execute; fencing via `attempt` increment prevents stale executor write-through.** **(c.ii)** if `row.consumed_at IS NOT NULL` AND `row.idempotency_key != request.idempotency_key`, return `Err(TokenAlreadyUsed)` (genuine replay with different idempotency_key). **(c.iii) [winner path]** otherwise (`row.consumed_at IS NULL`): generate `operation_id = uuid_v7()`, set `current_attempt = row.attempt + 1`; mark `consumed_at = NOW()`, `idempotency_key = request.idempotency_key`, `in_progress_at = NOW()`, `in_progress_expires_at = NOW() + interval '5 minutes'`, `operation_id = $operation_id`, `attempt = $current_attempt`, `outcome = NULL`, COMMIT — then proceed to step (d) Execute, passing `operation_id` + `current_attempt` as fencing token.

  6. **(e) Persist outcome (atomic with in_progress clear + fencing; architect r5 fix + critic r2 fix 1 fencing):** UPDATE `RollbackTokenStore SET outcome = $outcome, in_progress_at = NULL, in_progress_expires_at = NULL WHERE token = $token AND attempt = $current_attempt` in a single transaction. **Fencing predicate `attempt = $current_attempt` ensures stale executor (whose lease expired and was reconciled by (f)) CANNOT overwrite reconciler's terminal outcome** — UPDATE no-op silently if attempt was bumped by reconciler. This atomic write is what releases concurrent (c.i.b) waiters to retry into (c.i.a). Then return the outcome to the caller (or NoOpDueToFencing if reconciler already wrote terminal outcome).

For each row: acquire FOR UPDATE, increment `attempt`, query `WorkflowBridgePort::query_operation_state(row.operation_id)`. Decision matrix: (i) **Succeeded** → atomically write `outcome = {status: Success, details: ...}, in_progress_at = NULL, in_progress_expires_at = NULL` + emit audit-chain row. (ii) **Failed** → atomically write `outcome = {status: Failed, error: ...}, in_progress_at = NULL, in_progress_expires_at = NULL` + emit audit-chain row. (iii) **Running** (workflow still executing; stale lease was misread) → extend lease: `in_progress_expires_at = NOW() + interval '5 minutes'`, commit, re-check on next tick. (iv) **Unknown/Lost** (workflow engine has no record of operation_id — implies winner crashed before workflow accepted the request) → atomically write `outcome = {status: Lost, reason: WorkflowOperationNotFound, recoverable: true}, in_progress_at = NULL, in_progress_expires_at = NULL` + emit audit-chain row + emit ALARM (operator-actionable; client retry with new idempotency_key permitted since rollback did NOT execute). Worker MUST emit OTel SpanKind::Internal trace per reconcile decision. Worker is liveness-critical: at least 2 replicas per cell with lease-based leader election (Postgres advisory lock or Redis Redlock); no single point of failure. **No double execute under any sequence: workflow engine itself is idempotent on `operation_id`; reconciler only queries state, never re-submits.**

  **Replay attack model rejected:**
  - **New idempotency_key + same token** → fails at step (b) claims-match (idempotency_key is in signed claims; mismatch).
  - **Same idempotency_key + same token after execution** → returns cached outcome at step (b1); this is idempotent retry, not replay.
  - **Same token + tampered other field (cell_id, version, etc.)** → fails at step (b) claims-match.
  - **Forged token** → fails at step (a) signature verify.
  - **Tampered signature** → fails at step (a).
  - **Race condition — pre-execution** (two concurrent requests with same token + same idempotency_key arrive before either consumes the row) → FOR UPDATE serializes; winner takes (c.iii); loser hits (c.i.b) "in-flight" → receives `Err(RollbackInProgress { retry_after: 5s })` HTTP 409 → idempotent client retry hits (c.i.a) once winner persists outcome at step (e) (architect r5 in-flight close).
  - **Race condition — outcome NOT yet persisted** (loser's (c.i) check fires AFTER winner's (c.iii) commit but BEFORE winner's (e) outcome-persist; lease still valid) → (c.i.b) sees `consumed_at IS NOT NULL` AND `outcome IS NULL` AND `in_progress_at IS NOT NULL` AND `in_progress_expires_at > NOW()` → returns 409 RollbackInProgress with Retry-After 5s; client retries; NEVER returns null cached outcome (architect r5 fix).
  - **Crash recovery — winner crashes after (c.iii) consume commit, before (e) outcome persist (critic r2 fix 1+2+3 crash-recovery):** scenario sequence: (1) winner commits (c.iii) with `operation_id=O1`, `in_progress_expires_at = T+5min`, `attempt=1`; (2) winner submits workflow request via WorkflowBridgePort (workflow engine accepts and records `operation_id=O1`); (3) winner CRASHES before (e) outcome persist; (4) at T+5min, lease expires; (5) durable reconciler worker (f) picks up the row via `in_progress_expires_at <= NOW()`, increments `attempt → 2`, calls `query_operation_state(O1)`; (6) workflow engine returns Succeeded/Failed/Running/Unknown deterministically (workflow engine is idempotent on `operation_id`); (7) reconciler writes terminal outcome atomically + clears `in_progress_at`. Meanwhile, same-idempotency_key retries before reconciler runs hit (c.i.c) [in-flight, lease expired] → trigger synchronous reconciler-by-`operation_id` lookup → return cached outcome OR 409 with longer Retry-After. After reconciler completes, retries hit (c.i.a) → return cached outcome. **Bounded recovery guarantee: ≤5min lease + 30s reconciler tick = ≤5.5min max staleness window before terminal outcome visible to clients.** **No double rollback guarantee:** workflow engine is idempotent on `operation_id` (won't accept duplicate operation_id submission); reconciler only QUERIES state, never re-submits; fencing predicate `attempt = $current_attempt` in (e) prevents stale crashed-executor from clobbering reconciler's terminal write if it somehow resumes mid-reconcile. **No 4xx-loop guarantee:** (c.i.c) routes to reconciler synchronously OR returns 409 with bounded Retry-After (max 30s); reconciler runs ≤30s tick; client retry into (c.i.a) returns within bounded window. **Lost/Unknown handling:** if workflow engine has no record of `operation_id` (winner crashed before workflow accepted), reconciler writes `outcome = {status: Lost, recoverable: true}` + emits ALARM; subsequent retries with same idempotency_key return that Lost outcome; operator must issue new idempotency_key to re-attempt rollback.

- **Idempotency:** `idempotency_key` (UUID per attempt; bound to confirmation_token per fix 2). The atomic sequence above guarantees: (i) legitimate retry with same idempotency_key returns cached outcome; (ii) any new idempotency_key or tampered field fails before re-execution. **Process-local nonce caches are forbidden** per architect r3 fix 1 — only the shared `RollbackTokenStore` is authoritative.

Composite index `(state, expires_at)` for reconciler scans; index on `target_token` for lookup.
  - Table `ops_approval_votes(ticket_id UUID NOT NULL REFERENCES ops_approval_ticket_store(ticket_id), voter_id PrincipalId NOT NULL, decision ApprovalDecision NOT NULL /* Approve | Reject */, voted_at TIMESTAMPTZ NOT NULL, PRIMARY KEY (ticket_id, voter_id))`. **PRIMARY KEY (ticket_id, voter_id) enforces unique vote per principal per ticket** — Postgres rejects double-vote with `Err(VoteAlreadyRecorded)`.
- **Threshold-flip idempotency (architect r7 fix 3b — execute-once contract under N concurrent votes):** `vote_approval(ticket_id, principal, decision)` transaction sequence (`SELECT FOR UPDATE` on `ops_approval_ticket_store` row): (i) Cedar pre-check `ops-multi-party-approval-vote.cedar` (see below); (ii) INSERT INTO `ops_approval_votes` (fails on PRIMARY KEY conflict → `Err(VoteAlreadyRecorded)`); (iii) IF `decision == Reject`: UPDATE ticket SET `state = Rejected` (race-safe under FOR UPDATE); RETURN; (iv) UPDATE ticket SET `current_approval_count = current_approval_count + 1`; (v) IF `current_approval_count >= required_approvals AND state == Pending AND threshold_flipped_at IS NULL`: atomically UPDATE ticket SET `state = Approved, threshold_flipped_at = NOW(), execute_operation_id = uuid_v7()` (this UPDATE is THE ONCE-AND-ONLY transition that allocates `execute_operation_id`; subsequent concurrent votes find `threshold_flipped_at IS NOT NULL` and skip allocation); (vi) INSERT row into outbox `ops_approval_execute_outbox(ticket_id, execute_operation_id, target_token, created_at)` for at-least-once delivery to executor; COMMIT. **Execute path consumes outbox row + calls `execute_rollback`/etc. with the ticket's `execute_operation_id` — workflow engine's idempotent-on-operation_id contract guarantees execute-once even under outbox-retry.** Three concurrent votes after threshold-2 reached produce: vote#1 flips threshold + outbox row; vote#2 sees `threshold_flipped_at NOT NULL`, just increments count to 3 (no outbox row); vote#3 same. Single execute.
- **Split Cedar predicates (architect r7 fix 3c — vote authorization vs execute authorization decoupled):** `cedar-policies/ops/ops-multi-party-approval.cedar` contains TWO permit rules:
  - **Rule 1 (vote authorization):** `permit(principal, action == VoteApproval, resource: ApprovalTicket) when { principal.role in [InternalAdmin, ...action-type-specific-roles] && principal != resource.requester_id && !(principal in resource.approvers_so_far) && resource.state == Pending && resource.expires_at > context.now };` — enforces separation-of-duties at vote (requester cannot self-approve; voter cannot double-vote; ticket still Pending and unexpired).
  - **Rule 2 (execute authorization):** `permit(principal, action == ExecuteApprovedAction, resource: ApprovalTicket) when { resource.state == Approved && resource.execute_operation_id != null && principal.role allows resource.action_type };` — execute permission decoupled from vote permission; only granted once threshold flipped. **Note (separation):** the executor principal may equal `resource.requester_id` (requester may execute after approval) but the executor MUST have the role-binding for the action_type (e.g., rollback execute requires InternalAdmin role).
- **WBP methods (4th + 5th port method extensions; v9):** `request_approval(req: ApprovalRequest) -> Result<ApprovalTicket>` creates Pending row in `ops_approval_ticket_store` with `target_token` referencing the prepared write-action-token (consumed only after Approved+executed); emits audit "pending"; required_approvals defaulted per action_type per `docs/standards/multi-party-approval-contract.md`. `vote_approval(ticket_id, principal, decision) -> Result<ApprovalState>` performs the 6-step transaction above.
- **ApprovalRequest defaults per action_type:**
  - `Rollback`: 2-of-N InternalAdmin OR 1-of-N InternalAdmin + 1-of-N InternalSre (Sev-2 auto-rollback bypass allowed per ADR-0040 metric-gated path; manual rollback requires N≥2 humans).
  - `TenantAdminElevation` + `CrossTenantGrant`: 2-of-N InternalAdmin (no Foundry/Sre).
  - `UserRoleChange` to InternalAdmin: 2-of-N InternalAdmin (separation enforced via Cedar Rule 1).
  - Other write actions (`TenantConfigSave`, `SsoConfigUpdate`, `TenantSettingsUpdate`, `UserInvite`, `UserDeactivate`) NOT subject to multi-party approval by default (configurable per-tenant via tenant policy).
- **Audit-chain integration:** each vote emits row `(ticket_id, voter_id, decision, ts, current_count_after)`; threshold-flip emits row `(ticket_id, state=Approved, execute_operation_id, ts)`; execute emits row `(ticket_id, execute_operation_id, outcome, ts)`; final state emits row on Rejected/Timeout/Executed.
- **`lean-a-multi-party-approval` test row (folded into `lean-a-rollback-authorization` lane scope):** asserts single-party action fails 403 at Cedar Rule 2 (state not Approved); 2-party vote-then-execute succeeds; requester self-vote fails at Cedar Rule 1 (`principal != requester_id`); double-vote fails at Postgres PRIMARY KEY constraint; approval timeout (24h default) emits row + sets state=Timeout; **3-concurrent-vote race test** asserts exactly 1 outbox row + 1 execute call per Scenario 7 threshold-flip idempotency contract.

**Recovery:** Manual override only via emergency-break-glass workflow (NEW; documented in `docs/runbooks/multi-party-approval-break-glass.md`) requiring N-of-M (N≥3) InternalAdmin votes + ticket-of-record; emits ICM + audit row + post-incident review.
