# Generated-Artifact Policy Determination — Stop Committing Pure-Derivation Faces

Status: Determination (adversarially pressure-tested against the live review worktree
`/private/tmp/wt-repo-review` @ HEAD `d6e115d56`). Verdict on the input recommendation:
**NEEDS_REVISION** — the *direction* is sound, but the recommendation's load-bearing
"CRITICAL CORRECTION" is itself false in this tree, and two concrete gate-mechanics
prerequisites are missing. This determination corrects them.

door: one-way (de-committing is reversible per-face during the strangler, but the policy
class — "pure-derivation faces are not contributor merge surfaces" — is a one-way commitment
once the no-tracked-generated guard gate lands).

---

## 1. Problem

Seven generated faces under
`cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app/` are git-tracked despite the
repo-wide `.gitignore:63` `**/*.generated.json` rule (they are force-tracked). Verified
sizes/contents in this tree:

| Face | Size | Content | Human bits |
|---|---|---|---|
| `accounting-registry.generated.json` | 11.6 MB / 18,499 rows | git ls-files × OWNERS × ADR front-matter × specs | none |
| `gate-baseline.generated.json` | 3.46 MB | enumerated currently-failing keys | none (modes/frozen_empty are policy DATA, see below) |
| `scm-facts.generated.json` | 1.2 MB | sorted tracked paths + blob SHAs (STABLE half only; volatile half already de-committed by ADR-0552) | none |
| `decision-crosswalk.generated.json` | 80 KB | projection of ADR front-matter/specs | none |
| `enforcement-inventory.generated.json` | 27 KB | projection of gates/** + oya-ci.toml | none |
| `enforcement-liveness.generated.json` | 6 KB | projection of hook wiring | none |
| `ttl-policy.generated.json` | 1.6 KB | expansion of `src/ttl-policy.json` | none |

Every one is a pure deterministic function of (tracked tree × small committed policy). The
cache-to-decision ratio is ~1000:1. Because the settle protocol MANDATES regenerating faces
in any PR that touches a non-generated path, and the freshness gate MANDATES
committed==regenerated byte parity, every PR rewrites these multi-MB blobs — making them an
all-pairs merge-conflict surface that single-threads the merge queue. The same byte-parity
mandate is the exact mechanism that laundered new debt past the firewall (PR #670) and that
red-gated three post-merge dev runs (FRIC-1781234047), motivating ADR-0551 and ADR-0552.

The question: can these faces be de-committed and derived on demand without losing any gate
invariant (malicious-producer detection, merge-base baseline, born-accounting
enforceability, reproducibility/audit), and without a flag-day where gates go dark?

---

## 2. What the input recommendation got RIGHT (kept)

- **De-commit direction is correct and unanimous across all five angles.** The faces are
  pure derivations; committing them is the cause of the conflict/laundering/asymmetry class.
- **Keep-committed slim human set is correct**: `gate-baseline.signoff.json` (the one-way
  door — verified human-edited, NOT producer-generated, keyed by (gate,code,key)),
  `ratchet-policy.json` (~1.5 KB policy DATA), `registry/generated-artifact-control-plane.json`
  (the control surface), the producer's `src/ttl-policy.json` / `src/gate-disposition.json`
  policy sources (commit the SOURCE not the expansion), and the upstream SOURCES
  (OWNERS, ADR front-matter, oya-ci.toml, specs/**). `specs/reorg/move-manifest.generated.json`
  stays committed (already special-cased via `.gitignore:78` negation + control-plane
  declared-must-be-tracked).
- **Determinism is the load-bearing precondition** (STEP 0 regen-twice canary) — correct and
  essential.
- **Strangler ordering is mostly correct**: flip the integrity predicate BEFORE de-committing,
  de-commit smallest-first, run the full gate fleet between each.
- **The merge-base materialization IS the right frozen-reference mechanism** — and (correcting
  the recommendation) it ALREADY EXISTS here.

## 3. Where the recommendation BREAKS (holes found by verification)

### HOLE 1 (fatal to the recommendation's premise) — the "CRITICAL CORRECTION" is false in this tree
The recommendation asserts the merge-base snapshot `gate-baseline.merge-base.generated.json`
does NOT exist, has zero code references, and that ADR-0551/0552 do not exist — concluding
the firewall byte-compares the committed face and the merge-base materialization "must be
BUILT as a prerequisite." **All of that is wrong in `/private/tmp/wt-repo-review`:**

- The file is declared, code-referenced (`firewall/src/lib.rs:113` `FROZEN_SNAPSHOT_PATH`,
  `main.rs:82`, scm-facts emitter `main.rs:1418`), and explicitly gitignored
  (`.gitignore:109`). It is materialized by the scm-facts emitter (the single git boundary).
- `docs/decisions/ADR-0551-merge-base-frozen-baseline-ratchet.md` and
  `docs/decisions/ADR-0552-stable-volatile-scm-facts-split.md` both exist (status Proposed).
- The firewall HAS a `main.rs` (the recommendation says "pure lib, no main.rs"). The
  production gate harness is the buck2 `rust_test` `oya-cloud-ci-firewall-app-gate`
  (`tests/firewall.rs`), which is HERMETIC: it loads the frozen reference from the
  out-of-graph merge-base snapshot (`load_frozen_baseline`, never the committed face) and
  computes the *proposed* baseline by EXEC-ing the buck2-built producer
  (`regenerate_baseline` via `OYA_CI_PRODUCER_BIN`), NOT by reading the committed
  `gate-baseline.generated.json`.

Consequence: **the firewall does not depend on any committed accounting-registry face.** The
recommendation's STEP 1 ("build the missing materialization") and STEP 2 ("repoint the
firewall reader") for the firewall are already DONE. This is the canonical-checkout-staleness
trap (MEMORY) the recommendation warned about — and then fell into.

### HOLE 2 — the real committed-byte consumer is FRESHNESS, not the firewall
The recommendation conflated the firewall (merge-base based) with the gate that actually
reads the committed bytes. Verified: `oya-cloud-ci-freshness-app/src/lib.rs`:
- `read_committed_generated_faces` (line 703) reads EVERY `*.generated.json` in `FACES_DIR`
  (`cloud/cloud-ci/gates/oya-cloud-ci-accounting-registry-app`, const line 19).
- `evaluate_face_freshness` (line 623) byte-compares committed vs buck2-regenerated and emits
  `GeneratedFaceStale` on: "committed bytes differ from regenerated" / "regeneration did not
  produce this committed face" / **"regeneration produced an uncommitted generated face"
  (line 654)**.

The third clause is the genuine blocker: de-committing any face while regeneration still emits
it → freshness goes RED. So freshness's predicate MUST be flipped from
committed==regenerated to regenerated-internally-valid+deterministic BEFORE the de-commit, and
the de-committed faces must not be left in `FACES_DIR` as an uncommitted file that re-triggers
the "uncommitted generated face" clause (or the materialization writes them there and the
predicate ignores absence). The recommendation sequences the flip before de-commit (STEP 3
before STEP 5) — correct — but attributes the predicate to the wrong gates (firewall +
registry-drift) and never names the "uncommitted generated face" clause that is the actual
trap.

### HOLE 3 (missing prerequisite) — the control-plane gate has NO `not-tracked-in-git` exemption
The recommendation's STEP 5(c) says: set the manifest entry to
`materialization_mode=main-branch-materialized / merge_policy=not-tracked-in-git` "so the
control-plane gate stays GREEN." Verified false: in
`oya-cloud-ci-generated-artifact-control-plane-app/src/lib.rs`, `evaluate_keyed` (line 997)
emits `generated_artifact_declared_path_not_tracked` (line 1013) for ANY declared path absent
from scm-facts `tracked_paths` — with NO exemption for `not-tracked-in-git`. The enum value
`not-tracked-in-git` exists in `MATERIALIZATION_MODES` (line 51) but is used by zero manifest
entries and is wired to nothing. Symmetrically, `generated_artifact_tracked_generated_output_not_declared`
(line 1009) needs the path to remain declared. So de-committing a face would make the gate
fire `declared_path_not_tracked` → RED. **The control-plane gate must first be taught that a
`materialization_mode == "not-tracked-in-git"` (or `main-branch-materialized`) declared path
is EXEMPT from the declared-path-must-be-tracked predicate.** This is a code change that must
land BEFORE STEP 5, not a DATA edit during it.

Also note: `merge_policy: not-tracked-in-git` is not a valid `merge_policy` value
(`not-tracked-in-git` is a `materialization_mode`); the scm-facts class requires
`merge_policy == "controller-owned-main-materialization"` (lib.rs:1045). The recommendation
mixed the field taxonomy.

### HOLE 4 — scm-facts is the HARDEST de-commit (declared hermetic input to ~20 gates), and is already half-done
The committed `scm-facts.generated.json` is read as a DECLARED INPUT by the producer and by
~20 gate tests (verified: firewall, freshness, registry-drift, total-accounting,
staleness-reaper, control-plane, target-parity, enforcement-liveness, cross-artifact-agreement,
catalog-liveness, register-crate, et al.). The producer reads it to regenerate faces WITHOUT
calling git (the hermeticity contract — `firewall.rs:88`). De-committing scm-facts therefore
requires the materialization to run before EVERY gate lane, and the buck2 `$(location)`/`env`
wiring for every one of those ~20 targets to point at the materialized path. This is far more
invasive than the recommendation's "repoint ~3 readers" and must be the LAST face de-committed
(after a dedicated repoint pass), not merely "second-to-last, smallest-first."

Critically, ADR-0552 ALREADY split scm-facts into a STABLE committed half (paths+SHAs, the
1.2 MB tracked file) and a VOLATILE de-committed half (`scm-volatile-facts.generated.json`,
gitignored `.gitignore:115`). The volatile/history-derived part — the actual squash-merge
churn source — is GONE from the merged surface. The residual stable half churns only when the
tracked file SET changes, which is far less than the recommendation implies. De-committing the
stable half is still desirable (git's object DB already stores the SHAs) but is the lowest-ROI,
highest-blast-radius move, and should be gated behind its own repoint IP.

### HOLE 5 — the materialization entry point is a SHELL script (doctrine conflict)
`infra/ci/materialize-cloud-ci-generated-faces.sh` is a bash script. The recommendation wires
it into presubmit/merge-queue as the steady-state materialization step. Per MEMORY
[shell-and-cli-retirement] and [rust-hooks-scripts-tools], new automation must not ship as
shell; this script is transitional/irreducible-glue (ADR-0523) at best and should be on a
path to a Rust materialization controller (cloud-native, API/CRD-driven per
[cloud-native-k8s-native-ops]) as the end state. The recommendation should explicitly mark
this as transitional, not the destination.

### HOLE 6 — manifest class mislabel
The recommendation claims "two faces are already flagged
`branch-committed-regenerated-until-controller-materialization`, i.e. transitional" and reads
this as evidence the eviction started on the accounting faces. Verified: in this tree the
`branch-committed-regenerated-until-controller-materialization` faces are
`docs/machine-readable/board-sync.generated.json` and `masterplan.generated.json` — NOT the
seven accounting faces (which are `merge-candidate-regenerated`, and scm-facts is
`main-branch-materialized`/`controller-owned-main-materialization`). The eviction precedent the
recommendation cites is in the docs/machine-readable lane, a useful pattern to copy, but the
accounting faces are still fully committed `merge-candidate-regenerated`.

## 4. Multi-angle analysis summary

The five input angles converge: **de-commit the producer-generated faces; keep the slim
human-decision set.** Disagreement is only about keep-committed SCOPE (commit-none vs
baseline-only vs hybrid), never about de-committing the faces. Resolution: **hybrid** —
de-commit all seven producer faces; keep committed the human inputs (signoff door,
ratchet-policy, control-plane manifest, producer policy sources, upstream sources). The
recommendation's resolution is correct; the corrections above are about *execution mechanics
in the real tree*, not about the resolution.

A frozen prior reference a PR cannot regenerate IS required for the ratchet — and it already
exists as the out-of-graph merge-base materialization (ADR-0551). A slim committed "ratchet
datum" as the recommendation proposed is therefore UNNECESSARY in this tree: the per-(gate,code)
`mode`/`frozen_empty` policy already lives in the producer's `src/gate-disposition.json`
(committed source), and the frozen KEYS come from the merge-base snapshot, not a committed
copy. Do NOT introduce a new committed ratchet datum; it would re-create a churning surface
the merge-base mechanism already eliminated.

## 6. Conflict-resolution

- **The merge-conflict problem is largely SOLVED for the de-committed faces by definition**:
  once a face is gitignored and derived, it is never in a PR diff, so it cannot conflict.
- **signoff door** (the one human file needing cross-PR coordination): keyed by (gate,code,key)
  so disjoint sign-offs touch disjoint keys. If concurrent same-key edits become a problem,
  add a SERVER-SIDE structural-union merge driver in the cloud-ci/Tide admission path (hermetic
  pure-Rust object-union, deterministic), and re-validate the union result with the firewall so
  a union can never launder debt. Local `.gitconfig` drivers are advisory here (friction-ledger
  / Cargo.lock precedent — merge authority lives in cloud-ci gates, never invoked by squash/
  Tide). This is the scope of faces-merge-driver issue #125.
- **ratchet-policy / control-plane manifest / producer policy sources**: small, low-churn,
  hand-edited; plain 3-way merge; genuine concurrent policy edits SHOULD serialize.
- **Determinism is the precondition**: today byte-equality-to-committed masks any
  nondeterminism. Before removing any face, add a cross-runner regen-twice-byte-identical
  canary (the producer already emits `source_inputs_digest` + canonical JSON). A
  non-deterministic producer must hard-fail, never silently green.

## 7. Strangler migration (corrected ordering — no flag-day, no dark window)

- **STEP 0 — prove determinism.** Cross-runner regen-twice-byte-identical canary for all seven
  faces + the scm-facts emitter. Must be GREEN before proceeding. Faces stay committed.
- **STEP 1 — confirm, don't build, the merge-base materialization.** It already exists
  (ADR-0551). Verify against origin/dev that this is steady state. Ensure the candidate-tree
  materialization for the other faces exists / is wired in presubmit + merge-queue. Faces stay
  committed.
- **STEP 2 — teach the control-plane gate the `not-tracked-in-git` exemption (NEW, blocking
  prerequisite).** In `evaluate_keyed`, a declared artifact whose `materialization_mode` is
  `not-tracked-in-git` (or `main-branch-materialized`) must be EXEMPT from
  `generated_artifact_declared_path_not_tracked`, AND a path that is no longer tracked must not
  trip `generated_artifact_tracked_generated_output_not_declared`. Add RED/GREEN fixtures. Land
  this while faces are still committed (no-op until a mode flips).
- **STEP 3 — flip freshness from committed==regenerated to regenerated-internally-valid +
  regen-twice-identical.** Change `evaluate_face_freshness` so that (a) for de-commit-class
  faces it does NOT require a committed copy and does NOT fire "uncommitted generated face",
  and (b) it asserts the regenerated face is internally valid + deterministic. Keep the
  committed==regenerated check ONLY for any face still classed committed. Do this WHILE faces
  are committed so nothing is missing. This is the keystone — after it, no gate depends on the
  committed bytes of a de-commit-class face. Run the full fleet; must stay green.
- **STEP 4 — repoint scm-facts readers (prep for STEP 5.7 only).** Repoint the ~20 gates that
  read `scm-facts.generated.json` to the materialized path / a buck2 `$(location)` genrule dep.
  Both copies byte-identical (STEP 0), so green throughout. (Defer the actual scm-facts
  de-commit to its own IP.)
- **STEP 5 — de-commit one face at a time, smallest-first**, in the SAME commit per face:
  (a) `git rm` the committed copy; (b) confirm `**/*.generated.json` now covers it (remove any
  force-add); (c) flip its control-plane manifest entry to `materialization_mode =
  not-tracked-in-git` (now exempt per STEP 2). Order: ttl-policy → enforcement-liveness →
  enforcement-inventory → decision-crosswalk → gate-baseline → accounting-registry → (scm-facts
  LAST, behind STEP 4 + its own IP). After each, run the full fleet (buck2 + freshness +
  affected-set + control-plane gate) and confirm green. NEVER de-commit before STEP 2/3 land.
- **STEP 6 — retire the vacuous machinery.** Remove the committed==regenerated predicate and
  the `FACE_SETTLE_PROTOCOL` / settle-and-commit ergonomics for de-commit-class faces (the
  mandatory pre-push re-materialize+re-commit barrier IS the serialization point). Add a guard
  gate FORBIDDING tracking `**/*.generated.json` producer outputs (except the explicit small
  exceptions). Add a gate asserting signoff/ratchet-policy are human-owned (not in the
  producer's output set). Begin the Rust-native successor to
  `materialize-cloud-ci-generated-faces.sh` (no-shell doctrine) — track as irreducible-glue
  until replaced.
- **STEP 7 — converge with cellular-hub / corpus (optional, non-blocking).** Publish each
  commit's materialized faces to CAS keyed by commit SHA for historical/offline inspection
  (reproducibility/audit — see §8). Per-capability shards become a WHERE-to-read optimization,
  not a re-committing of projections. Do not block STEPS 0-6 on corpus-substrate delivery
  (ADR-0541 / corpus is Phase -1, Proposed).

No step removes a gate input before its readers are repointed and its integrity predicate is
flipped, so gates never go dark and there is no flag-day.

## 8. Reproducibility / audit / provenance (does anything need a committed snapshot?)

- **Merge-base baseline**: needs a frozen reference a PR cannot regenerate — SATISFIED by the
  out-of-graph merge-base materialization (ADR-0551), NOT by a committed face.
- **Malicious producer detection**: SATISFIED by determinism (regen-twice cross-runner) +
  internally-valid predicate + the firewall re-deriving the proposed face by execing the
  buck2-built producer. A committed snapshot does NOT detect a malicious producer (the producer
  also writes the committed snapshot); it only detects hand-edits, which the no-tracked-generated
  guard makes impossible anyway.
- **scm-facts vs git**: the committed stable scm-facts (paths+blob SHAs) is information git's
  object DB already stores; nothing is lost by deriving it. The volatile half is already gone
  (ADR-0552).
- **Historical/offline inspection at release** (the one genuine pull toward a committed
  snapshot — `git show` of an old registry): SATISFIED by STEP 7 CAS-by-commit-SHA, which is
  superior (content-addressed, fetch-on-demand, no merge surface). Until STEP 7, derivation is
  reproducible from any historical tree by re-running the buck2 producer, because the faces
  carry no history-derived data (ADR-0552 guarantees this).

Conclusion: NO gate invariant genuinely needs the committed snapshot. The audit/release need
is real but is better served by CAS than by a tracked file.

## 9. Founder-doctrine cross-check

- **pipeline-as-product (universal + hermetic + automated + cloud-native)**: derivation engine
  is the buck2 producer (hermetic pure Rust, declared inputs, no git in the action). De-commit
  + no-tracked-generated guard + auto-materialization ships its own automation (not flag-only).
  The shell materializer (HOLE 5) is the one doctrine gap — mark transitional, plan Rust
  successor. ALIGNED with a caveat.
- **cold-vs-warm cache integrity-canary**: the regen-twice cross-runner determinism canary IS
  the integrity-canary that makes warm-by-default (derive-don't-commit) sound. ALIGNED.
- **born-accounting enforceability**: register-crate / accounting-registry remain fully
  enforceable — the registry is DERIVED and validated each PR by execing the producer; nothing
  about born-accounting depends on the bytes being committed. The firewall already proves this
  (it execs the producer for the proposed face). ALIGNED.
- **buck2 green != CI green** (MEMORY): every migration step's verification must run the
  freshness + affected-set gates AND regen the lock+faces, not just `buck2 build`. Encoded in
  STEP 5.
- **gate-baseline PR/push asymmetry** (MEMORY): the merge-base mechanism (ADR-0551) +
  stable/volatile split (ADR-0552) are the fixes for this exact class; this determination
  preserves them (frozen reference from merge-base, inert/drift predicates against the
  candidate). ALIGNED.
- **canonical-checkout-staleness** (MEMORY): the input recommendation fell into this trap (its
  CRITICAL CORRECTION analyzed a stale/different tree). This determination is verified against
  the live worktree. The open question "confirm against origin/dev whether these exist on the
  integrated tip" is INVERTED: they exist HERE; confirm they were not reverted upstream.

## 10. Risks

- **R1 (medium)**: STEP 3 freshness flip is subtle — a too-broad flip could stop catching a
  genuinely stale committed face that is still in the committed set (e.g. move-manifest).
  Mitigate: scope the flip per materialization_mode (committed-class keeps byte parity;
  not-tracked-class gets internally-valid+deterministic).
- **R2 (medium)**: scm-facts de-commit (STEP 5.7) has ~20-gate blast radius; a single
  unrepointed reader red-gates CI on a missing input. Mitigate: dedicated repoint IP (STEP 4)
  with a full-fleet green proof before the `git rm`.
- **R3 (low)**: nondeterminism currently masked by byte-equality (STEP 0 may flap). If it
  flaps, the committed copy was hiding a real bug — fix determinism first; do not de-commit.
- **R4 (low, doctrine)**: the shell materializer perpetuates no-shell debt. Mitigate: log as
  irreducible-glue, schedule Rust successor.
- **R5 (low)**: signoff door concurrent same-key edits. Mitigate: server-side union driver
  (#125) only if observed; (gate,code,key) keying makes it rare.

## 12. Net verdict

The recommendation's POLICY is SOUND (de-commit producer faces, keep the slim human set). Its
EXECUTION PLAN needs revision: the merge-base materialization, ADR-0551/0552, and the firewall
`main.rs` already exist (HOLE 1); the real committed-byte consumer is FRESHNESS not the
firewall (HOLE 2); the control-plane gate needs a `not-tracked-in-git` exemption BEFORE any
mode flip (HOLE 3); scm-facts is a ~20-gate declared hermetic input that must de-commit last
behind its own IP and is already half-done by ADR-0552 (HOLE 4); the materializer is shell
(HOLE 5); and the manifest class read was mislabeled (HOLE 6). The corrected ordering above
inserts the two missing prerequisite steps (control-plane exemption; correctly-scoped freshness
flip) and re-sequences scm-facts last, yielding a no-flag-day, no-dark-window strangler.
