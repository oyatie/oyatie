## FINAL SPEC
MECHANISM (firewall UNCHANGED; the staleness is fixed at the single sanctioned git boundary):

The firewall (cloud/cloud-ci/gates/oya-cloud-ci-firewall-app/src/lib.rs: compare / ratchet_growth / inert_signoff_entries / FrozenBaseline::from_value) stays byte-for-byte pure DATA-over-DATA on opaque string keysets — VERIFIED it never sees content, paths, or git. The fix is a content-aware relabel of the FROZEN merge-base snapshot's keys, applied inside the scm-facts emitter BEFORE build_merge_base_baseline_snapshot wraps it, driven by an authoritative committed move-manifest.

1) MANIFEST (the bijection, anti-forgery-bound). The codemod (tools/oya-reorg-codemod-app) is the sole holder of the bijection. MovePlan is crate-DIR level (VERIFIED model.rs: old_path/new_path are crate dirs, old_cargo_name/new_cargo_name are package names). The codemod emits a COMMITTED canonical-JSON generated face carrying BOTH (a) FILE-level pairs derived deterministically as <old_crate_dir>/<rel> -> <new_crate_dir>/<rel> for every tracked file under each moved crate dir (exact because plan.rs step-7 is a wholesale `git mv <old_dir> <new_dir>`), and (b) the crate-IDENT pairs (old_cargo_name->new_cargo_name) for tier-dep edge-endpoint mapping. Schema oya-ci/reorg-move-manifest/v1: {schema, capability, files:[{old_path,new_path}], crate_idents:[{old,new}]}. It is declared in registry/generated-artifact-control-plane.json with a generator_target of //tools/oya-reorg-codemod-app and final_tree_validation 'regenerate from final candidate tree + committed plan, byte-compare'; the existing registry-drift/freshness gate enforces committed==regenerated, so a hand-forged row is RED before the firewall runs. MovePlan::validate already guarantees the bijection (no dup/nested/colliding old/new — VERIFIED).

2) RELABEL PASS (in the emitter, resolve_merge_base_baseline_snapshot). After `face` is obtained at the merge_base (existing line ~316) and before build_merge_base_baseline_snapshot (existing line ~323), call a new pure relabel_frozen_face(face, manifest, source, merge_base, candidate_tracked, vocab_policy) -> Value. The emitter already has FrozenRefSource (merge_base + show_file at any revision) AND the candidate tree (repo_root + git ls-files). Per-gate dispatch keyed by gate id in face["gates"]; gates with non-path key spaces pass through untouched.

   CANDIDATE-SIDE PRIMITIVE (the load-bearing correction): candidate existence := membership in the emitter's tracked_paths (git ls-files) — the producer's exact universe — NOT `git show HEAD:`. Candidate content := the bytes the producer censuses (index via `git show :<path>` or on-disk under repo_root, consistent with the materialize step which regenerates from the checked-out candidate tree). Frozen-side := `git show <merge_base>:<path>` (unchanged). This is mandatory: VERIFIED that in the staged-uncommitted exhibit HEAD==merge_base, so a HEAD-keyed guard would never relabel and move-3 would stay RED.

   (A) cloud-ci-brand-residue (code=forbidden_<stem>, key=repo-relative file path). For each frozen (code, old_path) and each manifest FILE pair (old_path -> new_path):
       P1: old_path is a frozen key under THIS exact code.
       P2: old_path ABSENT from the candidate tracked set.
       P3: new_path PRESENT in the candidate tracked set.
       P4: NEW_OCC ⊆ OLD_OCC, OCC := de-duplicated set of normalized (lower-cased) matched-line texts of `stem` (decoded from code), computed by the SAME line-walk census_findings_with uses (skip wholly-path-carved files; skip LineContainsCi lines) with the LIVE VocabPolicy from oya-ci.toml. OLD_OCC over merge_base content of old_path; NEW_OCC over candidate content of new_path. Subset (move may DROP residue, must ADD none).
       If P1..P4: remove old_path from [code].keys, insert new_path. Else: leave old_path (fail-closed -> firewall reads it as fixed/regression normally). Reject fail-closed if new_path is already a distinct frozen key under that code.

   (B) cloud-ci-tier-dependency-acyclicity (key="<code>|<from-ident> -> <to-idents>", VERIFIED). Map endpoint IDENTS via manifest crate_idents (old_cargo_name->new_cargo_name). Relabel a frozen edge key ONLY IF the rewritten edge key is already present in the candidate edge keyset the producer emitted (conservative existence guard — avoids duplicating graph logic at the git boundary). A resolved edge is left (reads fixed); a new inversion was never a frozen key so is never relabeled and the gate recomputes acyclicity over the candidate graph => RED.

   (C) total-accounting / target-parity (key = path / member_path). Relabel old->new per the FILE/dir manifest pair iff P2 (old absent from candidate keyset for that code) and P3 (new present). Pure existence keys; the codemod's own buck/cargo rewrites are independently registry-drift-checked.

3) CENSUS PARITY. relabel_frozen_face computes P4 via libs/oya-check-brand-residue::forbidden_vocab (census_findings_with line-walk + is_path_carved_out_with + is_line_carved_out_with) under the VocabPolicy sourced from oya-ci.toml via oya-ci-config-kernel — byte-identical to the producer's collect_brand_residue (VERIFIED main.rs:445/467 uses census_findings_with + vocab_policy(cfg)). So both sides agree on carve-outs and case-folding.

4) FAIL-CLOSED EVERYWHERE. Missing/malformed manifest, unreadable content, ambiguous pairing, or any guard failure => identity (no relabel) => the firewall sees the honest stale frozen face and goes RED on the moved paths. The relabel can only ever REMOVE a false-RED for a proven pure-or-shrinking relocation; it can never manufacture a false-GREEN. No _sign_off_additions used (founder doctrine: purely mechanical rename, no signoff door).

WHY MOVE-3 GOES GREEN (verified on the live exhibit): the 3 frozen forbidden_foundry keys (cloud/cloud-observability/crates/oya-cloud-observability-domain/src/lib.rs, cloud/cloud-observability/crates/oya-cloud-observability-api/tests/cloud_observability_audit_api.rs, oya/observability/crates/oya-observability-domain/src/lib.rs — all present in the frozen baseline, confirmed) each have: P1 yes (frozen key under forbidden_foundry); P2 yes (old path not in candidate tracked set — ls-files confirms); P3 yes (new observability/core/* path in candidate tracked set); P4 yes (foundry line byte-identical old vs new => NEW_OCC==OLD_OCC). They relabel to the observability/core/* new paths; the firewall then differences candidate (new paths) vs relabeled-frozen (new paths): tolerated, zero regressions, zero growth. cloud-ci-brand-residue GREEN; firewall GREEN; staged move preserved.

## Attack/hole analysis (all defeated unless noted)

- [HIGH (blocks move-3 as written; latent soundness drift)] CANDIDATE-SIDE PRIMITIVE IS HEAD, NOT THE CANDIDATE TREE (the one real defect; both designs share it). Both A and B write the P2/P3 (and P4 new-side) guards against `git show HEAD:<path>` / `show_file("HEAD", path)` / `repo_root.join(new_path)` treating HEAD as the candidate. But the producer the firewall consumes scans the CANDIDATE TREE via --repo-root (working tree + index), and the emitter's universe is `git ls-files` (the staged/index tracked set). VERIFIED in this worktree: the move is STAGED-uncommitted, so HEAD == merge_base == f2cf13a; `git cat-file -e HEAD:observability/core/aggregate/src/lib.rs` => ABSENT and `HEAD:cloud/.../oya-cloud-observability-domain/src/lib.rs` => PRESENT. So a HEAD-keyed P2 (old absent from HEAD) and P3 (new present in HEAD) BOTH FAIL on the actual exhibit => NO relabel => the 3 files stay RED => move-3 NOT unblocked. The fix is not cosmetic: the candidate side must be the producer's tracked-path universe and content (git ls-files for existence; `git show :<path>` index content or on-disk for content), the SAME source the producer censuses. Read against the candidate tree, the staged exhibit satisfies P2/P3 (ls-files shows new tracked, old not tracked) and P4 (index foundry count old=1==new=1).
  fixed_by: Synthesis: candidate-existence := membership in the emitter's tracked_paths (git ls-files); candidate-content := the bytes the producer censuses (read via `git show :<path>` for the index, or on-disk under repo_root — whichever the producer uses; they agree at gate time because the materialize step regenerates from the same checked-out tree). NEVER `git show HEAD:`. Frozen-side stays `git show <merge_base>:<path>` (unchanged). P4 reuses census_findings_with over the live VocabPolicy on BOTH sides.

- [MEDIUM] P4 occurrence-identity must be the line-content SET, not a count, and must run the SAME carve-out line-walk on both sides.
  fixed_by: P4 := NEW_OCC ⊆ OLD_OCC where OCC = set of normalized matched-line texts (lower-cased, the exact line-walk census_findings_with does: skip wholly-path-carved files, skip LineContainsCi lines e.g. palantir), de-duplicated, line-number-free (churn-stable). Subset (not equality) so de-brand may DROP lines; ANY new line breaks subset => no relabel => RED. Both designs already specify line-content subset; I pin it as mandatory, rejecting the count variant.

- [defeated] stem-swap during move (foundry -> jenkins).
  fixed_by: Relabel is PER-(gate,code). Relabeling forbidden_foundry's old_path->new_path never touches forbidden_jenkins. At new_path the census emits a forbidden_jenkins key absent from the frozen forbidden_jenkins set => compare() regression + ratchet_growth() => RED. Independently, P1 (old_path is a frozen key under THIS code) fails for forbidden_jenkins (old_path carried no jenkins), so nothing is relabeled there. Verified no moved file carries a second stem in the live exhibit, and the per-code set algebra closes it abstractly.

- [defeated] add-residue-within-an-otherwise-pure-move.
  fixed_by: P4 NEW_OCC ⊆ OLD_OCC fails (the injected line is in NEW_OCC, not OLD_OCC) => old_path NOT relabeled => old_path reads `fixed` AND new_path is a genuine new forbidden_foundry key vs the (unmoved) frozen set => compare regression + growth => RED. This is the exact hole that sank the -M100% relaxation; content-subset closes it structurally.

- [defeated (two independent layers)] false-manifest-pair (claim accepted_old -> unrelated_new_with_residue).
  fixed_by: Layer 1 anti-forgery: the manifest is a GENERATED face produced by the codemod from the committed MovePlan over the candidate tree; the registry-drift/freshness gate regenerates it in-sandbox and byte-diffs committed==regenerated (the same discipline that protects every .generated.json). A row the codemod would not regenerate => RED before the firewall runs. MovePlan::validate (verified in model.rs) rejects duplicate/nested/colliding old/new => bijection. Layer 2 guard: even a regen-consistent forged pair must pass P2 (old genuinely absent from candidate tree), P3 (new genuinely present), P4 (new occurrence-set subset of old). An unrelated new file with its OWN residue fails P4; a clean new file is not a frozen key for that code at all.

- [defeated] carve-out asymmetry (move out of / into a carve-out).
  fixed_by: OLD_OCC and NEW_OCC are both computed with is_path_carved_out_with + is_line_carved_out_with from the LIVE VocabPolicy (oya-ci.toml [vocab]). If old_path wholly carved at MB => no frozen key under that code (P1 false) => nothing to relabel. If new_path wholly carved => producer emits no candidate key for it (consistent) and it is not a relabel target. A single LineContainsCi (palantir) difference is reflected identically on both sides because the same line-walk runs on both contents. No asymmetry can fabricate a subset that hides real residue.

- [defeated] ambiguous/duplicate pairing.
  fixed_by: Pairing is the codemod's authoritative file-level bijection derived from the crate-dir MovePlan (verified: plan.rs step-7 does a wholesale `git mv <old_dir> <new_dir>`, so <old_dir>/<rel> -> <new_dir>/<rel> is exact and total over moved-dir contents). NO git -M, no -C, no similarity threshold. MovePlan::validate guarantees injectivity; on any residual collision (two olds -> same new, or new already a distinct frozen key) the relabel FAILS CLOSED (leave both originals) => RED.

- [defeated] moved-AND-edited (the NORM; 2 of 3 targets are R099).
  fixed_by: Pairing is manifest-driven (independent of similarity), and safety is content-subset (P4) not edit-distance. VERIFIED: aggregate old(mb) and new(staged) foundry line is byte-identical (`actor: "sp_foundry"` at line 1749); api-test identical (line 123); domain identical (5 lines: 45,46,51,52,347,369). NEW_OCC == OLD_OCC => subset holds => relabel applies => GREEN. The R099/R100 status is irrelevant to the decision.

- [defeated] a file carrying TWO stems where only one moves.
  fixed_by: The relabel iterates per-(code, old_path) frozen key independently. A two-stem file produces TWO frozen keys (forbidden_foundry|path, forbidden_jenkins|path); each is relabeled separately, each gated by its own P4 on its own stem. Both transfer iff both subsets hold; if the move added a jenkins line, only forbidden_jenkins fails P4 (RED for jenkins) while forbidden_foundry transfers correctly. No coupling, no silent drop.

- [defeated, with a tightening] edge whose endpoint crate moved AND whose inversion was newly introduced (tier-dep).
  fixed_by: Tier-dep key shape VERIFIED as `"<code>|<from-ident> -> <to-idents>"` (e.g. TDA-CYCLE|a -> b,c) over crate IDENTS, not crate dirs. Relabel maps endpoint IDENTS via the manifest's old_cargo_name->new_cargo_name (NOT old_path->new_path — a correction to both designs, which said crate-dir), and relabels a frozen edge key ONLY IF the rewritten edge STILL EXISTS in the candidate observed-edge set the producer emits. A NEWLY-introduced inversion is not a frozen edge (its endpoints were never a frozen key) => never relabeled => the gate recomputes acyclicity over the candidate graph and goes RED. A genuinely-resolved edge is `fixed` (not relabeled). To avoid duplicating graph logic at the git boundary, the conservative form (relabel iff the rewritten edge key is already a candidate key the producer emitted) is recommended.

- [defeated (fail-closed)] buggy/hostile codemod manifest (the codemod itself emits a wrong bijection).
  fixed_by: The guards re-verify against REAL state independent of the manifest's claims: P2/P3 check the candidate tracked set (a manifest claiming new-present when ls-files disagrees => no relabel), P4 checks real content. A manifest that disagrees with the actual move cannot relabel beyond what the content/existence facts already license; worst case is false-RED (move stays blocked), never false-GREEN. Plus the registry-drift byte-equality binds the manifest to the deterministic codemod output.
