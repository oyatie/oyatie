# Enterprise omni-SaaS suite — interview decisions (founder, 2026-08-20)

Thesis: a superset of Palantir Foundry/Ontology + SAP + Slack. Entity/object/action/analytics built in.
All statements below are founder answers unless marked (open).

## Scope and buyers
- D1  V1 module clusters: **Finance core** (accounting, payments, treasury, financial-planning) + **People suite** (hr, payroll, performance-management, learning-management).
- D2  Buyers: Enterprise, Global Enterprise, Global SME, Korea SME — ALL in scope; do not tunnel on one. **Korea localization pack first.** Architecture must make localization packs first-class.
- D3  Scale envelope: mid-market first, ratcheting to thousands of multi-enterprise tenants (certified envelopes, not redesigns).
- D4  Packaging: per-seat suite tiers + jurisdiction-pack add-ons; usage-metered items via billing/. **Mail, messenger, community (social) are free** — unlimited seats, quota-bound (storage, fair use; custom domain on paid tiers).

## Platform spine (Foundry-class)
- D5  The Foundry-class platform is the spine; the Ontology (typed Object/Link/Action/Function, **Bominal** ADR-0106 lineage = oyatie ADR-0006/0055) runs on it. Distinct from the RETIRED "foundry" AI/RAG contracts under contracts/openapi/foundry.
- D6  Capability root stays **data/** (no rename to foundry/, no new sibling root). data/ = datasets + pipelines + lineage + ontology binding + built-in analytics. (Earlier answer chose "new root foundry/"; later answer "data sounds fine" — resolved as: data/ is the foundry-class root.)
- D7  Model/AI integration (intelligence/ bound to ontology objects, AIP-class): **built, flag-disabled on day 1**; platform must function without it.
- D8  Write model: **Action → Event → [Document → Posting]**. Every business write is a typed ontology Action (validated, Cedar-gated, audited). Actions emit events. Actions with financial effect produce a Document; documents post journal entries to the universal ledger.
- D9  Event truth: **platform-level event sourcing** — the ontology write path appends to a per-object event log; ontology state is the platform-maintained projection; ledger journal and audit chain ride the same log; app teams define Actions only and never implement replay. (Recommended by Claude; founder accepted via follow-up questions.)
- D10 Erasure: **crypto-shredding** — PII only in ciphertext-typed properties (**Bominal** ADR-0111 lineage = oyatie ADR-0006 ciphertext tier), per-data-subject keys in secrets/, erasure = key destruction; covers log + projections + snapshot backups; enforced by a schema-lint gate that PII cannot appear in plain event fields.
- D11 **Legal retention overrides erasure**: some data is required by law to be retained (e.g., Korea: accounting books/vouchers, payroll and withholding records, e-tax invoices; EU: tax/employment records). Retention classes and periods are jurisdiction-pack data; legal hold blocks key destruction for the retained class; erasure applies to everything else about the subject.
- D12 Built-in analytics engine: **ClickHouse behind the data/ analytics port now** (recorded C++ exception to the entirely-Rust bar, language-agnostic it is the better OLAP server today), **owned DataFusion/Arrow-based engine later** as the swap. Arrow/Parquet is the dataset format; protobuf remains RPC serialization only.
- D13 Extensibility: two tiers, **built but flag-off in v1** (same posture as AI): Tier 1 WASM (wasmtime) in-path functions — validation, computed fields, hooks, capability-scoped, ms-budgeted; Tier 2 Firecracker microVM jobs for heavy partner apps. Both marketplace-reviewed. **Config-level extension is ON in v1**: ontology overlay types, Cedar policies, automations, report/format templates. No proprietary language, ever.
- D14 Import: one shared **import engine** underneath (consistent behavior); Excel is the v1 adapter through the port; incumbents (Douzone/SAP B1) later adapters.

## Round 15 (2026-08-20)
- D65 **L4 is enrollment-time, not per-transaction.** Founder correction: eKYC (document + liveness) is performed ONCE at signup/onboarding (industry pattern), with a validity period (re-verify on document expiry or annually, pack-configurable). The assurance level is a property of the principal; Cedar `acr_required` checks the level HELD and its recency. Per-transaction step-up is L2 re-auth (passkey), plus pack-defined **transaction signing** where a jurisdiction requires it (e.g., KR firm-banking 공동인증서 signature per transfer batch) — a different mechanism from identity assurance. Defaults for which actions require L4-held (payment/treasury above threshold, legal-entity/ownership/signatory changes, break-glass, optional personal-network badge) stand as pack data.
- D66 **i18n/a11y**: ko + en at parity (UI, docs, statutory output); ICU messages, locale-aware formats, CJK typography; RTL-ready; WCAG 2.2 AA enforced by a CI a11y gate; KWCAG alignment.
- D67 **FinOps**: per-tenant → legal-entity → capability cost attribution from day 1; unit economics (per seat, mailbox, posting, MAU) in console; free-tier cost tracked as CAC; margin gates on pricing changes; billing/ rates from the same stream.
- D68 **Isolation — adversarial review of the proposed "flat encrypted KV + per-tenant DEK + ephemeral creds" architecture (founder asked to question the prose, adopt only worthy patterns, add no dependencies):**
  - REJECTED: a flat append-only encrypted KV as the ONLY store ("no tenant tables"). It kills indexes, joins, aggregates, balances, Grid, analytics; every query needs decrypted projections — which re-creates the tables it claims to remove, in a second system. "Immune to SQL injection" is already true of parameterized queries; the bug moves to the app layer where decryption happens. We ALREADY have the append-only system of record (D9 event log); queryable projections stay.
  - REJECTED: encrypting EVERY field app-side under one per-tenant DEK. DB cannot filter/sort/sum/search ciphertext → performance cliff at D49/D55 envelopes; hot path hammers KMS; "flush memory immediately" contradicts DEK caching; compromised app servers hold DEKs anyway, so the "mathematics" claim holds only against storage/backup/DBA threats (which ARE worth defending).
  - REJECTED: per-request 30-second dynamic DB credentials + OPA proxy. Destroys connection pooling at 1,000 postings/s; Vault dynamic secrets rotate per service (hours), not per request; OPA = second policy engine (violates Cedar-sole, ADR-0702) and a Go dependency; DB roles don't scope to tenant partitions — RLS + `SET LOCAL` does.
  - REJECTED deps: CockroachDB (BSL), ScyllaDB/RocksDB (C++), Vault (BSL), Acra. Postgres now → fabric data tier later (TiKV) stands.
  - ADOPTED (the worthy patterns): (1) **PDP-gated key release** — the Cedar+Zanzibar decision returns the key-context handle; no decryption without a passing decision. (2) **No ambient authority** — every transaction opens with `SET LOCAL` tenant context enforced by RLS; services authenticate with short-lived workload identity (SPIFFE/SVID, already in iam), never static all-tenant connection strings. (3) **Tiering by key custody, not schema**: standard = platform-managed per-tenant keys; enterprise = CMK/BYOK by key swap (no migration); sovereign/BYOC = HSM in a dedicated cell. Schema-per-tenant is DROPPED as a tier. (4) **Field-classed encryption**: ciphertext-class properties (PII, secrets, biometrics) app-side under per-subject DEKs beneath the tenant KEK (D10/D48); all data at rest under per-tenant storage keys; structural/financial fields plaintext-in-DB behind RLS so they stay queryable. (5) Append-only log as system of record — already D9.
  - RESULT — **three-plane isolation**: authz plane (Cedar + Zanzibar, D64) → crypto plane (key custody tiers + field-classed envelope encryption) → storage plane (RLS + tenant partitioning + dedicated cells; event log tenant→entity→object; ledger by legal_entity). Pending founder confirm.
